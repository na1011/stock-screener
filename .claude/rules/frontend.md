# 프론트엔드 판단 기준

대상 사용자는 전문 트레이더가 아닌 초보~중급 투자자다. 이 전제가 화면 설계 판단의 기준이다. 폭넓은 지표를 다루면서도 사용자가 소외되지 않아야 한다.

- MUST NOT: 지표를 값만 나열하지 않는다. 초보 사용자는 그 값이 좋은 것인지 나쁜 것인지 알 수 없다. 지표가 무엇을 의미하는지, 어느 방향이 유리한 신호인지 함께 제공한다.

- MUST: 스크리닝 결과에 선정 이유를 노출한다. 프리셋 전략은 조건별로 획득한 점수를 확인할 수 있게 한다. 이유가 보이지 않는 결과는 신뢰를 얻지 못한다.

- MUST: 지지·저항 정보는 확정된 매매 신호와 시각적으로 명확히 구분한다. IMPORTANT — 사용자가 이를 매매 신호로 오해하면 실제 금전적 손실로 이어진다.

- MUST NOT: 진입가·손절가처럼 구체적인 매매 실행 가격을 제시하지 않는다. 이 서비스의 목적은 종목 발굴이다.

- MUST: 오류가 나도 문제 영역만 격리하고 화면 전체는 정상 동작하게 한다. 일시적 오류는 사용자 개입 없이 짧게 자동 재시도하고, 그래도 실패하면 사용자가 직접 재시도할 수단을 제공한다.

- 데스크톱과 모바일은 한 번에 노출할 수 있는 정보량이 다르다. 같은 화면을 축소해 보여주는 대신, 정보 밀도 높은 상세 분석과 빠르게 훑어보는 조회를 각 디바이스에 맞게 다르게 다룬다.

- MUST: 관리자 영역은 일반 사용자 화면과 명확히 구분하고, 권한 없는 사용자에게 노출하지 않는다. 관리 기능이 보이는 것만으로도 운영 구조가 드러나며, 지인이 쓰는 서비스라도 계정별 권한 경계는 유지되어야 한다.

## 서버가 준 것을 화면이 되짚지 않는다

- MUST NOT: 지표 코드로 분기하지 않는다. 유불리 방향은 `lib/direction.ts`가 서버의 `higherIsBetter`·`favorableEnd`만 보고 판단한다. **그 함수들이 지표 코드를 인자로 받지 않는 것**이 강제 수단이다 — 받는 순간 백엔드에서 없앤 하드코딩이 프론트로 옮겨온 것이고, 지표가 추가될 때마다 화면을 고쳐야 한다.
- MUST NOT: 값 부재를 `?? 0`으로 메우지 않는다. 서버는 계산되지 않은 지표의 **키 자체를 보내지 않는다.** `Object.hasOwn`으로 가르고 `—`(`MISSING`)로 그린다. 0으로 그리면 사용자는 부채비율 0%인 회사를 본 것으로 읽는다. 정렬 비교자에서도 마찬가지다 — 내림차순에서는 우연히 맞아 보이지만 오름차순이 생기는 순간 값 없는 종목이 최상위로 올라온다.
- MUST NOT: 서버가 판단해서 주는 값을 다른 필드로 다시 유도하지 않는다. `editable`은 "고쳐도 되는가"이고 `type`은 "어디서 왔는가"다. 권한 질문에 출처로 답하면, 서버가 규칙을 바꿔도 화면이 따라오지 못하고 **서버와 모순된 상태**가 된다.
- MUST NOT: 서버가 이미 아는 사실을 화면이 다른 요청으로 재계산하지 않는다. 그 요청만 실패했을 때 판단이 조용히 뒤집힌다 — 백분위 주의 문구가 카탈로그 실패로 사라지던 것이 그 사례다.

## 모르는 값을 만났을 때

타입 수준 exhaustiveness는 **누군가 유니온을 갱신했을 때만** 돕는다. 백엔드가 값을 늘리고 프론트가 낡았을 때가 진짜 위험이고, 그때 무엇을 할지는 매핑마다 **의도적으로** 정한다.

- MUST: 뜻이 왜곡되는 곳은 **던진다.** 판정 상태(`lib/outcome`), 유불리 방향(`lib/direction`), 판정 방식(`lib/evaluationMode`), 화면 종류(`lib/screen`)가 그렇다. 틀린 라벨은 결과를 잘못 설명하고, 그 오해는 사용자가 대조하기 전까지 드러나지 않는다.
- MUST: 배치·이름만 흔들리는 곳은 **낯선 이름을 그대로 보인다.** 지표 분류(`lib/indicatorCategory`), 지지·저항의 역할·강도·산출 방식(`lib/priceReference`)이 그렇다. 던지면 새 값 하나 때문에 영역 전체가 사라지는데, 지지·저항 패널은 사라지는 것이 가장 나쁘다 — 경고 문구가 함께 없어진다.
- MUST NOT: 모르는 값을 **걸러내지** 않는다. 던지는 것도 감추는 것도 아닌 세 번째 선택지처럼 보이지만, 사라졌다는 사실 자체가 드러나지 않아 셋 중 가장 나쁘다. 실제로 조건 빌더에서 지표 한 분류가 통째로 선택 불가능해진 적이 있다.
- MUST: 순서·선택지 배열은 `Record<Union, T>`나 `as const` 배열에서 파생시킨다. 손으로 적은 `Union[]` 배열은 빠뜨린 값을 잡지 못한다.

## 문자열을 어디에 두는가

다국어는 하지 않는다. 그래서 전역 문자열 테이블(`t('screener.run')`)도 만들지 않는다 — 얻는 것이 없고, 한 번만 쓰는 문구는 오히려 파일을 하나 더 열어야 버튼에 뭐라고 쓰였는지 알 수 있게 된다.

- MUST: 한글 리터럴이 템플릿을 떠나는 것은 **(a) 값을 백엔드 enum·상수가 정하거나 (b) 둘 이상의 컴포넌트가 같은 것을 그릴 때**뿐이다. 그 외에는 템플릿에 그대로 둔다.
- MUST: 한 개념에 여러 문구가 필요하면 합치지 말고 **변형에 이름을 붙여 한 곳에 모은다**(`evaluationModeLabels`의 `noun`/`short`/`action`). 고르는 버튼에는 동사가, 요약에는 명사가, `Tag`에는 두 글자가 들어가야 한다. 하나로 합치면 어느 한 자리는 반드시 어색해진다.
- MUST NOT: 한국어 조사를 코드로 계산하지 않는다. 종성 판정(`(코드 - 0xAC00) % 28`)은 순한글에서만 맞고 `S&P500` 같은 이름에서 **조용히 틀린다.** 닫힌 집합이면 데이터로 적고(`ASYNC_PANELS`), 맞는지는 테스트가 검사한다.

## 값이 두 곳에 있어야 할 때

- MUST: 서버 값을 프론트가 거울로 들면 `wire-contract.json`에도 함께 적는다(ADR-0020). 거울은 어긋나도 아무 데서도 티가 나지 않는다.
- MUST: 화면 폭 경계값은 `lib/breakpoints.ts`에만 적는다. CSS는 리터럴 px을 유지하되(미디어 쿼리는 `var()`를 받지 않는다) `breakpoints.spec.ts`가 토큰 밖의 값을 잡는다. **표↔카드 경계는 JS와 CSS 양쪽에 걸쳐 있어** 어긋나면 좁은 폭 구간에서만 레이아웃이 깨진다.
- MUST: 자동 재시도는 GET에만 붙인다. 생성 요청을 재시도하면 응답만 유실된 경우 같은 화면이 두 개 만들어진다. 조회인데 POST인 `/api/screening`은 호출부가 명시적으로 켠다.

**빌드·의존성 함정은 `.claude/rules/config.md`에 있다** — `./gradlew build`의 프론트 결합과 primevue 4.x 고정(ADR-0019)이 거기로 갔다. 트리거가 `frontend/src/**`가 아니라 `build.gradle`·`package.json`이기 때문이다.
