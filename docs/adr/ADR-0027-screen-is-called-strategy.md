# ADR-0027. 저장된 스크리닝 정의를 한국어로 "전략"이라 부르고 영문 식별자 `screen`은 그대로 둔다

## 결정

사용자에게 보이는 한국어에서 저장된 스크리닝 정의(프리셋 + 사용자가 저장한 것)를 **"전략"**이라 부른다. **영문 식별자는 `screen`을 유지한다** — DB 테이블 `screen`·`screen_condition`, API `/api/screens`, 에러 URN `duplicate-screen-name`, TS 타입 `ScreenResponse`·`ScreenType` 전부 그대로다.

"화면"은 **UI 뷰·페이지·뷰포트만** 가리킨다.

## 규칙

- MUST: 저장된 스크리닝 정의를 한국어로 가리킬 때 "전략"이라 쓴다. 섹션 제목은 "프리셋"/"내 전략", 관리 페이지는 "전략 관리", 저장 대화상자는 "전략 이름"·"새 전략으로 저장"이다.
- MUST: 개별 조건(칩 하나)은 "조건", 그것들을 모은 저장 단위는 "전략"이다. **한 낱말이 두 층위를 겸하지 않는다.** `FRESH_DRAFT_TITLE`이 "새 조건"이던 동안 사용자가 그 버튼을 "프리셋을 추가하는 것"으로 읽었다.
- MUST NOT: 영문 식별자를 `strategy`로 바꾸지 않는다. 얻는 것은 영문 일관성뿐인데 마이그레이션·`wire-contract.json`(ADR-0020)·ADR 넷을 함께 고쳐야 하고, 실데이터가 적재된 상태다.
- MUST NOT: 한국어 "화면"으로 저장된 정의를 가리키지 않는다. 뷰포트 뜻으로는 계속 쓴다 — 낱말 자체를 금지하는 것이 아니다.
- MUST: 새 사용자 노출 문구를 쓸 때 `lib/screen.ts`의 `screenTypeLabel`이 정본인지 먼저 본다. 세 곳(전략 목록·스크리너의 선택기·조건 빌더의 태그)이 같은 두 낱말을 각자 적고 있던 것을 그 함수가 모았다.

### 대응표

| 영문 식별자 | 한국어 표시어 |
|---|---|
| `screen`, `ScreenResponse`, `/api/screens` | 전략 |
| `ScreenType.PRESET` | 프리셋 |
| `ScreenType.CUSTOM` | 내 전략 |
| `screen_condition`, `DraftCondition` | 조건 |
| (해당 없음 — UI 뷰) | 화면, 페이지 |

`watchlist` → "관심종목"이 이미 같은 형태다. 영문 식별자와 한국어 표시어가 다른 것은 이 코드베이스의 예외가 아니라 통상이다.

## 검증

```bash
cd frontend && npx vitest run src/lib/terminology.spec.ts
```

`lib/terminology.spec.ts`가 `frontend/src/**/*.{vue,ts}`(단, `.spec.ts` 제외)를 훑어 **엔티티 뜻으로만 성립하는 연어**(`내 화면`·`화면 관리`·`화면 이름`·`화면 목록`·`화면 삭제`·`화면 선택`·`저장한 화면`·`저장된 화면`·`화면으로 저장`·`화면 덮어쓰기`·`커스텀 화면`·`남의 화면`)를 찾으면 파일·줄·문구를 찍고 실패한다.

낱말 "화면" 전체를 금지하지 않는 것이 요점이다 — 전부 막으면 "좁은 화면"·"화면 폭"까지 걸려 규칙이 곧 무시된다. `.spec.ts`를 제외하는 이유는 금지 문구 목록이 그 파일 안에 리터럴로 있어 스캐너가 자기 자신을 잡기 때문이다. `breakpoints.spec.ts`처럼 **스캐너가 실제로 파일을 읽었는지**(파일 수 > 20)를 먼저 단정한다.

## 배경

기획 정본(`docs/stock-screener-project-spec.md`)은 "화면"을 **오직 UI 뷰 뜻으로만** 쓴다. 저장된 스크리닝 정의를 spec이 부르는 말은 "커스텀 스크리닝"·"조건 조합"·"사전 정의된 투자 전략"이다.

지금의 오역은 `V3__condition.sql`(Phase 1, `eb6a4c1`)이 `CREATE TABLE screen`을 만들면서 시작됐다. **그 테이블의 정의 주석은 자기를 "스크리닝 정의"라고 부르는데**, 같은 파일 아래쪽에서 이미 `screen`을 "화면"으로 옮기고 있었다 — 더 나은 역어가 같은 파일 안에 있었는데 채택되지 않았다. 그 역어가 ADR-0003 → ADR-0017 → `design/v1-architecture.md` → ADR-0024/0026 → `.claude/rules/frontend.md` → 사용자 노출 문구까지 검증 없이 전파됐다.

결과는 동음이의어다. `AppRail.vue`에는 `aria-label="주요 화면"`(UI 뜻) 바로 아래에 `<span>화면 관리</span>`(엔티티 뜻)가 있었다. 대상 사용자가 초보~중급 투자자인데(`frontend.md`) "화면을 저장한다"는 말은 기획 어디에도 근거가 없다.

**옛 ADR(0003·0017·0024·0026)과 그 안의 "화면"은 고치지 않는다.** 결정 당시의 기록이고, 소급 수정하면 무엇이 언제 정해졌는지 알 수 없게 된다. 그 문서들을 읽을 때 이 대응표를 함께 본다.

## 버린 대안

- **"조건식"** — 키움 영웅문의 "조건검색식"과 같은 국내 증권앱 표준어라 경험자에게 즉시 통한다. 그러나 개별 조건(칩)과 한 글자 차이라 두 층위를 가르는 목적을 절반만 달성하고, 초보~중급이라는 대상 사용자에게 딱딱하다.
- **"스크리닝"** — spec이 실제로 쓰는 낱말("커스텀 스크리닝")이다. 그러나 셀 수 있는 명사로 쓰면 어색하고("스크리닝 3개"), 행위(스크리닝을 실행한다)와 사물(스크리닝을 저장한다)이 같은 말이 된다.
- **"스크리너"** — 이미 (1) 서비스 이름 `주식 스크리너` (2) 메인 뷰의 nav 라벨 (3) 라우트 이름 `screener` 셋을 가리킨다. 네 번째 뜻을 얹으면 지금 고치려는 중의성이 그대로 재발한다.
- **영문 식별자까지 `strategy`로 전면 개명** — 영문 일관성은 얻지만 마이그레이션을 새로 쓰고 `wire-contract.json`·백엔드 `WireContractTest`·ADR 넷을 함께 고쳐야 한다. 실데이터가 적재된 상태(2026-08-06)라 위험 대비 이득이 없다. 한국어 표시어와 영문 식별자가 다른 것은 `watchlist`→"관심종목"으로 이미 선례가 있다.

## 결과

쉬워지는 것: 사용자가 "전략"과 "조건"을 층위로 구별한다. `＋ 조건`(칩 추가)과 `새 전략`(전부 비우기)이 같은 낱말을 쓰지 않게 되어 두 버튼의 뜻이 라벨만으로 갈린다. 문서에서 "화면"을 만나면 UI 뷰라고 확신할 수 있다.

어려워지는 것: 코드를 읽을 때 `screen`(식별자)과 "전략"(표시어)을 머릿속에서 잇는 단계가 하나 생긴다. 위 대응표와 `lib/screen.ts`의 주석이 그 비용을 갚는다.

되돌리려면: `lib/terminology.spec.ts`를 지우고 `lib/screen.ts`의 `screenTypeLabel`부터 되돌린다. 사용자 노출 문구가 `.claude/rules/frontend.md`의 배치 규칙대로 템플릿에 흩어져 있어 전역 치환으로는 끝나지 않는다 — UI 뜻의 "화면"이 같은 파일에 섞여 있기 때문이다.
