# ADR-0009. 국내 두 소스의 실패 표현이 정반대이므로 봉투 판별을 각각 만든다

## 결정

공공데이터포털과 DART의 응답 판별을 **공통화하지 않고 소스별로 분리**한다. 실패를 알리는 방식이 정반대이기 때문이다. 어댑터는 키가 실제로 설정되어 있을 때만 빈으로 등록한다(`@ConditionalOnApiKey`).

## 규칙

- MUST: 공공데이터포털 응답은 **두 가지 봉투를 모두** 파싱한다 — 정상은 `response.header`, 오류는 `OpenAPI_ServiceResponse.cmmMsgHeader`다.
- MUST: DART 응답은 **HTTP 상태와 무관하게 `status` 필드를 파싱**한다. 인증 실패도 HTTP 200으로 온다.
- MUST: 공공데이터포털 호출 **전에** 파라미터를 검증한다(티커 `\d{6}`, 구간 순서). 잘못된 파라미터가 빈 결과와 구별되지 않는다.
- MUST: 공공데이터포털 응답은 **`totalCount`를 읽어 페이징한다.** 종료 조건은 `누적 수신 >= totalCount`이며, "한 페이지가 `numOfRows`보다 적으면 끝"으로 판단하지 않는다 — `likeSrtnCd`가 부분 일치라 다른 종목이 섞이고, 그것을 걸러내면 페이지당 유효 건수가 항상 `numOfRows`보다 적어 첫 페이지에서 멈춘다. **(2026-08-06 추가.)**
- MUST: 페이징 진행도는 **필터 전 행 수**로 센다. 걸러낸 뒤의 수로 세면 다른 종목만 담긴 페이지에서 진전이 0이 되어 같은 페이지를 무한히 다시 읽는다.
- MUST NOT: `numOfRows` 상한에 기대어 페이징을 생략하지 않는다. 실측상 2,000까지 받아주지만 문서화된 값이 아니며, 벤더가 조이는 순간 **다시 조용히 잘린다.**
- MUST NOT: 페이징 중 실패했을 때 **부분 결과를 반환하지 않는다.** `PriceCollector`가 반환 목록을 완전한 구간으로 취급하므로, 부분 반환은 "그 기간에 데이터가 없다"와 구별되지 않는다.
- MUST: 어댑터는 벤더 예외를 `DataSourceException`으로 감싼다(ADR-0006).
- MUST: 발급 키를 `normalizeServiceKey`로 디코딩해 넘긴다. 이중 인코딩되면 "등록되지 않은 서비스키"로 보인다.
- MUST NOT: `RestClient`에 공통 상태코드 핸들러를 걸지 않는다. 어댑터가 상태코드와 본문을 함께 봐야 한다.
- MUST NOT: `fnlttSinglIndx`(주요 재무지표)를 쓰지 않는다. 계산된 비율을 반환하고 2023년 3분기 이후만 제공한다.
- MUST NOT: `@ConditionalOnProperty`로 키 유무를 판단하지 않는다. 빈 문자열도 "속성 있음"이라 조건이 참이 된다.

## 검증

```bash
./gradlew test --tests "*DataGoKrPriceAdapterTest*" --tests "*DartFinancialAdapterTest*" --tests "*DartAccountMapperTest*"
```
통과해야 한다. 실제 응답을 녹화한 `src/test/resources/fixtures/`로 검증하므로 API 키가 필요 없다. 특히 "미등록 키는 AUTH", "잘못된 키는 AUTH(HTTP 200)", "잘못된 티커는 호출 전에 막는다"가 이 ADR의 실질이다.

```bash
./gradlew liveTest
```
키가 있으면 실제 API를 호출해 9건이 통과하고, 없으면 스킵된다(실패가 아니다). 벤더가 아직 그대로인지를 지킨다.

```bash
grep -rn "fnlttSinglIndx\|fnlttCmpnyIndx" src/main/java/ | grep -vE ':[0-9]+: *(\*|//|/\*)'
```
아무것도 반환하지 않아야 한다. 주석 줄을 제외하는 이유는 "왜 쓰지 않는가"를 설명하려면 그 이름을 적어야 하기 때문이다 — 항상 걸리는 검사는 곧 무시된다.

```bash
grep -rn "ConditionalOnProperty" src/main/java/com/stockscreener/pipeline/datasource/ | grep -vE ':[0-9]+: *(\*|//|/\*)'
```
아무것도 반환하지 않아야 한다 — 빈 문자열 함정 때문에 `@ConditionalOnApiKey`를 쓴다.
범위가 `kr/`이 아니라 `datasource/` 전체인 이유는 애노테이션이 `http/`에 있고 어댑터가 시장별
하위 패키지로 늘기 때문이다. `kr/`로 좁히면 **새 시장의 어댑터에서 같은 함정이 통과한다.**

## 배경

2026-08-06에 실제 키로 두 API를 호출해 스펙을 확정했다. 그 결과 세 가지가 드러났고, 전부 코드 구조를 바꿨다.

**첫째, 실패 표현이 정반대다.** 공공데이터포털은 미등록 키에 **HTTP 403**과 함께 최상위 키부터 다른 봉투를 준다. DART는 인증 실패에도 **HTTP 200**과 `status: "010"`을 준다. 한쪽만 보고 공통 처리를 만들면 다른 쪽이 조용히 통과한다.

**둘째, 그리고 가장 위험한 것 — 공공데이터포털에서 없는 종목·휴장일·잘못된 파라미터가 응답상 완전히 동일하다.** 셋 다 `resultCode "00"` + `totalCount 0` + HTTP 200이다. 즉 **날짜 형식 오타가 "그날 데이터 없음"으로 조용히 저장된다.** `resultCode` 검사로는 잡히지 않으므로 요청 전 검증이 유일한 방어다. 이것이 이 프로젝트에서 가장 발견하기 어려운 종류의 결함이다 — 아무 에러도 나지 않고 데이터에 구멍만 남는다.

**셋째, 초기 메모의 DART 엔드포인트가 틀렸다.** `fnlttCmpnyIndx.json`은 존재하지 않는 이름이고(단일회사는 `fnlttSinglIndx.json`), 그마저도 **계산된 비율**(`idx_val`)을 반환해 spec §7의 "모든 지표는 원자료에서 자체 계산"과 충돌한다. 게다가 2023년 3분기 이후만 제공해 3년 이력을 만들 수 없다. 올바른 것은 `fnlttSinglAcnt.json`이다.

부수적으로 확인한 것: 종목별 기간조회가 되어 초기 적재가 350콜이고(일자별 전종목만 됐다면 구조가 달랐다), KRX는 거래대금을 실제로 제공해 V1의 "합성 금지" 규칙을 지키면서 값을 채울 수 있다.

**넷째 — 페이징을 하지 않으면 조용히 잘린다 (2026-08-06 추가).** 어댑터가 `pageNo=1` 한 페이지만 읽고 `totalCount`를 보지 않았다. 6.5년을 요청하면 `totalCount=1618`인데 **1,000행만 반환되고 앞의 618일이 경고 없이 사라진다.** 2년(487행)이 안전했던 것은 우연히 상한 아래였기 때문이며, 다개년 적재로 넘어가는 순간 문제가 된다. 이것은 둘째 항목과 같은 계열의 결함이다 — **에러가 나지 않고 데이터에만 구멍이 남는다.** 잘린 구간이 오래된 쪽이라 최근 시세만 보면 정상으로 보이는 점이 더 나쁘다.

같은 조사에서 `numOfRows`가 **2,000까지 허용**되는 것도 확인했다(6.5년 1,618행이 1콜). 그러나 문서화된 상한이 아니므로 그것에 기대지 않고 페이징을 구현했다. `numOfRows`는 콜 수를 줄이는 최적화이고, 정확성의 근거는 `totalCount` 기반 루프다.

## 버린 대안

- **공통 `ResponseEnvelope` 추상화** — 두 소스의 봉투가 최상위 키부터 다르고 실패를 알리는 계층(HTTP vs 본문)도 달라, 공통화하면 분기가 추상화 안으로 옮겨갈 뿐 사라지지 않는다.
- **`RestClient`의 `defaultStatusHandler`로 4xx·5xx 처리** — DART는 실패에 200을 주므로 절반이 걸러지지 않고, 공공데이터포털은 403 본문을 읽어야 코드를 알 수 있다.
- **빈 결과를 `NOT_FOUND`로 매핑** — 휴장일이 종목 실패로 기록되어 매 주말 850건이 쌓인다. 휴장 판정은 `MarketCalendar`가 관측으로 한다.
- **`@ConditionalOnProperty(havingValue=...)`** — 키 값이 매번 다르므로 특정 값과 비교할 수 없다.
- **어댑터를 항상 등록하고 조회 시점에만 실패** — 테스트가 Fake 소스를 쓸 때 같은 시장에 두 소스가 걸려 기동에 실패한다. 그 충돌 자체는 레지스트리가 의도대로 동작하는 증거지만, 매 테스트가 걸리면 우회 코드가 늘어난다.
- **XML 응답 파싱** — `resultType=json`으로 JSON을 받으면 `jackson-dataformat-xml` 의존성이 필요 없다.

## 결과

- 쉬워지는 것: 두 소스의 실패를 각각 정확히 분류해 재시도·중단·기록이 올바르게 갈린다. 키 없이도 애플리케이션이 기동하고 fixture로 파싱을 검증할 수 있다.
- 어려워지는 것: 소스가 늘면 봉투 판별 클래스도 는다. 다만 그것이 벤더 지식을 어댑터에 가두는 대가이며(ADR-0006), 공통화했을 때 생기는 조용한 오분류보다 낫다.
- 되돌리려면: `datasource/kr`의 어댑터와 `docs/api-spec/`의 스펙 문서를 함께 고쳐야 한다.
