## IMPORTANT — 쓰면 안 되는 엔드포인트

`fnlttSinglIndx.json`(단일회사 주요 재무지표)을 **쓰지 않는다.** 배제 사유가 셋이고 각각 단독으로 충분하다.

1. **계산된 비율을 반환한다.** 응답이 `idx_val`(지표값)이며 원본 계정이 아니다. `idx_cl_code`로 수익성(M210000)·안정성(M220000)·성장성(M230000)·활동성(M240000)을 고른다. spec §7의 "모든 지표는 원자료를 수집한 뒤 자체 계산"과 정면으로 충돌하며, `RawFinancialReport`에 비율 필드가 없는 것이 이를 타입 수준에서 막고 있다.
2. **2023년 3분기 이후만 제공한다.** 3년치 재무 이력(spec §7)을 만들 수 없다.
3. 두 시장(한국·미국)의 계산식을 통일한다는 목적 자체가 무너진다.

> 참고: 초기 메모에 있던 `fnlttCmpnyIndx.json`은 존재하지 않는 이름이다. 단일회사는 `fnlttSinglIndx.json`이다. 어느 쪽이든 위 사유로 쓰지 않는다.

## 1. 단일회사 주요계정 — `fnlttSinglAcnt.json` (채택)

한 번의 호출로 재무상태표(BS)와 손익계산서(IS)의 주요 계정을 모두 받는다.

**요청**

| 이름 | 필수 | 설명 |
|---|---|---|
| `crtfc_key` | Y | 인증키(40자리) |
| `corp_code` | Y | DART 고유번호(8자리). 종목코드가 아니다 |
| `bsns_year` | Y | 사업연도(4자리, 2015~) |
| `reprt_code` | Y | 보고서 코드 |

`reprt_code`: **`11011`** 사업보고서(연간) / **`11012`** 반기 / **`11013`** 1분기 / **`11014`** 3분기

`fs_div` 파라미터는 **없다.** 응답에 CFS(연결)와 OFS(별도)가 모두 담겨 오므로 소비 측에서 고른다.

**응답 필드** (실측으로 확인한 21개)

```
rcept_no, reprt_code, bsns_year, corp_code, stock_code,
sj_div, sj_nm, account_nm, fs_div, fs_nm, ord, currency,
thstrm_nm, thstrm_dt, thstrm_amount, thstrm_add_amount,
frmtrm_nm, frmtrm_dt, frmtrm_amount, frmtrm_add_amount,
bfefrmtrm_nm, bfefrmtrm_dt, bfefrmtrm_amount
```

- `sj_div`: 이 엔드포인트는 **`BS`(재무상태표)와 `IS`(손익계산서) 두 값만** 낸다. CIS/CF/SCE는 전체 재무제표 API에만 있다.
- `fs_div`: `CFS`(연결) / `OFS`(별도). **CFS 우선, 없으면 OFS 폴백** — 연결재무제표가 없는 회사가 있다.
- `thstrm_amount`: 당기 금액. **분기 보고서에서는 해당 분기 단독 금액**
- `thstrm_add_amount`: 당기 **누적** 금액. Q4 유도의 핵심
- `currency`: 통화(`KRW`)

**실측 — 삼성전자(00126380) 2025 사업보고서, CFS 기준 15개 계정**

| `sj_div` | `account_nm` | 값(2025) |
|---|---|---|
| BS | 유동자산 / 비유동자산 / **자산총계** | 자산총계 566.9조 |
| BS | 유동부채 / 비유동부채 / **부채총계** | 부채총계 130.6조 |
| BS | 자본금 / 이익잉여금 / **자본총계** | 자본총계 436.3조 |
| IS | **매출액** | 333.6조 |
| IS | **영업이익** | 43.6조 |
| IS | 법인세차감전 순이익 | 49.5조 |
| IS | **당기순이익(손실)** | 45.2조 |
| IS | 총포괄손익 | 51.3조 |

### 계정명 매핑

실측 결과 **삼성전자·KB금융·카카오·NAVER 네 회사 모두** `매출액`·`영업이익`·`당기순이익(손실)`·`자산총계`·`부채총계`·`자본총계`로 **일관**됐다. 금융지주(KB금융)도 `매출액`으로 나왔다 — 주요계정 API가 계정명을 정규화하는 것으로 보인다.

그래도 **후보군 집합으로 매칭한다.** 일관성이 확인된 것은 4개사뿐이고, 350종목에는 업종이 훨씬 다양하다.

| 목표 | 후보군 |
|---|---|
| revenue | `매출액`, `수익(매출액)`, `영업수익` |
| operatingIncome | `영업이익`, `영업이익(손실)` |
| netIncome | `당기순이익(손실)`, `당기순이익` |
| totalAssets | `자산총계` |
| totalLiabilities | `부채총계` |
| totalEquity | `자본총계` |
| currentAssets | `유동자산` |
| currentLiabilities | `유동부채` |
| retainedEarnings | `이익잉여금`, `이익잉여금(결손금)` |

아래 셋은 **응답에 원래 들어 있던 것**이다(위 실측표의 BS 행). 총계만 뽑고 버리고 있었을 뿐이라
호출 수도 응답 크기도 늘지 않는다. Altman Z-Score의 운전자본 항과 누적 수익성 항이 여기서 나온다.

**금융업은 유동/비유동을 구분하지 않는 재무상태표를 낸다.** 그 종목에서 `유동자산`·`유동부채`가
비는 것이 정상이며 null로 둔다 — 0으로 대체하면 운전자본이 0인 회사가 되어 값이 그럴듯하게 틀린다.
Altman Z는 애초에 금융업에 적용할 수 없는 지표이므로, 계산되지 않는 것이 옳은 결과다.

MUST: 매핑 실패를 **집계해 로그로 남긴다.** 대량 발생은 후보군을 보강해야 한다는 신호이며, 조용히 null로 두면 그 종목의 지표가 사라진 이유를 알 수 없다.

### 주의 — 숫자 파싱

금액이 **콤마 포함 문자열**이다: `"333,605,938,000,000"`. 음수는 `-` 접두. 빈 문자열(`""`)은 **null로 둔다 — 0으로 대체 금지**(0은 "값이 0"이라는 다른 사실이다).

### 주의 — 중복 행

실측에서 `당기순이익(손실)`이 **두 번** 나왔다(지배기업 소유주지분 / 비지배지분으로 추정되나 `account_nm`만으로는 구분되지 않는다). `ord` 오름차순 첫 행을 취하고, 중복이 사라지거나 3개 이상이 되면 알 수 있도록 로그를 남긴다.

### Q4 유도

**4분기 보고서는 존재하지 않는다.** 사업보고서(11011)가 연간 누계다.

```
Q4(손익) = 사업보고서 금액 − 3분기보고서의 thstrm_add_amount(누적)
```

실측(삼성전자 2025): 매출액 FY 333.6조 − 3Q누적 239.8조 = Q4 93.8조

**MUST: 손익(IS)만 차감한다. 재무상태표(BS)는 시점 잔액이므로 차감하면 안 된다** — 차감하면 자산총계가 음수가 된다. `sj_div`로 분기 처리한다.

## 2. 고유번호 — `corpCode.xml`

종목코드 → `corp_code` 매핑의 **유일한 공식 경로**.

- 요청: `crtfc_key` 하나
- 응답: **ZIP 바이너리**. 내부에 `CORPCODE.xml` 한 개
- 필드: `corp_code`(8자리), `corp_name`, `corp_eng_name`, `stock_code`(6자리, **상장사만 채워짐**), `modify_date`

**실측**: 3.5MB ZIP, 전체 118,664법인 중 `stock_code`가 있는 **상장사 3,925건**. 시드 15종목 전부 매핑 성공.

주의: **content-type이 `application/x-msdownload`**로 온다(`application/zip`이 아니다). 타입으로 분기하면 실패한다.

## 3. 발행주식수 — `stockTotqySttus.json`

주요계정에 발행주식수가 없으므로 PER·PBR에 필요하면 별도 호출한다.

- 요청: `crtfc_key`, `corp_code`, `bsns_year`, `reprt_code`
- **필드 계약은 §11-H**다. 자주 쓰는 것만: `se`(구분), `istc_totqy`(발행주식의 총수), `tesstk_co`(자기주식수), `distb_stock_co`(유통주식수)
- `se`가 보통주/우선주/합계로 나뉘므로 **행 선택 로직이 필요**하다. 값에 콤마가 포함된다.
- **감소 내역 넷(`redc`·`profit_incnr`·`rdmstk_repy`·`etc`)이 자사주 소각을 분해해 준다** — 발행주식수 배수로 분할 비율을 유도할 때 조용히 틀리는 자리다(§11-H·§10-B).

> v1 범위 판단: 초기 적재에서는 호출하지 않는다. 종목당 12콜이 이미 필요하고, 발행주식수는 `price_daily`가 아니라 `financial_statement.shares_outstanding`에 들어가므로 Phase 3에서 PER·PBR을 실제로 계산할 때 붙여도 늦지 않다.

## 4. status 코드 — HTTP 200과 함께 온다

**IMPORTANT — DART는 인증 실패도 HTTP 200으로 응답한다.** data.go.kr이 403을 주는 것과 정반대다. HTTP 상태코드만 보면 잘못된 키로 조회한 결과를 정상으로 오인한다. **`status` 필드 파싱이 필수다.**

| status | 의미 | → `Kind` |
|---|---|---|
| `000` | 정상 | — |
| `010` | 등록되지 않은 인증키 | `AUTH` |
| `011` | 사용할 수 없는 키(일시 중지) | `AUTH` |
| `012` | 접근할 수 없는 IP | `AUTH` |
| `013` | **조회된 데이터 없음** | `NOT_FOUND` |
| `014` | 파일이 존재하지 않음 | `NOT_FOUND` |
| `020` | 요청 제한 초과 | `RATE_LIMITED` |
| `021` | 조회 가능한 회사 개수 초과(최대 100) | `MALFORMED` |
| `100` | 필드의 부적절한 값 | `MALFORMED` |
| `101` | 부적절한 접근 | `AUTH` |
| `800` | 시스템 점검 중 | `TRANSIENT` |
| `900` | 정의되지 않은 오류 | `TRANSIENT` |
| `901` | 개인정보 보유기간 만료 키 | `AUTH` |

**실측 확인**: 없는 연도 조회 → HTTP 200 + `status 013`. 잘못된 키 → HTTP 200 + `status 010`.

## 5. 쿼터

- **일 20,000건** — 2차 출처 다수. 공식 문서에 명시를 찾지 못했다(status 020 설명에 "일반적으로는 20,000건 이상의 요청에 대하여"라고 언급됨).
- **분당 제한은 공식 문서에 없다.** 미검증이므로 보수적으로 간격을 둔다.

초기 적재 비용: 종목당 4콜(11011·11012·11013·11014) × 3년 = 12콜. 350종목이면 **약 4,200콜**로 일 한도 안에 넉넉히 들어간다.

## 6. 정정공시 탐지

별도 플래그 필드가 **없다.**

`rcept_no`(14자리) = 접수일자(8) + 일련번호(6). 같은 `(corp_code, bsns_year, reprt_code)`에 대해 **`rcept_no`가 큰 쪽이 최신 정정본**이다.

- `publishedAt`은 `rcept_no` 앞 8자리에서 유도한다.
- 재무 API는 최신 보고서 기준으로 응답하므로, `FinancialWriter`의 기존 로직(`publishedAt`이 더 늦으면 정정본으로 보고 `revision_no + 1`로 append)이 그대로 성립한다.

## 7. 전체 재무제표 — `fnlttSinglAcntAll.json` (2026-08-10 실측)

주요계정이 주지 않는 것들(영업활동현금흐름·현금성자산·차입금·이자비용)을 얻으려고 실측했다.
표본은 삼성전자·NAVER·카카오·KB금융의 **2025 사업보고서(`reprt_code=11011`, `fs_div=CFS`)**다.

**요청**: 주요계정과 같되 **`fs_div`가 추가로 필수**다(`CFS` | `OFS`). 주요계정과 달리
**응답 행에 `fs_div` 필드가 없다** — 어느 쪽을 받았는지는 요청이 정하므로, CFS가 비면 OFS로
다시 부르는 폴백이 필요하고 그때만 호출이 2배가 된다.

**필드 계약은 §11-E다.** 특히 **`thstrm_amount`가 분/반기 (포괄)손익계산서에서는 [3개월]
금액**이라는 것 — TTM을 4분기 합으로 만들기 전에 그 절을 읽는다.

**응답 규모**: 229~349행(주요계정은 7~15행). `sj_div`가 다섯이다.

| 회사 | 총 행 | BS | CF | CIS | IS | SCE |
|---|---|---|---|---|---|---|
| 삼성전자 | 229 | 52 | 42 | 13 | 17 | 105 |
| NAVER | 239 | 51 | 53 | 30 | — | 105 |
| 카카오 | 233 | 65 | 41 | 36 | — | 91 |
| KB금융 | 349 | 42 | 69 | 49 | — | 189 |

**IMPORTANT — 손익이 `IS`에만 있다고 가정하면 안 된다.** 삼성전자만 `IS`가 있고 나머지 셋은
`CIS`(포괄손익계산서)뿐이다. 주요계정 API가 `BS`/`IS` 둘로 정규화해 주던 것을 여기서는
소비 측이 감당해야 한다.

### `account_id`(XBRL 표준계정ID)가 계정명보다 안정적이다

전 행에 `account_id`가 채워진다. 표준코드를 쓰지 않는 행은 `-표준계정코드 미사용-`이라는
**문자열 파수꾼**으로 오며 5~31행(2~9%)이다 — null이 아니므로 그 값으로 판별해야 한다.

이름이 회사마다 갈리는 것을 실측으로 확인했다:

| 항목 | 회사별 `account_nm` | 공통 `account_id` |
|---|---|---|
| 영업활동현금흐름 | `영업활동현금흐름` / `영업활동으로 인한 현금흐름` / `영업활동으로부터의 현금흐름` | `ifrs-full_CashFlowsFromUsedInOperatingActivities` |

계정명 후보군을 계속 늘리는 방식은 업종이 늘수록 반드시 새어 나간다. 이 엔드포인트를 쓴다면
매칭은 `account_id`를 우선하고 계정명은 폴백으로만 둔다.

### 얻을 수 있는 것과 없는 것 — **전환을 결정하기 전에 이 표를 본다**

| 목표 | 결과 | 근거 |
|---|---|---|
| **영업활동현금흐름** | **4/4 확보** | `ifrs-full_CashFlowsFromUsedInOperatingActivities` |
| 현금및현금성자산 | 4/4 확보 | `ifrs-full_CashAndCashEquivalents`. **단 `sj_div='BS'`로 좁혀야 한다** — KB금융은 CF의 `기초 현금 및 현금성자산`이 먼저 잡혔다 |
| 단기금융상품 | 3/4 | `ifrs-full_ShorttermDeposits…`. KB금융에 없다 |
| 총차입금 | **합성해야 한다** | 단기차입금·유동성장기부채·사채·차입부채가 회사마다 다른 조합으로 온다. 무엇을 더할지가 회사마다 다르므로 "총차입금"은 우리가 **만드는** 값이 된다 |
| **이자비용** | **1/4 (금융업만)** | `ifrs-full_InterestExpense`가 KB금융에만 있다. 비금융 3사는 `금융비용`(`FinanceCosts`)뿐이고 **그것은 이자비용이 아니다** — 외환손실·파생상품손실을 포함한다 |
| **감가상각비** | **1/4 (금융업만)** | `AdjustmentsForDepreciationAndAmortisation`이 KB금융에만 있다. 비금융 3사의 현금흐름표에 표준코드로 오지 않는다 |

**따라서 이 엔드포인트로 전환해도 열리는 것은 영업활동현금흐름 하나다.**
이자보상배율(EBIT ÷ 이자비용)과 순부채/EBITDA(EBITDA에 감가상각비가 필요)는 **여전히 계산할 수
없다.** 금융비용을 이자비용으로 대신 쓰는 것은 다른 값을 같은 이름으로 부르는 것이라 하지 않는다.

**쿼터**: 종목·연도당 4콜로 주요계정과 같다(`reprt_code` 넷). `fs_div` 폴백이 필요한 종목만 8콜이다.
비용은 호출 수가 아니라 **응답 크기와 계정 매핑의 복잡도**에 있다.

## 8. 주요계정의 계정 집합은 회사마다 다르다 (2026-08-10 실측)

**§1의 "계정명 일관성" 미검증 항목이 실제로 새어 나갔다.** 결손 보정(ADR-0040) 뒤 편입 350종목
중 **이익잉여금만 세 종목에서 비었다** — 오리온·오리온홀딩스·에스티큐브. 유동자산·유동부채는
왔으므로 금융업 사유가 아니다. 탐침은 `DartAccountNameProbeLiveTest`이고 회사당 1콜이다.

| 회사 | CFS(연결) | OFS(별도) |
|---|---|---|
| 삼성전자(대조군) | 유동자산·유동부채·**이익잉여금**·자본금·총계 3종 | 같음 |
| 에스티큐브 | 이익잉여금·자본금 **없음** | **있음** |
| 오리온 | 이익잉여금 **없음** | **없음** |
| 오리온홀딩스 | 이익잉여금 **없음** | **없음** |

**IMPORTANT — 계정명 후보군을 늘려도 열리지 않는다.** 이름이 다른 것이 아니라 **행 자체가 없다.**
오진하기 쉬운 자리이므로 여기 적는다 — 다음 세션의 첫 시도가 `RETAINED_EARNINGS` 후보군 보강이
될 것이고, 그것은 아무것도 바꾸지 못한다.

**CFS/OFS 폴백으로도 열리지 않는다.** 어댑터는 "CFS가 비면 OFS"를 <b>보고서 단위</b>로 고른다.
에스티큐브처럼 CFS는 있고 그 안에 계정만 없는 경우, 계정 단위로 폴백하면 열리기는 한다 —
**그러나 연결 총자산과 별도 이익잉여금을 한 행에 섞는 것이라 뜻이 달라진다.** Altman Z가
그럴듯하게 틀린 값을 내고 화면에는 흔적이 없다. ADR-0039의 "뜻이 다른 값을 같은 이름으로
부르지 않는다"에 걸린다.

**남는 길은 전체 재무제표(`fnlttSinglAcntAll`)다.** §7의 표본에서 `account_id`가 전 행에 채워졌고
자본변동표(SCE)가 91~189행으로 함께 온다. 즉 **ADR-0039의 P10(전체 재무제표 전환)이 H-05뿐
아니라 이 결손도 연다** — 전환의 근거가 하나 늘었다.

영향은 작다(3종목). 다만 그중 오리온이 실제로 스크리닝 결과에서 빠졌으므로 **"영향이 없다"가
아니라 "지금은 3종목이다"** 로 읽는다.

## 9. 엔드포인트 카탈로그 — 무엇이 있고 무엇이 없는가 (2026-08-10)

이 절은 **"무엇이 있고 무엇이 없는가"의 정본**이고, "어떻게 부르는가"는 §10이, "어떤 필드가
오는가"는 §11이 답한다.

> **근거는 사용자가 DART 개발가이드 목록에서 옮겨 온 카탈로그 101줄이다.** 그 파일과 개발가이드
> 13종 원문은 **저장소에서 지웠고 git 이력에 있다**(§11 머리에 복구 명령). 아래 "액면분할 전용
> API가 없다"와 "다중회사 주요계정 복수조회 가능"의 근거가 그 101줄이며, **개발가이드는 이미
> 있는 API의 사용법이라 없는 API를 증명하지 못한다** — 두 자료는 답하는 질문이 다르다.
>
> **MUST NOT: 목록에 없다는 것을 얻을 수 없다로 읽지 않는다.** 이 절이 실제로 그렇게 한 번
> 틀렸다(액면분할 → §10-B가 뒤집었다).

| 우리가 막혀 있던 것 | 대응 API | 판정 |
|---|---|---|
| 업종 상대 비교(H-02·S-01·S-02) · Altman Z 금융업 제외 | 공시정보 **기업개황** | **있다.** 업종 코드가 실제로 오는지·분류 체계는 미확인 |
| 피인수 진행 제외(U-06) | 주요사항보고서 **회사합병 결정 · 주식교환·이전 결정 · 영업양수/양도 결정**, 증권신고서 **합병 · 주식의포괄적교환·이전** | **있다. 넉넉하다** |
| 5년 누적 영업현금흐름(H-05) 등 | 재무정보 **단일회사 전체 재무제표** | **있다**(§7에서 이미 실측) |
| 모듈 B 공시(E)·소유구조(G) 계열 | 정기보고서 주요정보 **30종**, 주요사항보고서 **36종**, 지분공시 **2종**(임원·주요주주 소유보고 / 대량보유 상황보고) | **있다.** 40개 플래그 중 상당수가 대응된다 |
| **액면분할 이력 → 수정주가(P9)** | **전용 API가 없다** | **아래 참조** |

### IMPORTANT — 카탈로그의 "분할"은 **회사분할**이지 **액면분할**이 아니다

목록에 분할이 셋 있다 — 주요사항보고서의 **「회사분할 결정」·「회사분할합병 결정」**, 증권신고서의
**「분할」**. **셋 다 우리가 찾는 것이 아니다.** 헷갈리기 쉬운 자리라 여기 적는다.

| | 무엇인가 | 주가에 하는 일 |
|---|---|---|
| **회사분할**(카탈로그에 있다) | 회사를 둘로 쪼갠다(물적·인적분할). **기업 구조**가 바뀐다 | 인적분할이면 자산이 빠져나가 **기준가가 조정된다** |
| **액면분할·주식분할**(카탈로그에 없다) | 1주를 N주로 쪼갠다. **주식 수**만 바뀐다 | 주가가 **1/N**이 된다 |

우리가 `adj_factor`에 필요한 것은 아래쪽이고, **주요사항보고서 36종에 유상·무상·유무상증자와
감자 결정은 있는데 그것만 없다.** (액면분할이 자본시장법상 주요사항보고 대상이 아니라
거래소 수시공시 대상이라 목록에 없는 것으로 보이나, 그 법적 근거는 **확인하지 않았다** —
관측은 "이 목록에 없다"까지다.)

**다만 회사분할도 무시할 것이 아니다.** 인적분할은 기준가 조정 사건이라 `adj_factor`가
필요하고, 그런데 **`CorporateAction.Type`에는 `SPLIT`/`REVERSE_SPLIT`밖에 없어 표현할 자리가
없다.** P9에서 액면분할과 함께 봐야 하고, 타입을 늘릴지가 그 phase의 결정 하나다.

즉 `adj_factor`를 만들 원자료를 **전용 엔드포인트로 받을 수 없다.** 남는 길은 셋이었고,
**2026-08-10 실측으로 2번이 열렸다**(§10-B).

1. **공시검색**으로 보고서 존재만 찾고 **원문을 파싱한다** — 가장 비싸다. **쓰지 않는다.**
2. **정기보고서 주요정보의 「증자(감자) 현황」** — **열렸다.** `isu_dcrs_stle`에
   **`주식분할`**이 오고 액면가와 일자가 함께 온다. 상세와 함정은 **§10-B**에 있다.
3. **「주식의 총수 현황」 + 시세 불연속** — 분할을 *탐지*할 수는 있으나 **추정이지 이력이 아니다.**
   §10-B가 그것을 실측으로 못박았다 — 삼성전자 2018은 발행주식수가 **50배가 아니다**(자사주
   소각이 겹쳤다). 배수로 비율을 유도하면 조용히 틀린다. **대조군으로만 쓴다.**

**전용 엔드포인트가 없다는 것이 P9을 막지 않는다.** 단 **회사분할**(인적분할)은 여전히
열려 있지 않다 — 「회사분할 결정」 개발가이드를 아직 받지 않았고, `CorporateAction.Type`에
표현할 자리도 없다.

### 부수 발견 — 호출 수를 줄일 수 있다

재무정보에 **「다중회사 주요계정」(복수 조회 가능)**이 있다. 지금 `financial-refill`은
종목당 1콜이라 350종목 × 4개년 × 4보고서 = 5,600콜인데, 복수 조회로 묶으면 그 수가 크게 준다.
**상한 100을 실측으로 확정했다 — §10-C.**

**「XBRL택사노미재무제표양식」**도 있다 — 표준계정과목 체계를 준다.

**MUST NOT: 이것을 회사별 계정 진단에 쓰려 하지 않는다.** 요청 인자가 `crtfc_key` + `sj_div`
둘뿐이라 **`corp_code`를 받지 않는다** — 회사별 재무제표가 아니라 **표준계정 사전**이므로
특정 회사가 무엇을 냈는지 원리적으로 알 수 없다(§10-C). 이름이 "재무제표양식"이라 §8의
이익잉여금 결손을 가르는 데 쓸 수 있어 보이는 것이 함정이다. 쓸 데는 따로 있다 —
P10의 계정 매칭 후보군 생성.

## 10. 확장 엔드포인트 실측 (2026-08-10)

개발가이드 13종을 받아 그중 넷을 탐침으로 실제 호출했다. **요청·응답 필드 표는 §11**에 있다.

**§9가 "있다/없다"의 정본이라면 여기는 "어떻게 부르고 무엇이 오는가"의 정본이다.**
스펙에 필드가 있는 것과 그 값이 실제로 오는 것은 다르며, 아래 넷 중 셋에서 실제로 갈렸다.

**아래는 탐침 표준출력의 사본이다.** 원본은 어디에도 남지 않으므로 값을 의심하면 다시
돌린다 — 넷이 합계 약 45콜이고 일 20,000 한도에 무시할 수준이다.

```bash
./gradlew liveTest --tests "*DartCompanyProfileProbe*"      # 10-A  6콜
./gradlew liveTest --tests "*DartShareChangeProbe*"         # 10-B 20콜
./gradlew liveTest --tests "*DartBulkAndTaxonomyProbe*"     # 10-C 12콜
./gradlew liveTest --tests "*DartCorporateEventProbe*"      # 10-D  7콜
```

**MUST: 표본을 바꾸면 이 절도 함께 고친다.** 탐침의 표본 종목·연도가 아래 표의 근거이며,
어긋나면 이 문서가 "실측"이라 주장하는 값이 아무것도 재지 않은 것이 된다.

### 10-A. 기업개황 — `company.json` → **P8이 열린다**

- 요청: `crtfc_key`, `corp_code`. **종목당 1콜**, 유니버스 350종목이면 350콜.
- **IMPORTANT — 응답이 `list`가 아니라 평면 객체다.** 다른 엔드포인트와 형태가 다르므로
  `DartResponse.requireList`를 그대로 쓰면 빈 결과가 된다.

| 회사 | `induty_code` | `est_dt` | `acc_mt` |
|---|---|---|---|
| 삼성전자 | **264** (3자리) | 19690113 | 12 |
| 오리온 | **108** (3자리) | 20170601 | 12 |
| NAVER · 카카오 | **63120** (5자리) | 19990602 · 19950216 | 12 |
| KB금융 | **64992** (5자리) | 20080929 | 12 |
| 삼성화재 | **65121** (5자리) | 19520126 | 12 |

**업종 체계는 한국표준산업분류(KSIC)다.** 264=통신·방송장비 제조, 108=기타 식품 제조,
63120=포털·인터넷정보매개, 64992=기타 금융, 65121=손해보험. 금융·보험이 **64~66 중분류**로
모인다 — ADR-0039 §부작용의 **Altman Z 금융업 명시 제외**가 이것으로 성립한다.

- **MUST: 금융업 판정은 앞 2자리(중분류)로 한다.** **자릿수가 회사마다 3자리와 5자리로
  섞여 온다**(6개사 중 2개가 3자리). 전체 문자열 비교나 5자리 전제는 3자리 종목을 통째로
  놓치고, 그 결과는 "그 종목만 조용히 안 걸린다"로 나타난다.
- **`est_dt`는 설립일이다. 상장일이 아니다.** 삼성전자 19690113은 설립 1969년이고 상장은
  1975년이다. 응답 전체를 훑어도 상장일 필드가 없다 — **U-05(상장 3년)는 이 엔드포인트로
  열리지 않으며**, 공공데이터포털 쪽을 봐야 한다.
- **`acc_mt`(결산월)는 뜻밖의 수확이다.** `DartFinancialAdapter.periodRange()`가
  *"12월 결산을 전제한 근사값이며, 정확한 기간은 소스가 주지 않는다"*고 주석에 적어 둔 그
  소스가 이것이다. **표본 6개사가 전부 12월이라 비12월 결산의 표기는 미확인이다.**

### 10-B. 증자(감자) 현황 — `irdsSttus.json` → **P9가 열린다**

**액면분할이 잡힌다. 형태 값은 `주식분할`이다**(「액면분할」이 아니다 — 낱말을 틀리면 0건이
되고 그것이 "분할이 없다"로 읽힌다).

| 표본 | `isu_dcrs_de` | 실제 매매개시일 | `isu_dcrs_stle` | 액면가 |
|---|---|---|---|---|
| NAVER 2018 | **2018.10.10** | 2018-10-12 | `주식분할` | **100**(분할 후) |
| 카카오 2021 | **2021.04.14** | 2021-04-15 | `주식분할` | **100**(분할 후) |
| 삼성전자 2018 | — | 2018-05-04 | **행이 없다** | — |

- **액면가는 분할 *후* 값이다.** 500→100이면 비율 5, 5000→100이면 50이다.
  `CorporateAction.ratio`("1주가 몇 주가 되었는가")를 직접 유도할 수 있고, javadoc이 경고하는
  방향 뒤집힘은 일어나지 않는다.
- **IMPORTANT — `isu_dcrs_de`는 매매개시일이 아니다.** 표본 둘 다 **하루~이틀 이르다**(신주
  효력발생일이며, 액면분할에는 변경상장까지 거래정지가 낀다). `CorporateAction.effectiveDate`는
  *"변경된 가격으로 거래가 시작되는 날"*이므로 **그대로 쓰면 안 되고, `price_daily`에서
  `isu_dcrs_de` 이후 첫 거래일로 보정한다.** 어긋나면 그 하루 봉만 잘못 조정되고 차트를
  직접 보기 전까지 드러나지 않는다.
- **IMPORTANT — 회사가 이 표를 비워서 낼 수 있다.** 삼성전자는 2018 사업보고서·분기 셋
  **전부** `status 000` + **모든 필드가 `-`인 1행**이다. `013`이 아니므로 오류로도 안 보이고,
  행 수만 세면 "1건 있음"으로 읽힌다. §8의 이익잉여금 결손과 같은 병이며 **대조군이 필요한
  이유가 이것이다.**
- **누적 범위가 약 5년이다.** 카카오 2021 사업보고서 하나가 **2017~2021의 128행**을 준다.
  즉 **최근 사업보고서 1콜(종목당)로 5년 이력이 끝난다 — 350콜.** 우리 시세가 2년치이므로
  넉넉하다. (삼성전자 2025가 `-` 2행인 것은 최근 5년에 변동이 없어서이며 위 결손과 다른 사실이다.)
- 그 외 관측된 `isu_dcrs_stle`: `유상증자(제3자배정)` · `전환권행사` · `주식매수선택권행사` · `-`.

**대조군 — 「주식의 총수 현황」(`stockTotqySttus.json`)은 비율 산출에 쓸 수 없다.**

| 삼성전자 | 보통주 발행총수 | 자기주식 |
|---|---|---|
| 2017 | 129,098,494 | 9,410,125 |
| 2018 | 5,969,782,550 | **`-`** |

50배면 6,454,924,700이어야 하는데 **아니다** — 2018년 자사주 소각이 겹쳤다. **주식 수 배수로
분할 비율을 유도하면 조용히 틀린다.** §9의 "추정이지 이력이 아니다"가 숫자로 확인된 자리다.
`se`는 `보통주`/`우선주`/`합계`/`비고` 넷으로 오고, `비고` 행은 전 필드가 `-`다.

### 10-C. 다중회사 주요계정 · XBRL택사노미 → **P10의 비용이 87분의 1이 된다**

**`fnlttMultiAcnt.json` — 복수조회가 된다. 상한은 100이다.**

- `corp_code`에 **콤마 구분**으로 넣는다. 2건·12건 모두 `status 000`, 12건이 384행(회사당 32행).
- **101건은 `status 021`**(조회 가능한 회사 개수 초과). §4의 매핑이 실측으로 확인됐다.
- **DART는 중복을 접지 않고 항목 수로 센다** — 101건 요청은 12개를 순환 반복해 만든 것인데도
  `021`이 나왔다. 상한 판정이 유효하다는 뜻이다.
- **응답에 `corp_code`가 실제로는 온다.** 개발가이드 응답 표에는 `stock_code`만 있는데
  둘 다 채워진다. 다만 **표에 없는 필드에 의존하지 않는다** — 매핑은 `stock_code`로 한다.
- **비용**: 350종목 ÷ 100 = 4묶음 × 4개년 × 4보고서 = **64콜**. 지금의 5,600콜이 그만큼 준다.

**`xbrlTaxonomy.json` — 회사별 진단에는 쓸 수 없다.**

- 요청 인자가 `crtfc_key` + `sj_div` 둘뿐. **`corp_code`가 없다.**
- `sj_div=BS1`에 519행. `ifrs_RetainedEarnings`=이익잉여금(결손금),
  `dart_RetainedEarningsBeforeAppropriations…`=미처분이익잉여금이 **표준계정에 존재한다.**
- **그러므로 §8의 결손은 "이름을 모르는 것"이 아니라 "그 회사가 그 계정을 안 낸 것"이 맞고,
  이 엔드포인트는 그것을 가려 주지 못한다.** 표준계정 사전이기 때문이다.
- 쓸 데: `account_id` ↔ `label_kor` 사전을 만들어 **P10의 계정 매칭 후보군을 손으로 늘리지
  않고 생성**하는 것. `sj_div` 하나당 1콜이다.

### 10-D. 합병·주식교환 · 감사의견 → **U-06은 절반만 열린다**

`cmpMgDecsn.json`(합병) · `stkExtrDecsn.json`(주식교환·이전). `corp_code`와 `bgn_de`/`end_de`가
전부 필수라 **종목별로 돌아야 한다 — API당 350콜, 둘이면 700콜.**

셀트리온(2023 셀트리온헬스케어 흡수합병) 관측:

- **`bddd`(이사회결의일)=`2023년 08월 17일` · `mgsc_mgdt`(합병기일)=`2023년 12월 28일`** —
  둘 다 채워진다. **U-06이 겨냥하는 "진행 중" 구간을 정의할 수 있다.**
- **날짜가 `YYYY년 MM월 DD일` 한국어 문자열이다.** 다른 엔드포인트의 `YYYYMMDD`·`YYYY-MM-DD`와
  또 다르다. 파서를 공유하면 깨진다.
- **IMPORTANT — `mg_stn`(합병형태)이 `해당사항없음`이라 방향을 가를 수 없다.** 존속/소멸은
  `mg_mth`(합병방법)에 **자유 텍스트**로만 있다(*"(주)셀트리온이 (주)셀트리온헬스케어를
  흡수합병 / 존속회사(합병법인) : … / 소멸회사(피합병법인) : …"*). 즉 이 API로 **"합병에
  관여했다"까지는 구조화되어 오고 "피인수인가"는 파싱이 필요하다.**
- `mgsc_trspprpd_bgd`/`_edd`(거래정지 예정기간)는 **`-`로 비어 왔다.**
- 대조군 삼성전자는 양쪽 다 `status 013`이다. **정상 응답과 데이터 없음이 제대로 갈린다.**

**감사의견 — `accnutAdtorNmNdAdtOpinion.json`** (부수 발견, 채택 미정)

- `adt_opinion` = **`적정의견`**(`적정`이 아니다). 1콜에 당기·전기·전전기 **3개년**이 온다.
- **`bsns_year`가 연도가 아니다.** `제57기 \n(당기)`처럼 **기수 + 줄바꿈 + 구분**이다.
  개발가이드는 "사업연도(당기, 전기, 전전기)"라고만 적었다. 연도로 파싱하면 실패한다.
- **행이 정확히 2배로 온다**(3개년인데 6행). 연결·별도로 추정되나 **필드로 구분되지 않는다** —
  §1의 `당기순이익(손실)` 중복 행과 같은 병이다.
- **표본 둘 다 `적정의견`이라 비적정의 표기는 미확인이다.** 그것을 보기 전에는 판정 로직을
  만들지 않는다.

### 이번에 탐침하지 않은 것

### 표본으로는 원리적으로 못 재는 것 — **착수 판단에 필요한 셋**

위 목록과 성격이 다르다. 아래 셋은 **"더 정확히 재면 좋은 값"이 아니라 phase가 성립하는지를
정하는 값**이고, 표본 몇 개사로는 답이 나오지 않는다. **각 phase의 첫 단계가 이것을 재는
것이어야 한다** — 나중에 재면 이미 구조를 짠 뒤라 결과에 맞춰 기준이 기운다.

| 무엇 | 왜 phase가 걸려 있는가 | 비용 |
|---|---|---|
| **업종당 종목 수 분포**(P8) | ADR-0036을 업종으로 다시 여는 것이 P8인데, **업종당 2~3종목이면 백분위가 뜻을 잃는다.** 게다가 `induty_code`가 3자리·5자리로 섞여 오므로 **어느 수준(중분류 2자리 / 소분류 3자리)으로 묶을지**가 첫 결정이고, 그 결정에 필요한 것이 바로 이 분포다. **§10-A의 "P8이 열린다"는 여기까지 재고 나서야 참이 된다** | 350콜 |
| **최근 2년 유니버스 내 분할 건수**(P9) | P9의 **실익 규모**다. 우리 시세는 2년치이므로 그 안에 분할이 0건이면 P9는 "미래 대비"이고 우선순위가 내려간다. 함께 **「증자(감자) 현황」을 비워 내는 회사 비율**도 나온다 — 삼성전자 하나를 봤을 뿐이고, **그 종목들은 분할이 있어도 안 잡힌다** | 350콜 |
