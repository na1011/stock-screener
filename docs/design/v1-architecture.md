# v1 설계 방향

이 문서의 성격과 한계는 [`README.md`](./README.md)를 먼저 읽는다. 요약하면 — **구현 명세가 아니다.** 검증된 사실과 spec 유도 방향만 고정하고, 설계 판단은 실행 시점 에이전트가 내린다.

---

## 1. 검증된 외부 사실 (판단 여지 없음)

의존성 추가 시점에 이것을 모르면 시간을 잃는다. Maven Central 메타데이터와 바이트코드 역어셈블로 확인했다 (2026-08 기준).

### QueryDSL — mainline은 이 스택에서 런타임에 깨진다

IMPORTANT — mainline `com.querydsl` 최신은 5.1.0(2024-01, 이후 릴리스 없음)이고, `AbstractHibernateQuery`가 `org.hibernate.query.Query.setFlushMode(org.hibernate.FlushMode)`를 호출한다. Hibernate 7.4(Spring Boot 4.1 baseline)에서 이 오버로드가 제거되어 `NoSuchMethodError`가 난다.

**컴파일은 통과하고 런타임에 터진다.** Boot 4.1의 의존성 관리가 아직 `querydsl.version=5.1.0`을 고정하고 있어, 별생각 없이 쓰면 이 함정에 빠진다.

→ OpenFeign 포크 `io.github.openfeign.querydsl` 7.5(2026-07-21)를 쓴다. 이 포크의 POM은 `springboot.version=4.1.0` / `hibernate.version=7.4.5.Final`을 명시해 이 스택을 정면으로 겨냥한다.

IMPORTANT — 7.x에서 jakarta classifier 규칙이 **역전**되었다. `querydsl-jpa`는 classifier를 뗐고(`:jakarta`를 붙이면 404), `querydsl-apt`는 여전히 `:jakarta`가 필요하다. Boot 3 예제를 그대로 복사하면 실패한다.

### 기타 확인된 함정

- `flyway-core` 12.4.0은 PostgreSQL 지원을 번들하지 않는다 → `flyway-database-postgresql` 별도 필요.
- Sentry는 `sentry-spring-boot-starter-jakarta`가 **아니다** — 그건 Boot 3용으로 `spring-boot-starter 3.5.0`에 컴파일되어 있다. Boot 4는 `io.sentry:sentry-spring-boot-4-starter`.
- Boot 4.1에서 `spring-boot-starter-web`은 `-webmvc`로 deprecated. 현재 `build.gradle`은 이미 올바른 이름을 쓰고 있다.
- JPA·Security·OAuth2 client·Validation·Actuator·Mail 스타터는 이름 변경 없음.
- Spring Batch 6.0.4는 Boot 4.1과 호환된다(Framework 7.0.8 baseline 일치). 도입 여부·시점은 판단 사항.

### 로컬 환경 (실측)

- 시스템 JDK 17 — toolchain은 21 요구. Gradle 자동 프로비저닝 또는 JDK 21 설치 필요.
- **Docker 없음.** PostgreSQL 16 로컬 설치됨 → 통합 테스트는 Testcontainers 대신 로컬 인스턴스나 다른 수단을 전제해야 한다.
- Node 24 있음.

## 2. spec에서 유도된 방향 (재논의 대상 아님)

spec과 `.claude/rules/`가 이미 요구하는 것이다. 구현 방식은 자유지만 방향 자체는 협상 대상이 아니다.

- **지표 저장은 스키마 변경 없이 새 지표를 추가할 수 있어야 한다** (spec §7, `backend.md`). 설계 세션에서 EAV 방식(`stock_id, trade_date, indicator_code, value` 행 단위)을 유력하게 봤으나, 이 요구를 만족하는 다른 구조를 택해도 된다.
- **프리셋 전략과 커스텀 필터는 하나의 조건 모델을 공유해야 한다** (spec §3, `backend.md`). 가중치 점수화와 충족/불충족 판정은 같은 조건 위의 두 판정 방식이다. 두 체계를 따로 만들면 지표 하나 추가에 양쪽을 고쳐야 한다.
- **지금의 평면 AND 목록이 향후 OR 트리의 최상위 계층으로 흡수될 수 있어야 한다** (spec §10, `backend.md`). v1에서 트리를 구현하지는 않는다.
- **모든 지표는 원자료에서 자체 계산한다** (spec §7, `data-pipeline.md`). 외부 API 계산값에 의존하지 않는다.
- **개발자가 새 지표를 쉽게 추가할 수 있어야 한다** (spec §3). 사용자 수식 정의는 범위 밖(spec §10).
- **초기 적재와 일일 갱신은 분리된 작업이다** (spec §7, `data-pipeline.md`).
- **배치 실패 격리 단위는 종목이고, 실패 단위를 나중에 식별할 수 있어야 한다** (`data-pipeline.md`). 관리자의 부분 재실행이 여기 의존한다.
- **인터랙션 로깅은 기능마다 손으로 넣지 않는다** (spec §8, `backend.md`). 선언적 표시 + 공통 계층 수집.
- **관리자 기능은 별도 앱으로 분리하지 않는다** (spec §4, `backend.md`). 같은 앱 안에서 권한으로 분리.

## 3. 설계 시 고려할 사항 (참고 — 결론 강제 아님)

설계 세션에서 검토한 논점들이다. **결론이 아니라 인과관계를 남긴다.** 다르게 판단해도 되며, 그 경우 ADR에 근거를 남긴다.

**조건 → 쿼리 번역.** 조건 하나를 상관 서브쿼리(EXISTS)로 번역하는 방식과 JOIN으로 번역하는 방식을 비교했다. AND만 있는 v1에서는 동등하지만, OR 그룹은 `(EXISTS(..) OR EXISTS(..))`로 자연스럽게 확장되는 반면 JOIN은 OUTER JOIN + null 검사로 변형되어야 한다. 이 선택이 §2의 "트리로 흡수 가능해야 한다"에 직접 걸린다. 행 증식(DISTINCT 필요 여부)도 함께 볼 것.

**번역기가 지표를 알면 안 된다.** 번역기에 `switch (indicatorCode)`가 생기는 순간 지표 추가마다 번역기를 고쳐야 하고, 이는 `backend.md`가 금지한 하드코딩 분기다. 분기는 연산자(닫힌 소형 집합)에 대해서만 하고 지표 코드는 데이터로 흘려보내는 형태가 이 문제를 구조적으로 없앤다.

**점수 계산 위치.** SQL이냐 Java냐는 성능이 아니라 **정렬·페이징 정합성** 문제로 접근하는 것이 맞다. 프리셋(SCORING)은 유니버스 전체에 순위를 매기므로 좁히는 WHERE가 없고, 5개 중 4개만 만족한 종목도 결과에 나와야 한다. 따라서 Java에서 점수를 매기면 매 요청마다 전 종목을 메모리로 올려야 하고 `LIMIT`을 DB로 내릴 수 없다. 다만 규모(약 850종목)를 감안하면 메모리 처리도 실제로는 감당 가능하다는 점도 함께 고려할 것.

**선정 이유 표시와 판정 로직의 일치.** `frontend.md`가 조건별 획득 점수 노출을 요구한다. 화면에 보여주는 설명과 실제로 종목을 고른 판정이 서로 다른 코드에서 나오면 시간이 지나며 어긋난다. 조건의 판정 의미를 한 곳에 두고 양쪽이 그것을 쓰게 하면 이 문제가 사라진다. 워치리스트 알림 판정도 같은 로직을 필요로 한다(spec §7) — 세 번째 사용처다.

**상대 조건.** "PER 하위 20%" 같은 조건은 스칼라 비교가 아니라 유니버스 내 순위다. 런타임 윈도 함수 대신 배치에서 백분위를 미리 계산해두면 평범한 스칼라 비교로 내려간다. 읽기가 쓰기보다 압도적으로 많은 워크로드라는 점이 이 교환의 근거다. v1 UI가 상대 조건을 노출하지 않더라도 저장 구조가 이를 수용할 수 있는지는 미리 볼 것 — 나중에 넣으려면 스칼라 전제가 깨진다.

**지표 대 지표 비교.** "종가 > SMA200" 같은 조건은 피연산자가 상수가 아니라 다른 지표다. 이를 표현할 수 없으면 이동평균 돌파류 조건이 전부 하드코딩 분기로 우회된다.

**저장량.** 850종목 × 150지표 × 500일 ≈ 64M행 / 약 6.7GB(인덱스 포함) — 실측 계산이다. 그런데 스크리닝은 항상 최신 일자 한 장만 조회하고, 과거 지표 시계열이 필요한 차트는 v1 범위 밖이다. 지표 값의 보존 기간을 제한하면(원자료는 전량 보관 — 지표는 원자료에서 재생성 가능하지만 그 역은 불가능하다) 1/8 수준으로 떨어진다. 보존 기간을 둘지, 둔다면 얼마로 할지는 판단 사항.

**EAV를 택할 경우의 약점.** 임의 컬럼 정렬이 자연스럽지 않다는 것이 실질적 대가다. 사용자가 한 번에 한 컬럼으로만 정렬한다는 점이 완화 근거가 된다. 인덱스 설계(조건 술어가 어떤 형태로 생성되는지에 맞춘)가 성능을 좌우한다.

**폐기된 지표.** 저장된 커스텀 화면이 참조하는 지표가 사라지면 화면이 깨진다. 삭제 대신 비활성 표시, FK 대신 서비스 계층 검증 같은 선택지가 있다.

**파생 지표의 중복 계산.** spec이 예로 든 MACD-V는 MACD와 ATR에서 파생된다. 파생 지표가 부모의 계산을 다시 구현하면 두 구현이 어긋나기 시작한다. 지표 간 의존을 선언할 수 있으면 이 문제와 워밍업 기간 산정이 같이 풀린다.

**워밍업 구간 처리.** 이력이 부족해 계산할 수 없는 구간에 값을 쓰지 않으면(행 자체가 없으면), 조건 판정에서 해당 종목이 자연히 제외된다. 부정확한 값을 채워 넣는 것보다 낫다.

## 4. Phase 구성 (순서 제안 — 조정 가능)

각 phase의 내부 설계는 해당 시점 에이전트가 판단한다. 여기서는 무엇을 다루는지와 그 phase에서 특히 걸리는 제약만 적는다. 진행 상태는 [`../progress.md`](../progress.md)에 있다.

| Phase | 다루는 것 | 그 phase에서 특히 걸리는 것 |
|---|---|---|
| **1. 기반** | 의존성, 스키마 기반, 지표 확장 지점, 조건 모델과 번역, 인증(Google OAuth + 허용 이메일) | §1의 함정 전부. §2의 지표 확장성·통합 조건 모델·트리 흡수성 |
| **2. 수집 파이프라인** | 소스 어댑터(v1은 국내 2개 — 미국은 v1.1, ADR-0010), 초기 적재, 일일 갱신, 유니버스 리밸런싱 | 소스 교체 영향의 국소화. 초기 적재/일일 갱신 분리. 종목 단위 실패 격리와 실패 단위 식별. Spring Batch 도입 판단 시점 |

## 5. Phase 완료 판정

구현 형태와 무관하게 성립해야 하는 것들이다. **통과 여부는 여기 적지 않는다** — 그것은 [`../progress.md`](../progress.md)의 몫이다. 기준과 현황을 같은 곳에 두면 기준까지 매번 다시 읽어야 하고, 기준이 현황에 맞춰 조용히 느슨해진다.

Phase 2·3 기준은 착수 시점에 이 문서에 없어 실행 에이전트가 새로 세웠고, 나중에 여기로 옮겼다. Phase 4 이후를 착수할 때는 **먼저 여기에 기준을 적고 시작한다.** 끝난 뒤에 세운 기준은 이미 한 일을 정당화하는 쪽으로 기운다.

### Phase 1 — 기반

- **QueryDSL이 런타임에 동작한다.** IMPORTANT — Hibernate 7 비호환은 컴파일이 아니라 런타임에 드러난다. 쿼리를 **실제로 실행하는** 테스트가 반드시 있어야 한다. 컴파일 성공은 아무것도 보증하지 않는다.
- **지표 추가가 실제로 싸다.** 더미 지표 하나를 추가했을 때 다른 파일을 몇 개 고쳐야 하는지 세어본다. 1개면 성공, 여러 개면 §2의 확장성 요구를 만족하지 못한 것이다. spec §7의 실질 검증이다.
- **하나의 조건 구성이 두 판정 방식 모두를 지탱한다.** 같은 조건 집합을 필터링과 가중 점수 양쪽으로 실행해 각각 올바른 결과가 나오는지 확인한다.
- **조건 N개가 예상한 쿼리 형태로 번역된다.**
- **허가되지 않은 이메일이 차단된다.**
- ADR이 기록되어 있고 각 `## 검증` 절이 채워져 있다.

### Phase 2 — 수집 파이프라인

- **소스 교체가 국소적이다.** 상위 계층(배치·수집기·지표)에서 벤더 이름이 검색되지 않아야 한다. `data-pipeline.md`의 "코드 수정과 재배포로 끝난다"는 요구의 실질 검증이다.
- **실패 격리의 단위가 종목이다.** 일부 종목이 실패해도 나머지가 처리되고, **어느 종목이 왜 실패했는지 나중에 식별**되며, 실패한 부분만 재실행된다. 셋이 모두 성립해야 관리자의 부분 재실행이 성립한다.
- **실패가 조용히 넘어가지 않는다.** 850종목이 실패해도 알림은 요약 **1건**이다. 종목마다 보내면 알림 자체가 무의미해진다.
- **초기 적재와 일일 갱신이 분리되어 있다.** 일일 배치에 초기 적재 분기가 섞이지 않는다.
- **중단 후 이어서 재시작된다.** 일일 쿼터가 있는 소스에서 한 번에 끝나지 않는 것이 정상 시나리오다.
- **멱등하다.** 같은 구간을 다시 돌려도 결과가 같고 `EXCLUDE` 제약을 위반하지 않는다.
- **실제 소스를 호출해 검증한다.** 목만으로는 봉투 파싱·에러 매핑·파라미터 검증이 전혀 검증되지 않는다.

### Phase 3 — 지표 계산

- **지표 추가 비용이 1파일이다.** Phase 1의 더미 지표 검증을 실제 지표로 다시 확인한다.
- **파생 지표가 부모의 시계열을 받아 계산한다.** 부모를 두 번 계산하지 않는다(MACD-V가 그 사례다).
- **워밍업 구간에 행이 없다.** 값을 낼 수 없는 구간에 0이나 null을 채우지 않는다 — 그 값은 조건 판정에서 "충족"으로 읽힌다.
- **입력이 지표 성격에 맞는다.** 기술적 지표는 `adj_close`, PER·PBR은 `close`. 섞이면 값이 그럴듯하게 틀린다.
- **멱등하고 종목 단위로 격리된다.** Phase 2와 같은 기준이다.
- **원자료가 바뀌면 파생 지표가 무효화된다.** 최소한 주가 수정(`PRICE_ADJUSTED`)과 재무 정정(`FINANCIAL_REVISED`) 두 경로.
- **백분위가 유니버스 한정 오름차순이다.** 전체 시장 기준으로 매기면 다른 값이 된다.
- **보존 정리가 원자료를 건드리지 않는다**(ADR-0011).
- **실데이터로 손계산과 대조한다.** 합성 데이터는 계산 구조만 검증하고 소스 해석의 오류는 잡지 못한다.

### Phase 4 — 스크리닝 엔진

- **HTTP 결과가 인메모리 판정과 일치한다.** 같은 조건 집합을 `ConditionEvaluator`로 직접 접은 결과와 API 응답의 종목·점수·조건별 상태가 같아야 한다. 어긋나면 화면이 보여주는 선정 이유가 실제로 종목을 고른 근거가 아니게 되고, 그 차이는 사용자가 손으로 대조하기 전까지 드러나지 않는다.
- **조건별 판정이 세 상태 그대로 응답에 실린다.** 충족·불충족·데이터없음이 각각 다른 값으로 나간다. boolean 하나로 접으면 "지표가 없어 판정할 수 없었다"와 "조건에 맞지 않았다"가 화면에서 같아 보이고, 사용자는 결과를 이해할 근거를 잃는다. 이 병합은 백엔드 테스트로는 잡히지 않으므로 응답을 직접 봐야 한다.
- **기준 일자를 서버가 정하고 응답에 함께 돌려준다.** 요청이 비워도 서버가 최신 지표 일자로 해석하고 그 값을 에코한다. 에코가 없으면 배치가 하루 밀렸을 때 사용자가 어제 데이터를 오늘 것으로 읽는다.
- **보존 기간 밖의 요청이 빈 결과가 아니라 오류로 돌아온다.** 지표는 180거래일만 남으므로(ADR-0011) 그 이전 일자는 "조건에 맞는 종목이 없음"과 구분되어야 한다. 빈 200을 주면 사용자는 조건을 계속 고치고, 그것이 조용한 실패다.
- **프리셋과 커스텀 화면이 같은 저장 구조와 같은 실행 경로를 쓴다.** 프리셋도 `screen`·`condition_group`·`screen_condition` 행이고, 실행은 어느 쪽이든 같은 코드로 간다. 프리셋을 코드 안의 특별 취급으로 두면 지표를 하나 추가할 때 고칠 곳이 둘이 된다.
- **프리셋 시딩이 멱등하고, 폐기가 삭제가 아니다.** 두 번 기동해도 결과가 같고, 선언에서 빠진 프리셋은 비활성이 될 뿐 행이 남는다. 지우면 그것을 참조하던 워치리스트가 함께 끊긴다.
- **백분위 조건의 부등호가 원본 지표의 유불리와 맞는다.** 백분위는 언제나 오름차순이므로 "PER 하위 20%"는 `<= 0.2`, "ROE 상위 20%"는 `>= 0.8`이다. 뒤집히면 정반대 종목이 최상위로 올라오는데, 값이 그럴듯해서 눈으로는 드러나지 않는다.
- **지지·저항이 지표와 물리적으로 분리되어 있다.** 응답에서 다른 자리에 있고, 지표 카탈로그에 코드가 없으며, 조건의 좌변으로 쓸 수 없고, 저장되지도 않는다. 같은 자리에 두면 사용자가 확정 신호로 오해하고 그 오해는 금전 손실로 이어진다.
- **오류가 조용히 삼켜지지 않고, 재시도 가능 여부를 프론트가 판별할 수 있다.** catch-all 핸들러가 없고, 응답 바디가 없어도 상태 코드만으로 자동 재시도 대상인지 구분된다. 구분이 없으면 버그를 무한 재시도하거나 일시 장애를 사용자에게 떠넘긴다.
