# 단일 누적 상태를 작업 단위로 해체하라

2026-05 이후 Claude Code와 OpenAI Codex 양쪽에서 널리 쓰이는 하네스 관행은 다섯 가지로 수렴했다. 진입 파일(AGENTS.md·CLAUDE.md)은 **100~200줄짜리 「지도」로 짧게 두고**, 나머지는 경로 스코프 규칙·skills로 필요할 때 불러온다. 큰 작업은 **작업 단위 plan 파일**(ExecPlan, plan mode)로 진행하고, 병렬 작업은 **worktree로 격리**한다. 규범은 문장이 아니라 hook·린터·CI 같은 **결정적 센서**로 강제하며, 에이전트가 스스로 쌓는 메모리는 **기계 로컬, 개인용**으로 한정한다. 평가 대상 하네스의 두 축은 방향이 옳다. progress 파일은 Anthropic이 장기 실행 에이전트용으로 직접 제시한 패턴이고, `applies_to` glob은 주요 도구 4종이 1급 기능으로 제공하는 패턴을 변형한 것이다. 실행 가능한 `premise` 펜스는 공개된 기업 사례보다 오히려 앞선 형태다. 그러나 두 축 모두 **「한 사람이 `main`에서 쓰기를 직렬화한다」는 전제 위에서만 안전하다**. 모든 작업이 같은 파일의 같은 앵커를 고치는 단일 progress 파일은 「브랜치 8개 중 7개 충돌」, 「열린 PR의 40%가 공유 지시 파일 수정」 같은 실사례를 그대로 재현할 구조다. 순차 번호, 에이전트 단독 작성, SessionStart 때마다 43초씩 도는 재검증도 팀에서는 각각 번호 충돌, 리뷰 병목, 사람 수만큼 곱해지는 비용이 된다. Anthropic·OpenAI·Google 누구도 공유 progress 파일의 머지나 대형 ADR 코퍼스를 다루는 공식 지침을 내지 않았다. 세 곳의 공통 답은 두 가지다. **충돌은 머지로 풀지 말고 소유권으로 피하고**, **에이전트가 쓴 지속 문서는 PR 리뷰를 거치게 한다**. 따라서 팀용 모듈로 가는 길은 이렇다. progress.md를 「불변식, 작업별 ExecPlan, 트래커 백로그」 셋으로 해체한다. ADR은 저장소에 그대로 두되 번호 선점, 사람 승인, 모순 검사를 붙인다. premise 재실행은 SessionStart에서 CI와 야간 「정원사」 잡으로 옮긴다. 증거 수준도 함께 밝혀 둔다. 에이전트 작성 ADR 누적이 팀 규모에서 통하는지를 측정한 연구는 찾지 못했다. 그리고 이 질문의 핵심 1차 자료인 OpenAI 「Harness engineering」 원문은 HTTP 403으로 열리지 않아 2차 요약에 기댔다.

> **신뢰도 표기.** 연구 노트의 표기를 그대로 쓴다. **[1차]**는 공식 문서·원저자·논문 원문을 직접 읽은 것이다. **[2차]**는 요약이나 재인용만 확인한 것이고, **[미검증]**은 원문을 열지 못했거나 검색 스니펫만 본 것이다. **[실무자]·[일화]**는 개인 블로그나 개별 저장소 이슈라 일반화 근거로 약하고, **[벤더]**는 자사 제품 홍보 성격의 글이다. **[기초·이전]**은 2026-05 이전 자료다. **[실측]**은 이 보고서를 쓰며 2026-10-13에 `stock-screener` 저장소에서 직접 잰 값이다. 공식 문서 페이지 대부분은 게시일을 표시하지 않는다. 그런 경우 「2026-10-13 열람」이라고 적고, 페이지 안의 버전 번호(예: Claude Code v2.1.28x)로 신선도를 가늠했다.

## 두 벤더는 「짧은 지도 + 필요 시 로드 + 기계 검증」으로 수렴했다

**Anthropic은 파일 기반 세션 간 상태 자체는 공식적으로 권한다.** 「Effective harnesses for long-running agents」에서 initializer 에이전트가 만드는 것은 세 가지다. 200개 이상의 기능을 `passes: false`로 나열한 `feature_list.json`, `claude-progress.txt`, 그리고 `init.sh`다. 이후 매 세션은 git log와 progress 파일을 읽고 기능 하나를 골라 진행한 뒤 커밋한다. 목록을 JSON으로 둔 이유도 적혀 있다. 모델이 Markdown보다 JSON을 부적절하게 덮어쓸 가능성이 낮다는 것이다 **[1차, 2025-11-26, 기초·이전]** ([Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). API memory tool 문서의 「multisession software development pattern」도 같은 구조다. progress log와 feature checklist를 두고, 세션이 끝나기 전에 progress log를 갱신한다. 이 문서의 코드 예제가 `claude-opus-5-5`를 쓰므로 Claude 5 출시 뒤에 갱신된 것이다 **[1차, 2026-10-13 열람]** ([Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). 다만 **Anthropic의 예시는 전부 「한 에이전트 계보가 한 작업, 한 브랜치를 이어 가는」 경우다.** 같은 글도 다중 에이전트 구조가 더 나은지는 "still unclear"라고 남겨 두었다.

동시에 Anthropic은 **팀이 공유하는 층과 에이전트가 누적하는 층을 날카롭게 가른다.** 커밋하는 프로젝트 CLAUDE.md는 "Team-shared instructions"이고 목표는 "under 200 lines per CLAUDE.md file"이다. 길수록 "consume more context and reduce adherence"하기 때문이다. 반면 에이전트가 직접 쓰는 auto memory는 "machine-local … not shared across machines or cloud environments"이고, 세션마다 `MEMORY.md`의 첫 200줄 또는 첫 25KB만 로드된다 **[1차, v2.1.214~v2.1.285 언급, 2026-10-13 열람]** ([How Claude remembers your project](https://code.claude.com/docs/en/memory)). Best practices 문서의 include/exclude 표는 "Architectural decisions specific to your project"를 CLAUDE.md에 넣을 것으로, "Information that changes frequently"를 뺄 것으로 분류한다. 그리고 "Treat CLAUDE.md like code: review it … prune it regularly"라고 쓴다 **[1차, v2.1.283 언급, 2026-10-13 열람]** ([Best practices](https://code.claude.com/docs/en/best-practices)). 평가 대상 하네스는 이 구분에 딱 맞지 않는다. **커밋되어 공유되는 쪽에 있으면서, 성장 방식은 에이전트 누적형이다.** 벤더 지침이 직접 다루지 않는 조합이고, 크기 한도와 「자주 바뀌는 정보는 빼라」는 원칙으로 보면 간접적으로 경계하는 조합이다.

**Claude 5 세대 이후 Anthropic의 방향은 「항상 로드되는 텍스트를 줄이라」로 더 강해졌다.** Thariq Shihipar의 「The new rules of context engineering for Claude 5 generation models」는 몇 가지를 보고한다. Claude Code 시스템 프롬프트를 80% 넘게 잘라냈지만 측정 가능한 손실이 없었다. CLAUDE.md는 가볍게 두고 토큰 대부분을 코드베이스의 함정(gotcha)에 쓰라. 규칙보다 판단을, 그리고 progressive disclosure를 택하라 **[1차로 보이나 claude.dev 도메인 소유 미검증, 페이지 표시 2026-07-24]** ([claude.dev blog](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)). The Decoder는 같은 내용을 2026-07-02에 보도했다 **[2차, 날짜 불일치]** ([The Decoder](https://the-decoder.com/anthropic-says-it-cut-80-percent-of-claude-codes-system-prompt-because-fable-5-models-want-a-smaller-system-prompt/)). 대규모 코드베이스 가이드는 설정을 맡을 **DRI나 전담 팀**을 성공 조건으로 든다. 설정은 3~6개월마다, 그리고 주요 모델이 나온 뒤 다시 검토하라고 권한다. 이전 모델의 한계를 보정하던 지시가 새 모델을 "actively constrain"할 수 있기 때문이다 **[1차, 2026-05-14]** ([Claude Blog](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)). 같은 계열 문서에는 세 가지가 더 있다. plan 파일은 compaction 뒤에 재주입된다. SessionStart hook의 stdout 주입은 공식 경로다. Stop hook이 CLAUDE.md 갱신을 제안하게 할 수 있다 **[1차, 2026-10-13 열람]** ([Large codebases](https://code.claude.com/docs/en/large-codebases)).

**OpenAI는 저장소 안에 계획과 결정을 두는 쪽을 가장 명시적으로 지지하는 벤더다.** 다만 핵심 원문은 읽지 못했다. Ryan Lopopolo의 「Harness engineering: leveraging Codex in an agent-first world」가 2차 요약 여러 곳에서 일치하는 내용은 다음과 같다. 커다란 AGENTS.md 하나는 "context crowding, guidance overload, rapid rot, hard to verify" 때문에 실패했다. 그래서 AGENTS.md를 약 100줄짜리 지도로 줄이고 `docs/`를 system of record로 삼았다. 그 아래에 `design-docs/`, `exec-plans/`(active·completed·tech-debt), `product-specs/`를 둔다. 전용 린터와 CI가 지식베이스의 최신성과 교차 링크를 검증하고, 반복 실행되는 "doc-gardening" 에이전트가 코드와 어긋난 문서를 찾아 fix-up PR을 연다 **[2차 — openai.com 원문 403, 2026-02-11, 기초·이전]** ([원문 openai.com](https://openai.com/index/harness-engineering/); [2ooks 요약](https://2ooks.github.io/knowledge-base/summaries/openai-harness-engineering.html); [businessdatasolutions 요약](https://businessdatasolutions.github.io/ai-wiki/sources/2026-02-11-lopopolo-codex-harness-engineering)). 1차로 읽을 수 있었던 ExecPlan cookbook은 기능마다 plan 하나를 두고, 필수 living 절 넷을 요구한다. 타임스탬프 체크박스로 쓰는 **Progress**, **Surprises & Discoveries**, 모든 결정을 적는 **Decision Log**, **Outcomes & Retrospective**다. 그리고 "Every ExecPlan must be fully self-contained"라고 쓴다 **[1차, 페이지에 archived 표시·날짜 없음, DevDay 2025 발표에서 처음 소개]** ([OpenAI Cookbook](https://developers.openai.com/cookbook/articles/codex_exec_plans)). Codex의 AGENTS.md는 루트부터 현재 디렉터리까지 이어 붙이며, 합친 크기에 `project_doc_max_bytes` 기본 **32 KiB** 상한이 걸려 있다 **[1차, 2026-10-13 열람]** ([Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). Codex memories는 기본으로 꺼져 있고 `~/.codex/memories/`에 로컬로 쌓인다. 문서는 "Keep required team guidance in AGENTS.md or checked-in documentation"이라고 못 박는다 **[1차, 2026-10-13 열람]** ([Codex Memories](https://learn.chatgpt.com/docs/customization/memories.md?surface=app)). Google도 같은 구도다. Gemini CLI의 `save_memory`는 **개인 전역** `~/.gemini/GEMINI.md`에 쓴다. 팀이 공유하는 것은 Conductor 확장이 저장소에 두는 spec과 plan Markdown이다 **[1차, Conductor 2025-12-17, 기초·이전]** ([Gemini CLI memory](https://google-gemini.github.io/gemini-cli/docs/tools/memory.html); [Google Developers Blog: Conductor](https://developers.googleblog.com/conductor-introducing-context-driven-development-for-gemini-cli/)).

## 단일 progress 파일은 병렬화하는 순간 모든 브랜치의 충돌 앵커가 된다

팀 설정에서 progress 파일이 실제로 어떻게 깨지는지 보여 주는 증거는 2026-09~10의 저장소 이슈 두 건이다. 둘 다 같은 뿌리를 가리킨다. melg8/swarm에서는 `agent_progress.md`가 열린 브랜치 8개 모두에서 수정되어, 순차 머지 때 **8개 중 7개가 충돌**했다. 작성자의 진단은 이렇다. "Every branch therefore carries an edit at the same anchor (the top of `agent_progress.md`) - a text conflict for any pair of branches by construction." 해결책은 `docs/progress/` 아래에 **작업마다 파일 하나**를 두고 그 작업의 소유자만 쓰게 하는 것이었다. 그러면 머지가 "a set union, not a text clash"가 된다 **[일화·1차 이슈, 2026-09-22]** ([melg8/swarm #33](https://github.com/melg8/swarm/issues/33)). francovp/cabros-bot에서는 최신 열린 PR 60개 중 **24개(40%)**가 AGENTS.md를 고쳤다. 그 결과 PR을 연 지 3분 만에 다른 머지로 충돌이 났고, 열린 PR 125개 중 33개가 DIRTY 상태였다 **[일화·1차 이슈, 2026-10-04]** ([francovp/cabros-bot #1339](https://github.com/francovp/cabros-bot/issues/1339)). 도구 쪽에서도 같은 고백이 나온다. Task Master 이슈 본문은 로컬 `tasks.json` 방식이 "works well for solo development, but … introduces merge conflicts … in team environments"라고 쓰고, GitHub Issues 백엔드를 제안했다 **[미검증 — GitHub 원문 대신 forgejo 미러만 열람, 날짜 미확인]** ([forgejo 미러 #1132](https://forgejo.us2.navan.dev/github/claude-task-master/issues/1132)). BMAD의 병렬 운영 가이드는 머지 단계의 충돌 핫스팟으로 `sprint-status.yaml`을 지목한다 **[2차]** ([bmad-orchestrate-skill](https://playbooks.com/skills/julianobarbosa/claude-code-skills/bmad-orchestrate-skill)). 연구 규모의 수치도 있다. 에이전트 PR 33,596건을 분석한 논문이 저장소의 40.2%에서 시간이 겹치는 에이전트 PR 쌍을 찾았고, 서로 다른 에이전트 사이의 충돌률을 41.7%로 보고했다는 것이다. 그러나 이것은 **[2차 블로그 경유 · arXiv:2607.04697 원문 미열람]**이다 ([Daniel Vaughan, 2026-07-28](https://codex.danielvaughan.com/2026/07/28/agent-pr-merge-conflicts-concurrent-coding-agents-codex-cli-worktree-isolation-coordination-defence/)).

**평가 대상 하네스가 지금 충돌하지 않는 이유는 구조가 아니라 규율이다.** 이 저장소에서 잰 값은 다음과 같다 **[실측, 2026-10-13]**. `docs/progress.md`는 214,121바이트, 1,829줄이다. 2026-08-04 첫 커밋 이후 이 파일을 건드린 커밋은 644건이고, 최근 30일만 298건으로 **하루 약 10회**다. 하네스는 이미 `hold/*`·`explore/*` 브랜치를 쓴다. 2026-10-07~13 사이 머지 커밋은 8건인데, 그중 **progress.md를 양쪽 부모가 모두 고친 머지는 0건**이다. 진행 상태 갱신을 `main`에서만 한다는 규율이 지켜졌기 때문이다. ADR 0172~0175도 브랜치에서 생겼지만 번호 중복은 0건이다. 한 사람이 번호를 순서대로 배정했기 때문이다. 같은 구조에 개발자가 둘 붙거나 worktree 병렬 에이전트가 각자 progress를 갱신하면 swarm #33과 같은 형태가 된다. 이것은 추론이지만, 앵커가 「맨 위의 현재 상태 절」 하나라는 점에서 구조가 같다. SessionStart 훅이 214KB 전체가 아니라 백로그를 뺀 부분만 주입한다는 점도 확인했다. 이번 실행에서 주입된 양은 약 7.3KB였다 **[실측]**. 이것은 Claude Code가 `MEMORY.md`에 거는 「첫 200줄·25KB만 로드」를 손으로 구현한 것과 같다. 따라서 **문제는 주입 비용이 아니라 쓰기 경합과 낡음이다.**

대안은 세 계열로 정리된다. 각각 무엇을 포기하는지가 다르다. 첫째는 **작업 단위 파일**이다. OpenAI ExecPlan, Spec Kit의 `specs/<NNN-name>/`, Kiro의 `.kiro/specs/<feature>/`가 여기에 든다. 서로 다른 작업끼리의 텍스트 충돌은 없애지만, 순번 식별자를 배정할 때 충돌이 다시 생긴다. Spec Kit에서는 공통 브랜치에서 갈라진 사람들이 같은 001, 002를 받는 문제가 보고됐다 **[1차 이슈 2026-04-01, 미해결 stale]** ([github/spec-kit #2047](https://github.com/github/spec-kit/issues/2047)); **[미검증 — 검색 스니펫만]** ([discussion #497](https://github.com/github/spec-kit/discussions/497)). 둘째는 **트래커를 상태 저장소로 쓰는** 방식이다. Copilot cloud agent는 이슈·PR·세션 로그로 진행을 남기고 팀원이 그것을 따라간다 **[1차, 2026-10-13 열람]** ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Claude Code GitHub Actions는 진행과 결과를 트리거한 이슈·PR 코멘트에 쓴다 **[1차]** ([GitHub Actions docs](https://code.claude.com/docs/en/github-actions)). 이 방식은 브랜치의 진행 상태가 `main`에 섞이는 문제를 원리적으로 없앤다. 대가는 세션 시작 때 MCP·API 호출이 필요하다는 것, 그리고 상태가 코드 리비전에서 분리된다는 것이다. 셋째는 **git-native 트래커**다. beads는 순번 ID가 "caused frequent collisions when multiple agents or branches created issues concurrently"하자 v0.20.1에서 해시 ID로 바꿨다. 이어 JSONL과 커스텀 merge driver를 쓰다가, 2026-02에 셀 단위로 머지하는 Dolt로 옮기고 저장도 코드 브랜치와 분리된 `refs/dolt/data`로 옮겼다 **[1차 README]** ([steveyegge/beads](https://github.com/steveyegge/beads); [v0.21.1 README](https://pkg.go.dev/github.com/steveyegge/beads@v0.21.1)). 이전 이유는 SQLite+JSONL 동기화가 "proved too fragile"했고 동시 에이전트가 4개를 넘으면 버티지 못했기 때문이라는데, 이 수치는 **[2차·벤더 — Dolt 자사 블로그, 2026-03-13]**이다 ([DoltHub](https://www.dolthub.com/blog/2026-03-13-multi-agent-persistence/)). 세 계열이 공유하는 기법은 셋이다. **충돌 없는 식별자, 항목당 파일 또는 행 단위 머지, 코드 브랜치와 분리된 저장소.** 단일 Markdown 누적 파일에는 셋 중 어느 것도 없다.

낡음 문제에 대해 공개된 기계적 해법 중 가장 정교한 것은 **GitHub Copilot Memory**다. 저장소 범위의 사실을 "citations pointing to the code"와 함께 저장한다. 그리고 쓰기 직전에 그 인용을 현재 브랜치에서 다시 검증하고, 검증된 사실만 사용한다. 28일 동안 쓰이지 않은 사실은 자동으로 삭제된다 **[1차, 2026-10-13 열람]** ([GitHub Docs: Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). GitHub는 이 메모리를 A/B로 시험해 coding agent PR 머지율이 **90% 대 83%**로 올랐다고 보고했다 **[1차, 2026-01, 기초·이전 — 게시일 01-09/01-15 표기 불일치]** ([GitHub Blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). Anthropic Managed Agents의 memory store는 동시 쓰기 문제를 다룬다. **`content_sha256` 전제 조건을 쓰는 낙관적 동시성 제어**를 두고, 모든 변경을 불변 버전으로 남기며, 표준과 관례는 **읽기 전용 공유 store**에 두라고 권한다 **[1차, beta 헤더 `agent-memory-2026-07-22`]** ([Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)). 같은 플랫폼의 "Dreams"는 쌓인 store의 중복·모순·낡은 항목을 정리해 **새 store를 만들고 원본은 건드리지 않는다** **[미검증 — 검색 스니펫만, 원문 미열람]** ([Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)).

## 에이전트 작성 ADR 175개는 앞서 있지만 사람의 승인 경로가 비어 있다

**ADR을 에이전트 컨텍스트로 쓰자는 담론은 2026년에 성숙했지만, 권위 있는 1차 출처는 「ADR」이라는 형식을 지목하지 않는다.** martinfowler.com의 Böckeler는 컨텍스트 수단을 CLAUDE.md, 경로 규칙, skills, subagents, MCP, hooks로 분류한다. 로드를 정하는 주체도 LLM, 사람, 결정적 트리거 셋으로 나눈다. 그러면서 "An agent's effectiveness goes down when it gets too much context"라고 경고하고, ADR은 언급하지 않는다 **[1차, 2026-02-05, 기초·이전]** ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html)). Thoughtworks Radar Vol.34에도 ADR 블립은 없다. 대신 "Curated shared instructions for software teams"를 Adopt에, "Agent instruction bloat"를 Caution에 놓았다 **[1차, 2026-04, 기초·이전]** ([Radar Techniques](https://www.thoughtworks.com/radar/techniques)). ADR을 명시적으로 권하는 쪽은 실무자와 벤더다. 이들이 기록한 실패 형태 둘이 이 하네스가 스스로 적어 둔 실패와 정확히 같다. Duncan Davidson은 에이전트가 "preserved an outdated storage abstraction … because an ADR still described it as mandatory"한 **과잉 순응** 사례를 적었다. 그래서 ADR은 현재 텍스트만 유지하고 변경 이력은 git에 맡기며, 충돌하면 에이전트가 멈추고 논의하게 하라고 처방한다 **[1차·실무자 에세이, 2026-10-02]** ([O'Reilly Radar](https://www.oreilly.com/radar/coding-agents-love-decision-records/)). Daniel Vaughan은 에이전트가 만든 ADR이 "capture *what* was decided but may fabricate the *why*"하므로 Context와 Consequences 절은 사람이 검토하라고 경고한다 **[실무자, 2026-04-28]** ([codex.danielvaughan.com](https://codex.danielvaughan.com/2026/04/28/codex-cli-architecture-decision-records-adr-automated-governance/)). 그가 근거로 인용한 arXiv 2604.04990은 저자 표기가 실제 논문과 어긋나 인용 정확성이 의심된다 ([arXiv 2604.04990](https://arxiv.org/html/2604.04990v1)). 이 하네스의 CLAUDE.md가 내건 「저장소 안의 서술은 전부 누군가 그때 그렇게 믿었다」와 「낡은 ADR이 최선의 판단을 막게 두지 않는다」는 외부에서도 관찰된 현상에 대한 대응이다. 이 둘은 이 하네스만의 특이 규칙이 아니다.

**`applies_to` glob은 확립된 패턴을 맞춤 구현한 것이다. 네이티브 구현과는 두 가지가 다르다.** 경로 glob으로 지시를 파일에 붙이는 기능은 Claude Code `paths:`, Cursor `globs`, Kiro `fileMatchPattern`, Copilot `applyTo`가 모두 1급으로 제공한다 **[1차, 2026-10-13 열람]** ([Claude Code memory](https://code.claude.com/docs/en/memory); [Cursor rules](https://cursor.com/docs/context/rules); [Kiro steering](https://kiro.dev/docs/steering/); [Copilot instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)). 첫째 차이는 시점이다. 네이티브 규칙은 Read 시점에 로드되므로 **편집 전**에 들어온다. 이 하네스의 PostToolUse 포인터는 **편집 후**에 알린다. 둘째 차이는 내용이다. 네이티브 규칙은 본문을 주입하고, 이 하네스는 포인터만 준다. 이 저장소의 ADR 디렉터리는 175개 파일에 디스크 2.5MB다(`du`). 그중 174개에 `applies_to`가 있고 101개에 `premise` 펜스가 있다(펜스 합 154개) **[실측, 2026-10-13]**. 이 규모에서는 포인터 방식이 맞다. 그러나 Claude Code는 rule frontmatter에서 "`paths` is the only field Claude Code reads … any other field is ignored without an error"이다. 그래서 ADR을 그대로 `.claude/rules/`로 옮기면 커스텀 필드는 무시되고 본문 전체가 주입된다 **[1차]** ([Memory](https://code.claude.com/docs/en/memory)). 팀에 Cursor나 Copilot 사용자가 섞이면 Claude Code 전용 hook 포인터는 그 사람들에게 아예 보이지 않는다. 현재 저장소에는 `AGENTS.md`도 없다 **[실측]**.

**실행 가능한 `premise` 펜스는 공개 사례 중 가장 가까운 것보다도 결정적이다.** 다만 SessionStart에 두기에는 팀 비용이 크다. 공개된 신선도 장치는 다음과 같다. OpenAI의 린터·CI와 doc-gardening 에이전트 **[2차]**가 있다. Claude Code `/doctor prompt-audit`는 오래된 모델용 지시, 존재하지 않는 파일 참조, 서로 모순되는 파일을 찾지만 기본 범위가 `.claude/`와 지시 파일이라 `docs/adr/`는 경로를 직접 지정해야 한다 **[1차]** ([Memory](https://code.claude.com/docs/en/memory)). Intercom은 주간 GitHub Action으로 모든 CLAUDE.md를 fact-check한다 **[기초·이전, 2026-03-19]** ([Intercom](https://ideas.fin.ai/p/how-we-use-claude-code-today-at-intercom)). 마지막이 앞서 본 Copilot Memory의 인용 검증이다. 그중 어느 것도 「결정마다 실행 가능한 전제를 달아 다시 잰다」는 형태는 아니다. LLM 판정에 맡기기 어렵다는 근거도 있다. 980개 ADR로 위반 탐지를 평가한 연구에서 상위 모델의 정확도는 90%대였다. 그러나 실패의 42.4%가 인프라·배포 결정에서 났고, 오류 원인의 28.3%가 missing context였다 **[1차, 2026-02-07, 기초·이전]** ([arXiv 2602.07609](https://arxiv.org/html/2602.07609v1)). 그러니 SQL과 셸로 전제를 결정적으로 재는 이 하네스의 방식이 LLM 감사보다 신뢰도가 높을 가능성이 크다. 다만 직접 비교한 측정은 없다. 팀 비용의 근거는 이 저장소에서 확인했다 **[실측, 2026-10-13]**. `check-premises.sh`는 읽기 전용 `psql`로 로컬 DB에 질의하고, 펜스 본문 199행에 `psql`이나 `SELECT`가 들어 있다. 훅 주석에는 고정비, 즉 guard fork와 psql 접속에만 **34.6초**가 든다는 기록과 「판정 불가 19」를 낸 실행 기록이 남아 있다. 이런 전제는 **운영자 한 명의 로컬 DB 상태를 사실로 삼는다**. 다른 개발자의 랩톱이나 CI에서는 판정 불가가 되거나 서로 다른 답을 낸다. 그리고 그 43초가 사람 수와 세션 수만큼 곱해진다.

**큰 컨텍스트 코퍼스의 비용에 관한 2026 실증은 「정확도는 거의 안 움직이고 비용은 오른다」 쪽으로 기운다.** 다만 측정 대상이 서로 다르다. ETH Zurich의 「Evaluating AGENTS.md」는 **LLM이 생성한** context file이 성공률을 0.5~2%p 낮추고 비용을 20~23% 올린다고 보고했다. 개발자가 쓴 파일은 성공률을 평균 4%p 올렸지만 비용도 최대 19% 올렸다. 그리고 기존 문서와의 **중복**을 주된 문제로 지목했다 **[1차, 2026-02-12, 기초·이전]** ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). Khatri의 2-에이전트 ablation은 Claude Code와 Codex에서 none, always_on, selective 세 전략을 비교했다. 결과는 "Context strategy does not measurably move correctness"였고, Claude의 selective 전략만 캐시 생성 토큰을 줄였다(p=0.012) **[1차, 소표본, 2026-07-28]** ([arXiv 2607.27250](https://arxiv.org/html/2607.27250)). McMillan의 1,650세션 요인 실험은 파일 크기, 위치, 구조, 모순 어느 것도 다중 검정 보정 뒤 준수율 차이를 내지 못했다고 보고했다. 대신 **에이전트가 함수를 하나 더 만들 때마다 준수 odds가 약 5.6% 떨어졌다(OR=0.944)** **[1차, Opus 4.6·4.7 포함, 2026-05-11]** ([arXiv 2605.10039](https://arxiv.org/abs/2605.10039)). 이 하네스는 ADR 본문이 아니라 포인터와 전제 결과만 주입하므로 selective 전략에 가깝다. 그리고 McMillan의 결과는 긴 세션 후반에 지시가 덜 지켜진다는 뜻이다. 따라서 **편집 시점에 결정적으로 재주입하는 트리거** 자체는 정당화된다. 다만 시점을 편집 후에서 편집 전으로 당길 근거가 된다(추론 · 직접 비교 연구 없음).

**팀으로 넘어가면 ADR 누적이 드러내는 문제는 셋이다. 번호, 리뷰, 모순.** 순차 번호 충돌은 오래된 문제고 정답이 없다. Cloud Posse는 ISO-8601 날짜 ID를 제안했다가 "We can no longer refer to ADRs by a single number"라는 단점 때문에 **기각**했다 **[1차, 2021-10-19, 오래됨]** ([Cloud Posse](https://docs.cloudposse.com/resources/adrs/proposed/proposed-use-iso-8601-date-index-for-adrs/)). Clan은 병렬 PR에서 "ADR-3"이 셋 생긴 사건을 겪은 뒤 **승인 전에 번호를 선점 커밋**하는 절차를 채택했다. PR 번호를 차용하는 안과 ADR을 별도 저장소에 두는 안은 기각했다 **[1차, 26.05 문서판·상태 Proposed]** ([Clan ADR 03](https://clan.lol/docs/26.05/decisions/03-adr-numbering-process)). 리뷰는 「ADR을 코드처럼 PR로」가 모든 지침의 공통 전제다. Kiro는 "Treat steering changes like code changes — require reviews"라고 쓴다 **[1차]** ([Kiro](https://kiro.dev/docs/steering/)). Vercel의 adr-skill은 "human approves the decision while an agent implements it"라고 쓴다 **[2차 — 원 페이지 403]** ([mcpservers.org](https://mcpservers.org/agent-skills/vercel/ai/adr-skill)). 그러나 Vaughan의 말대로 "Agents scaffold systems in minutes; teams need hours or days to audit them." 이 하네스는 175개 모두 에이전트가 썼고 사람 승인 단계가 구조적으로 없다. 모순 문제도 남는다. Claude Code 문서는 두 지시가 모순되면 "Claude may pick one arbitrarily"라고 쓴다 **[1차]** ([Memory](https://code.claude.com/docs/en/memory)). premise 펜스는 「이 결정의 전제가 아직 서는가」는 재지만, **ADR 사이의 모순은 재지 않는다**.

## 엔터프라이즈는 상태를 스레드·PR로, 규범을 플러그인과 센서로 옮겼다

2026-05 이후 대형 조직의 공개 사례를 보면 **에이전트가 누적하는 프로젝트 전역의 단일 progress 파일을 세션마다 주입한다는 곳은 하나도 없다.** 작업 상태는 작업 표면에 붙는다. Shopify의 River는 Slack 네이티브 에이전트로, 전사 머지 PR의 **8분의 1**을 공동 작성하고 30일 동안 59,918세션을 돌렸다. 작업 상태의 정본은 영속 Slack 스레드다. 이유는 "The next person to hit a similar problem starts from this thread, not from a blank prompt"이다. 공개 transcript에서 나온 패턴은 skills와 기본값으로 다시 먹인다 **[1차, 2026-05-28]** ([Shopify Engineering](https://shopify.engineering/under-the-river)). Spotify의 Honk는 Claude를 Kubernetes pod에서 다수 세션으로 돌려 자동 유지보수 PR 250만 건을 머지했다. 규범은 지시 파일이 아니라 **Golden State·Soundcheck와 린트 가드레일**로 즉시 피드백한다. 동시에 **리뷰할 PR이 76% 늘어 그것이 새 병목**이 되었고, "in our more fragmented codebases, agent performance is measurably worse"라고 보고했다 **[1차, 2026-06-03]** ([Spotify Engineering](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint)). Uber는 PR의 70% 이상이 에이전트 몫이다. design docs·인시던트·PR을 묶은 **AI Context Graph**는 노드 24M개, 엣지 80M개 규모다. 근거를 받은 에이전트는 38초 만에 정답을 냈고, 근거 없는 에이전트는 20분 동안 오류 3회를 거친 뒤 오답을 냈다 **[1차, 2026-08-27]** ([Uber Blog](https://www.uber.com/us/en/blog/efficient-software-factory/)). 이 기업들에게 결정 근거는 상시 로드하는 파일이 아니라 **검색하고 그래프로 찾아오는 대상**이다.

조직 단위 배포의 표준은 「파일 하나」가 아니라 **버전이 붙은 plugin·playbook 패키지와 관리형 allowlist**다. 그리고 그 장치에는 반드시 소유자가 있다. LinkedIn은 저장소를 가로지르는 중앙 playbook과 저장소별 로컬 playbook을 두 층으로 운영하고, 모든 랩톱에서 **매시간 자동 갱신**한다. 거버넌스는 **"Aggressive deprecation"**, 즉 쓰이지 않는 도구를 적극적으로 걷어내는 것이다 **[1차 발표, InfoQ 페이지 2026-09-19]** ([InfoQ LinkedIn](https://www.infoq.com/presentations/linkedin-context-engineering/)). Stripe는 Cursor rule을 정본으로 두고 "sync our Cursor rules into a format that Claude Code can read as well" 하는 **단일 정본 + 도구별 동기화** 구조를 쓴다. CI 역압에는 "After the second push and CI run, we send the branch back to its human operator"라는 상한을 둔다 **[1차, 2026-02-19, 기초·이전]** ([Stripe Dev Blog](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). Anthropic의 대규모 가이드는 단일 DRI가 "ownership over the Claude Code configuration … the plugin marketplace, and CLAUDE.md conventions"를 가져야 한다고 쓴다. 그렇지 않으면 "knowledge will stay tribal"이다 **[1차, 2026-05-14]** ([Claude Blog](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)). 벤더 쪽 배포 경로도 갖춰졌다. Claude Code는 private plugin marketplace와 managed settings의 `strictKnownMarketplaces` allowlist를 제공한다 **[1차 문서 / 발표일 2026-02-24는 2차]** ([Plugins install](https://code.claude.com/docs/en/plugins/install); [Claude Blog](https://claude.com/blog/cowork-plugins-across-enterprise)). Codex는 plugin marketplace와 관리자가 강제하는 `requirements.toml`을 제공한다 **[2차 — 개인 블로그 요약, 2026-05-19]** ([Daniel Vaughan](https://codex.danielvaughan.com/2026/05/19/codex-cli-enterprise-admin-setup-rbac-managed-configuration-compliance-apis/)). Patrick Debois는 이것을 Context Development Lifecycle(Generate·Evaluate·Distribute·Observe)로 정리했다. 그러면서 "Who owns the CLAUDE.md? Who owns my skills?"는 아직 열린 질문이라고 인정했다 **[1차 발표, InfoQ 2026-09-30]** ([InfoQ](https://www.infoq.com/presentations/context-as-code-devops-agents/)).

이 사례들이 이 하네스에 주는 함의는 하나다. **대형 조직은 「에이전트가 쓴다」와 「모두가 읽는다」 사이에 반드시 소유자와 리뷰를 끼워 넣는다.** LinkedIn은 사용률로 폐기하고, Copilot은 28일이 지나면 만료시키고, Intercom은 매주 fact-check한다. 셋 다 **양을 억제하는 장치**다. 반면 이 하네스는 ADR을 폐기하지 않고 쌓으면서 premise로 낡음만 잰다. 낡음 측정은 업계보다 정교하지만, 부피를 줄이는 장치는 없다.

## 팀용 하네스 모듈로 옮기는 여섯 단계

아래 처방은 앞 절의 출처에서 도출한 내 제안이다. **이 형태 그대로 검증된 공개 사례는 없다.** 순서는 「되돌리기 쉽고 하네스의 값을 바꾸지 않는 것」부터 놓았다.

**첫째, progress.md를 셋으로 해체하고 주입은 생성된 색인으로 바꾼다.** 지금 「어떤 파일을 열든 알아야 하는 것」, 「되돌리지 말 것」에 든 **불변식**은 짧은 커밋 파일로 옮긴다. 경로가 정해져 있으면 `.claude/rules/`, 아니면 진입 파일의 gotcha 절이다. 이 파일은 사람 리뷰를 거치고 거의 바뀌지 않는다. Anthropic이 말하는 "gotchas"가 바로 이 층이다. **진행 중인 작업**은 `docs/exec-plans/active/<YYYYMMDD>-<slug>.md`처럼 작업마다 파일 하나로 두고, 그 작업의 브랜치나 worktree만 쓰게 한다. 머지되면 `completed/`로 옮긴다. 절 구성은 ExecPlan의 넷(Progress, Surprises, Decision Log, Outcomes)을 그대로 따른다. **백로그**는 이슈 트래커로 보낸다. SessionStart 훅은 이 셋을 이어 붙여 주입하되, **손으로 고치는 색인 파일은 두지 않는다.** 색인을 손으로 고치면 그것이 swarm #33의 「맨 위 앵커」가 되기 때문이다. 대신 훅이 디렉터리를 훑어 「활성 plan 목록 + 현재 브랜치의 plan」을 생성한다. 지금의 7.3KB 주입이 이미 백로그를 빼고 있으니 이 단계는 자르는 선을 파일 경계로 옮기는 일이다.

**둘째, ADR은 저장소에 두되 번호 선점과 사람 승인을 붙인다.** 코드·주석·CLAUDE.md가 `ADR-0107`식 번호를 대량으로 인용하므로, 날짜나 ULID ID로 바꾸면 참조를 잃는 비용이 크다. Cloud Posse가 날짜 ID를 기각한 이유와 같다. 가장 싼 가드는 **CI가 중복 번호를 거부**하는 것이다. 그다음 단계가 Clan식 **`main` 번호 선점 커밋**이다. 에이전트는 초안을 쓰고, `docs/adr/`에는 CODEOWNERS를 걸어 사람 승인 PR을 거치게 한다. 리뷰 부담은 Spotify가 보여 준 76%처럼 커지므로, 생성 임계를 「되돌리기 어려운 결정」으로 더 엄격히 좁혀 양을 줄인다. 사용자 CLAUDE.md가 이미 이 기준을 갖고 있으니, 그것을 사람 리뷰가 실제로 집행하게 만드는 것이 이 단계의 일이다.

**셋째, `applies_to`를 정본으로 두고 도구별 glob 규칙을 생성한다.** 175개 ADR 본문을 규칙으로 옮기지 않는다. 대신 glob 영역마다 「현재 유효한 결정 요약(번호 + 한 줄)」을 생성한다. 출력은 `.claude/rules/*.md`(`paths:`), `.github/instructions/*.instructions.md`(`applyTo`), 필요하면 하위 디렉터리 `AGENTS.md`다. Stripe가 Cursor rule을 Claude Code로 동기화하는 것과 같은 **단일 정본 + 도구별 동기화** 구조다. 루트에는 `AGENTS.md`를 두고 CLAUDE.md가 `@AGENTS.md`로 가져오게 하면 Codex 사용자도 같은 지도를 본다 **[1차]** ([Memory](https://code.claude.com/docs/en/memory)). 포인터 시점은 PostToolUse에서 **Read 시점 또는 PreToolUse**로 당긴다. 그래야 편집 전에 결정이 들어온다. 생성물은 커밋하고, CI가 「생성물과 정본이 일치하는가」를 검사한다.

**넷째, premise 재실행을 SessionStart에서 떼어 CI와 야간 정원사 잡으로 옮긴다.** 이 하네스의 가장 앞선 부분이므로 버리지 않고 위치만 바꾼다. 전제는 두 종류로 태그한다. **저장소만 보고 답하는 전제**(파일 존재, `grep`, 스키마)는 PR CI에서 돈다. 이때 diff와 `applies_to`가 겹치는 ADR만 돌린다. **운영 DB가 있어야 답하는 전제**는 한 곳에서만 돈다. 정본 데이터를 가진 운영 호스트나 공유 스테이징의 야간 잡이다. 실패는 이슈나 fix-up PR로 연다. OpenAI의 doc-gardening과 Intercom의 주간 fact-check Action이 놓인 자리가 여기다. SessionStart는 마지막 결과 파일(커밋 SHA, 측정 시각, 참/발견/판정 불가 수)만 읽어 한 줄로 주입한다. 그러면 43초가 사실상 0이 되고, 개발자마다 로컬 DB가 달라서 생기는 판정 불가가 사라진다. CLAUDE.md의 「기록은 그때의 믿음이니 지금 다시 잰다」는 원칙은 살아 있다. 다만 **재는 주체가 세션이 아니라 스케줄**이 될 뿐이다.

**다섯째, 모순 검사와 은퇴 경로를 더한다.** CI가 `applies_to` glob이 겹치는 accepted ADR 쌍을 나열하고, 새 ADR이 그 쌍에 끼면 PR에 표시한다. 이런 검사를 공개한 사례는 찾지 못했으므로 내 제안이다. Claude가 모순된 지시 중 하나를 "arbitrarily" 고른다는 공식 문장이 근거다. 은퇴 쪽에서는, 결정은 메모리가 아니므로 28일 만료를 그대로 들여오지 않는다. 대신 이렇게 처리한다. superseded 상태와 양방향 링크를 CI로 강제한다. premise가 지속적으로 「발견」을 내는 ADR은 재심 이슈를 자동으로 연다. 오랫동안 포인터에 한 번도 걸리지 않은 ADR은 생성 규칙의 요약에서 빼서 `archive` 상태로 내린다. Davidson의 「현재 텍스트만」 원칙을 함께 쓰면 개정 이력이 본문에 쌓이지 않는다.

**여섯째, 범용 부분을 plugin으로 묶고 프로젝트 내용은 저장소에 남긴다.** 프로젝트를 가리지 않는 부분은 하나의 Claude Code plugin으로 묶어 버전을 붙이고 marketplace로 배포한다. 훅 스크립트(주입, 생성, premise 러너, 번호 가드), ADR 템플릿, plan 템플릿, 생성기가 여기에 든다. 기획 정본, ADR 본문, plan, 불변식 같은 프로젝트 고유 내용은 저장소에 남긴다. Codex 쪽은 같은 스크립트를 CI와 `AGENTS.md` 생성으로 받는다. 그리고 이 모듈 자체에도 Anthropic이 말한 「모델 출시 뒤 재검토」를 정기 작업으로 넣는다. 「every component in a harness encodes an assumption about what the model can't do on its own」라는 문장은 이 하네스의 규칙 81KB(`.claude/rules/` 11개 파일, **[실측]**)에도 그대로 선다 **[1차, 2026-03-24, 기초·이전]** ([Anthropic Engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

## 읽지 못한 원문과 남은 공백

결론의 무게를 정하는 데 필요한 공백을 밝혀 둔다. **OpenAI 「Harness engineering」 원문(openai.com/index/harness-engineering)은 HTTP 403으로 열리지 않았다.** 그래서 exec-plans, doc-gardening, 약 100줄 AGENTS.md에 관한 문장은 모두 여러 2차 요약이 일치하는 내용이다. 원문이 「ADR」이나 「decision log」라는 낱말을 쓰는지도 확정하지 못했다. 미검증으로 남은 것은 다음과 같다. Vercel adr-skill 원 페이지(403), Managed Agents "Dreams" 문서(스니펫만), arXiv 2607.04697(2차 블로그 수치만), Spec Kit discussion #497(스니펫만), Task Master #1132(미러만). claude.dev 블로그의 도메인 소유도 독립적으로 확인하지 못했다. 주제 자체의 공백도 있다. **벤더 셋 모두 공유 progress 파일의 git 머지 충돌이나 대형 에이전트 작성 ADR 코퍼스를 다루는 공식 지침을 내지 않았다.** 이것은 「없음」을 확인한 것이 아니라 「찾지 못함」이다. ADR 코퍼스 크기나 에이전트 작성 ADR의 팀 리뷰 비용을 측정한 연구도 없다. Codex cloud task의 상태 저장, Jules, Thoughtworks Radar Vol.35는 조사 범위에 들지 못했다. 그리고 「Claude Opus 5 출시 이후」라는 기준 창에 대해 덧붙인다. 노트에 Opus 5의 정확한 출시일은 없다. ExecPlan, Anthropic 장기 실행 하네스 글, ETH 연구, Stripe 등 핵심 근거 상당수는 2026-05 이전 자료(**[기초·이전]**)다. 그러니 「2026-05 이후 새로 생긴 관행」과 「그 이전에 정착해 지금도 인용되는 관행」을 구분해 읽어야 한다.

## Conclusion

이 조사로 판단이 바뀐 지점은 하나다. 이 하네스의 약점은 **기록을 쌓는 방식이 아니라 쓰기를 직렬화하는 주체가 사람 한 명이라는 사실**이다. 지금 잘 돌아가는 것은 progress.md를 `main`에서만 고치는 규율, 번호를 한 사람이 배정하는 습관, 로컬 DB를 정본으로 삼는 premise 덕분이다. 셋 다 그 사람이 빠지거나 둘이 되는 순간 사라지는 보장이다. 반대로 「기록은 그때의 믿음이니 다시 잰다」는 인식론과 결정적 premise 펜스는 공개된 기업 사례보다 앞서 있다. 업계가 Copilot Memory의 인용 검증이나 OpenAI의 doc-gardening으로 같은 문제를 더 약한 형태로 풀고 있다는 점이 이를 뒷받침한다. 그러므로 팀 모듈화는 내용을 버리는 작업이 아니다. **직렬화를 소유권(작업별 파일), 리뷰 게이트(ADR PR), 스케줄(CI와 야간 premise)로 바꿔 끼우는 작업**이다.

남은 미지수는 실험으로만 갈린다. 「누적 ADR 175개 + 결정적 premise」가 팀에서 리뷰 병목을 감당할 만큼 가치를 내는지는 측정한 연구가 없다. 2026 실증들은 컨텍스트 전략이 정확도를 거의 못 움직인다고 말한다. 따라서 이 하네스의 진짜 가치는 「에이전트가 더 맞게 쓴다」가 아니라 **「틀린 기록이 조용히 살아남지 못한다」**에 있을 가능성이 크다. 팀 버전을 만든다면 측정 지표도 그쪽에 둬야 한다. 즉 지시 준수율이 아니라, **premise가 잡아낸 낡은 결정의 수와 그것이 발견되기까지 걸린 시간**을 재야 한다.
