# 협의 도서관 하네스 — 어떻게 동작하는가

> WES 구축 프로젝트에서 Claude Code를 쓸 때의 작업 구조 설계안이다. 근거 조사는 같은 폴더의 05~07에 있다.

## 한 줄 요약

**사람은 「키워드 + 내용」만 넣는다. 회의 내용이든 협의든 명세든 상관없다. AI는 원문을 그대로 보관한 뒤, 도서관에서 같은 키워드의 주제 문서를 찾아 더하거나 고치거나 새로 만든다. 개발을 시킬 때 「연계 키워드」를 적으면, 그 키워드의 주제 문서와 설계 정본만 자동으로 AI 앞에 놓인다. 바뀌었거나 기각된 내용도 표시와 사유를 달고 함께 놓인다.**

## 왜 필요한가

| 문제 | 그대로 두면 | 이 구조에서는 |
|---|---|---|
| 같은 주제가 협의록·명세서에 흩어진다 | AI가 여러 문서를 맞춰 읽어야 하고, 문서끼리 어긋난다 | 주제마다 「지금 유효한 상태」 한 장으로 모은다 |
| 고객 협의가 수시로 바뀐다 | AI가 옛 내용대로 구현한다 | 주제 문서마다 상태와 변경 이력을 두고, 개발할 때 함께 보인다 |
| 기각된 안을 AI가 다시 제안한다 | 회의에서 이미 끝난 논의가 반복된다 | 기각 사유가 개발 요청 때 자동으로 따라 붙는다 |
| 문서가 계속 쌓인다 | 전부 넣으면 비용이 커지고 AI가 혼동한다 | 요청 키워드와 맞는 문서만 넣고, 너무 많아지면 정리를 권한다 |
| AI가 잘못 정리할 수 있다 | 틀린 정리가 정답이 되고 대조할 근거가 없다 | 입력 원문을 그대로 보관하고, 모든 변경이 원문을 가리킨다 |

## 전체 흐름

```
 [사람] 키워드 + 내용 ──▶ [AI] ① 원문 보관 (sources/)
                                ② 같은 키워드의 주제 문서 탐색 (topics/)
                                ③ 더하기 / 고치기 / 새로 만들기 판단 → 반영 요약 보고
                                         │   (main 브랜치, PR로 사람 검토)
                                         ▼
 [사람] 개발 요청 + 연계 키워드 ──▶ [자동] 맞는 주제 문서 + 설계 정본(skill) 목록을 AI에게 강제 전달
                                         │
                                         ▼
                           [AI] 필요한 문서만 읽고 구현 (바뀜·기각된 안은 피함)

 [사람] 키워드 + 「거시 설계」 요청 ──▶ [AI] 도서관을 바탕으로 설계 → 설계 정본 skill로 등록
                                          (사람용 설계 문서는 필요할 때 정본에서 생성)
```

## 예시 1 — 입력과 반영

**사람이 입력하는 것** — 회의 내용, 협의, 명세 중 무엇이든 같은 형식이다

```
키워드: inbound, devanning
10/16 설비사B 회의. 디베이닝 머신 투입 전 입고 팔레트는 중량 검사를 거친다.
허용 오차 ±2kg. 오차 초과 팔레트는 재작업 라인으로 보낸다.
```

**AI가 하는 일**

1. **원문 보관** — `knowledge/sources/SRC-20261016-AB12.md`. 입력을 고치지 않고 그대로 저장한다.

```markdown
---
id: SRC-20261016-AB12
kind: 회의                 # 사용자가 붙인 분류는 여기에만 남긴다
keywords: [inbound, devanning]
received: 2026-10-16
by: 홍길동
---
10/16 설비사B 회의. 디베이닝 머신 투입 전 입고 팔레트는 중량 검사를 거친다.
허용 오차 ±2kg. 오차 초과 팔레트는 재작업 라인으로 보낸다.
```

2. **주제 문서 반영** — 도서관에서 `inbound`·`devanning` 키워드 문서를 찾는다. 「디베이닝 투입 전 검사」 주제가 없으면 새로 만든다. 있으면 그 문서에 더한다.

```markdown
---
id: KN-20261016-7K3Q
title: 디베이닝 투입 전 입고 팔레트 검사       # 대상·논점. 설비를 강제하지 않는다
keywords: [inbound, devanning]
status: active
supersedes: []
---
## 규칙
- 디베이닝 머신 투입 전 입고 팔레트는 중량 검사를 거친다.
- 허용 오차: ±2kg
- 오차 초과 팔레트 → 재작업 라인

## 열린 사항
- 재작업 후 재투입 경로는 정하지 않았다.

## 변경 이력
- 2026-10-16 최초 작성 ← SRC-20261016-AB12
```

3. **반영 요약 보고** — AI가 사람에게 무엇을 했는지 알린다. 사람은 이것과 PR diff를 보고 승인한다.

```
반영 요약 (SRC-20261016-AB12)
- 새로 만듦: KN-20261016-7K3Q 「디베이닝 투입 전 입고 팔레트 검사」
- 확인함·변경 없음: KN-20260930-P8LM 「입고 팔레트 라벨 판독」 (같은 키워드, 무관한 내용)
```

- 「키워드: …」 형태의 입력이 들어오면 hook이 그것을 알아보고 **기록 절차(skill)와 변경 판단 기준을 강제로 붙인다.** skill을 AI가 스스로 불러오는 확률(약 50~55%)에 맡기지 않기 위해서다.
- 기록·변경은 **main 브랜치에서만** 한다. 사람의 습관에 맡기지 않고 hook이 main이 아닌 브랜치의 `knowledge/` 쓰기를 거부하며, CI가 「도서관 변경 PR은 도서관만 담고 최신 main 기준인가」를 다시 검사한다.
- 원문(`sources/`)은 hook이 기존 파일 수정을 거부하고, CI도 원문 수정을 실패로 처리한다.
- 저장 직후 「작성 즉시 검사」가 필수 항목·키워드·상태 값·원문 링크를 검사해 AI에게 **알린다**(알림까지가 이 단계의 역할이다). 저장을 막는 것은 커밋·PR 검사다.

## 예시 2 — 내용이 바뀔 때

AI는 변경을 두 종류로 나눈다. 어느 쪽인지는 AI가 대화하며 판단하고, 애매하면 사용자에게 한 줄로 묻는다. 판단 기준은 기록 skill에 두고, 기록 입력 때 hook이 강제로 붙인다.

| 종류 | 기준 | AI가 하는 일 |
|---|---|---|
| 단순 변경 | 수치·조건 보정, 취지가 같은 보완, 오탈자 | 같은 주제 문서를 고치고 「## 변경 이력」에 한 줄 **덧붙인다**(날짜 · 전 → 후 · 사유 · 원문 ID). 이력 줄은 지우지 않는다 |
| 결정 변경 | 규칙 자체가 뒤집힘, 설계 방향 변경, 제안 기각 | **새 주제 문서**를 만들고 `supersedes`에 옛 문서를 적는다. 옛 문서는 손대지 않는다. 「바뀜」 상태는 hook·CI가 계산한다 |

**단순 변경** — 입력: `키워드: inbound, devanning / 10/20 설비사B: 중량 허용 오차를 ±3kg으로 완화`

```markdown
## 규칙
- 허용 오차: ±3kg

## 변경 이력
- 2026-10-16 최초 작성 ← SRC-20261016-AB12
- 2026-10-20 허용 오차 ±2kg → ±3kg · 사유: 설비사B 센서 사양 · ← SRC-20261020-Q9ZT
```

**결정 변경** — 입력: `키워드: inbound, devanning / 10/25 고객 요청: 중량 검사를 없애고 디베이닝 머신 자체 계량으로 대체`
→ 새 주제 문서 `KN-20261025-M2XD`(`supersedes: [KN-20261016-7K3Q]`)를 만든다. 옛 문서는 그대로 남고, 목록에는 「바뀜」으로 표시된다.

기각된 제안은 처음부터 `status: rejected` 주제 문서로 남긴다(예: 「디베이닝 라인 2열 병렬 투입」, 사유: 설치 공간 부족).

**문서 크기 규칙** — 한 주제 문서는 한 결정 영역만 다룬다. 본문(변경 이력 제외)이 4,000자를 넘으면 AI가 쪼개기를 제안하고, 6,000자를 넘으면 CI가 경고한다. 변경 이력이 20줄을 넘으면 새 문서로 통합하기를 제안한다. CI는 길이로 막지는 않는다.

## 예시 3 — 개발 요청

**사람이 입력하는 것**

```
1. 요청: 기능개발
2. 작업: 디베이닝 투입 전 입고 처리
3. 연계 키워드: inbound, devanning
4. 요구사항: 입고 팔레트를 디베이닝 머신에 넣기 전 판정 로직을 만들어줘.
```

**자동으로 AI에게 전달되는 목록** — 사람이 따로 할 일은 없다

```
요청 키워드(inbound, devanning)에 매핑된 문서. 관련 문서를 골라 읽어라. 목록 밖도 필요하면 검색한다.
바뀜·기각된 안은 다시 시도하지 않는다. 주제 문서와 설계 정본이 어긋나면 주제 문서를 따르고 설계 갱신을 제안한다.
설계 정본: skill design-inbound-flow (inbound, devanning)
- KN-20261025-M2XD · [유효] · 2/2 · 디베이닝 투입 판정 (머신 자체 계량) · KN-20261016-7K3Q를 대체함
- KN-20260930-P8LM · [유효] · 1/2 · 입고 팔레트 라벨 판독 · 변경 2회(최종 10-11)
- KN-20261016-7K3Q · [바뀜] · 2/2 · 디베이닝 투입 전 입고 팔레트 검사 · 변경 1회 · 대체됨→KN-20261025-M2XD
- KN-20261002-C7WB · [기각] · 2/2 · 디베이닝 라인 2열 병렬 투입 · 사유: 설치 공간 부족
- OPEN-20261026-H5RP · [미결] · 2/2 · 계량 실패 팔레트의 재투입 경로 · 고객 확인 대기
```

- 목록이 7,000자(상한 10,000자의 70%)를 넘으면 사람에게 경고가 뜬다(예: 「inbound 관련 유효 문서 112건 — 정리를 권합니다」). AI에게는 작업 뒤 겹치는 주제 문서의 통합을 제안하라는 지시가 붙는다. 통합 문서가 옛 문서 여럿을 대체하므로 이력은 남고 목록은 짧아진다.
- 9,000자를 넘으면 일치순 상위만 싣고 「나머지 N건 생략」을 표시한다. 1,000자는 머리말·상태 줄 몫으로 남긴다.
- **원문(sources/)은 목록에 넣지 않는다.** AI가 정리 내용을 의심할 때만 원문 ID로 찾아 읽는다.
- AI가 다른 AI(서브에이전트)에게 일을 나눠 줄 때도 같은 목록이 자동으로 따라간다.

**AI가 만든 결과물(발췌)** — 결정 지점마다 근거 또는 미결을 단다(근거 주석 규약)

```python
def judge_devanning_input(pallet):
    # 근거: KN-20261025-M2XD — 투입 전 중량 검사 없음, 머신 자체 계량 결과로 판정
    #       (KN-20261016-7K3Q 중량 검사 ±3kg은 바뀜, KN-20261002-C7WB 2열 병렬은 기각 — 쓰지 않음)
    result = devanning_machine.weigh(pallet)
    if result.ok:
        return Route.DEVANNING
    # 미결: OPEN-20261026-H5RP — 계량 실패 팔레트의 재투입 경로는 협의 전. 임시로 보류 위치로 보낸다
    return Route.HOLD
```

## 왜 본문이 아니라 목록을 강제하나

**강제로 넣는 것은 후보 목록(제목·상태·사유 한 줄)이고, 어떤 문서 본문을 읽을지는 AI가 고른다.** 실측에서 목록 56~69건 중 AI가 실제로 연 문서는 3~16건이었다(06). 즉 이 구조는 「역색인으로 후보를 찾고 최종 선택은 AI에게」이며, 업계와 다른 점은 **후보 목록을 꺼낼지 말지까지 AI에게 맡기지 않는다**는 것 하나다.

- **본문 전부를 강제로 넣는 방식은 쓰지 않는다.** 근거:
  - 최신 문장이 이미 들어와 있어도 낡은 경쟁 문장이 섞이면 정답률이 크게 떨어진다(한 모델에서 100%→44.6%, NeurIPS 2026).
  - 컨텍스트 파일을 넣어도 성공률은 대체로 오르지 않고 비용만 20% 넘게 늘었다(ETH 2026).
- **완전 자율 검색은 「AI가 아예 찾지 않는」 약점이 있다.**
  - skill 자동 활성화는 50~55%, hook 강제는 100%였다(개인 실측, 일화).
  - 이 프로젝트에서 특히 아픈 곳은 기각·번복 이력이다. AI는 어떤 안이 예전에 기각됐는지를 스스로 검색할 동기가 거의 없다. 모르는 것을 모르기 때문이다.
- **벤더가 정착시킨 형태가 「작은 목록은 항상, 본문은 필요할 때」다.**
  - Claude Code skill: 이름·설명 목록은 항상, 본문은 AI가 고를 때.
  - Claude Code `MEMORY.md`: 목차는 매 세션, 토픽 파일은 AI가 골라서.
  - OpenAI: 약 100줄 `AGENTS.md` 지도는 항상, `docs/`는 찾아서.
  - 이 구조는 그 형태에서 목록을 요청 키워드로 좁힌 것이다.

| 남는 위험 | 대응 |
|---|---|
| 합집합이라 1/2만 맞는 약한 후보가 목록을 채움 | 일치 개수 순 정렬, 7,000자 경고, 9,000자 절단 |
| AI가 목록을 「전부」라고 믿고 그 밖을 안 찾음 | 목록 머리말에 「목록 밖도 필요하면 검색한다」. 실측에서는 12회 중 11회 목록 밖 문서도 열었다 |
| 키워드 없는 요청은 목록이 아예 없음 | CLAUDE.md의 「키워드가 없으면 먼저 묻는다」 |

**판단을 바꿀 조건:** 운영하면서 한 요청의 목록이 늘 수백 건이라 상한에 계속 걸리면 목록 자체가 소음이 된다. 그때는 「건수와 상위 N건만 강제, 나머지는 AI가 검색」으로 강제 범위를 줄인다. hook 출력 규칙만 바꾸는 작은 변경이다.

## 「협의에 없는 결정」을 막는 구조

고객 협의가 근거인 개발에서 AI가 빈칸을 그럴듯하게 채우면, 나중에 「누가 정했나」를 추적할 수 없다. 이 하네스의 가장 중요한 원칙이고, 규칙 한 줄로 끝내지 않고 세 층으로 막는다.

| 층 | 장치 | 무엇을 잡나 | 성격 |
|---|---|---|---|
| ① 표시 의무 | **근거 주석 규약**: 코드의 결정 지점마다 `근거: KN-…` 또는 `미결: OPEN-…` | 근거를 단 결정을 문서와 기계적으로 잇는다 | 규약 (코드를 만질 때 경로 규칙으로 로드) |
| ② 기계 검사 | CI가 주석의 ID를 도서관과 대조한다. ID가 없으면 실패. **인용한 문서가 「바뀜·기각」이 되면 경고** | 협의가 번복됐을 때 그 협의에 기대 구현된 코드를 자동으로 찾는다 | 결정적 |
| ③ 독립 검증 | 코드를 바꾼 작업이 끝날 때 별도 검증자가 diff와 주입 목록을 대조해, 근거·미결 표시가 없는 결정을 찾아 한 번 되돌려 보낸다 | ①을 빠뜨린 결정 (기계로는 「표시 없는 결정」을 볼 수 없다) | AI 판단 |

- **미결도 도서관 문서다.** 협의에 없는 결정은 `status: open` 문서(`OPEN-…`)로 등록하고, 개발 요청 목록에 `[미결]`로 표시한다. 사용자가 답하면 새 주제 문서가 미결 문서를 대체한다.
- **②가 번복 영향 분석을 대신한다.** 협의 문서가 「바뀜」이 되는 순간, 그 문서를 근거로 단 코드가 CI 경고로 드러난다.
- **근거:** Anthropic은 자기 결과를 스스로 평가하면 후하게 평가하므로 별도 평가자를 두라고 권한다(2026-03). Spotify는 PR 전에 LLM 판정자가 diff를 원 작업과 대조해 세션의 약 1/4을 거부하고 그중 절반을 에이전트가 스스로 고친다(1차). 우리 시험(06)에서도 AI는 협의에 없는 처리를 정할 때 12회 모두 「협의 필요」 주석을 남겼다(약한 근거).
- **비용·한계:** ③은 코드를 바꾼 작업마다 AI 호출이 한 번 더 든다. 도구까지 쓰는 검증 hook 형식은 공식 문서상 실험 기능이고, 되돌려 보내기는 연속 8회에서 자동 해제된다. ③을 로컬(작업 종료 hook)에 둘지 PR 검사에 둘지는 「정해야 할 것」에 남겼다.

## 예시 4 — 설계 정본

도서관이 충분히 쌓인 뒤 사람이 「키워드 + 거시 설계 요청」을 넣는다(예: `키워드: inbound, devanning / 입고~디베이닝 흐름 전체 설계`). AI는 해당 키워드의 주제 문서를 바탕으로 설계하고, 결과를 **설계 정본 skill**로 등록한다.

```
.claude/skills/design-inbound-flow/
├─ SKILL.md              # 설명 + keywords: [inbound, devanning] — 개발 요청 목록에 자동으로 실린다
└─ references/
   ├─ constraints.md     # 반드시 지킬 제약 (근거 주제 문서 ID 포함)
   ├─ states.md          # 상태·전이 표
   └─ interfaces.md      # 설비·시스템 인터페이스
```

- **AI용 구조화 형태 하나를 정본으로 둔다.** 제약·상태표·인터페이스·금지 사항으로 구성한다.
- skill은 원래 AI가 스스로 불러올 때만 읽힌다(자동 활성화 약 50~55%, 개인 실측). 그래서 설계 정본에도 키워드를 달아 **개발 요청 목록에 강제로 실리게** 한다.
- 사람용 설계 문서가 필요하면 정본에서 **생성**만 하고 손으로 고치지 않는다. 두 벌을 따로 관리하면 반드시 어긋난다.

| 낡음 경고 | 세션을 시작할 때 | 「main에 있고 이 브랜치엔 없는 도서관 변경 N건 — main을 먼저 반영하세요」 |
| 작성 즉시 검사 | AI가 문서를 저장한 직후 | 양식·키워드·원문 링크 위반을 AI에게 바로 알린다 |
| 근거 검증 | 코드를 바꾼 작업이 끝날 때 | 근거·미결 표시 없는 결정을 찾아 한 번 되돌려 보낸다(위치는 미정) |

Windows에서는 PowerShell로 쓴 파일에 `Write`·`Edit` 검사가 뜨지 않으므로(C12), 거부 장치의 최종 보증은 커밋·PR 검사다.

**별도의 색인 파일은 두지 않는다.** 요청이 올 때마다 문서 머리말을 바로 훑어 목록을 만든다. 3,000장에서도 0.1초 아래였다(실측). 따로 관리할 색인이 없으니 색인이 낡거나 팀원끼리 충돌할 일이 없다.

## 품질을 지키는 다섯 가지 원칙

1. **키워드는 정해진 목록에서만.** 「겐트리/갠트리/gantry」처럼 표기가 갈리면 검색에서 빠진다. 새 키워드는 키워드 파일을 하나 추가하는 PR로만 늘린다.
2. **원문은 지우지도 고치지도 않는다.** 주제 문서는 AI의 해석이다. 해석이 틀렸을 때 대조할 근거가 원문이다.
3. **이력은 지우지 않는다.** 단순 변경은 「변경 이력」에 덧붙이고, 결정 변경은 새 문서가 옛 문서를 대체한다.
4. **협의에 없는 결정은 지어내지 않는다.** 결정 지점마다 근거나 미결을 달고, 기계 검사와 독립 검증으로 확인한다(위 「협의에 없는 결정」을 막는 구조).
5. **검사는 저장·커밋·PR 세 번.** 사례 조사에서 실제로 난 사고 둘을 미리 막기 위해서다. 하나는 키워드가 엉뚱한 값으로 몰려 문서가 검색에서 사라진 일이고, 다른 하나는 깨진 문서가 조용히 빠진 일이다.

## CLAUDE.md 구성

공식 작성 가이드(code.claude.com best-practices·memory)를 따른다.
- 200줄 미만, 제목과 글머리표로 묶는다.
- 줄마다 「지우면 Claude가 실수하는가」를 묻는다.
- 넣을 것: 추측 못 하는 명령어, 기본값과 다른 규칙, 시험 방법, 저장소 규약, 개발 환경 특이점, 드러나지 않는 함정.
- 뺄 것: 코드로 알 수 있는 것, 자주 바뀌는 정보, 긴 설명.
- `IMPORTANT`는 한 줄에만 쓴다.
- 가끔 필요한 지식은 skill로, 반드시 일어나야 하는 것은 hook으로 둔다.

**자동으로 들어가는 내용은 CLAUDE.md에 넣지 않는다.**

| 내용 | 둘 곳 |
|---|---|
| 문서 목록, 바뀜·기각 재시도 금지, 「주제 문서 > 설계 정본」 | 개발 요청 hook의 목록 머리말 |
| 정본에 없는 키워드 경고, 목록 상한 경고, 낡음 경고 | hook |
| 기록은 main에서, 원문 불변 | hook 거부 + CI 검사 |
| 기록 절차, 변경 종류 판단 기준, 문서 길이 규칙 | 기록 skill (기록 입력 때 hook이 강제로 붙임) |
| 근거 주석 형식 | 경로 규칙 `.claude/rules/code.md` |

**골격 (약 40줄 목표)**

```markdown
# 명령어
- 빌드: (확정 후)   - 테스트: (확정 후, 단일 테스트 실행법 포함)   - 실행: (확정 후)

# 코드 규칙
- (팀 규약 중 언어 기본값과 다른 것만)

# 근거와 미결
- IMPORTANT: 협의 문서에 없는 동작을 정하지 않는다. 필요하면 미결 문서로 등록하고 사용자에게 묻는다. 임시 처리에는 `미결: OPEN-…`를 단다.
- 개발 요청에 연계 키워드가 없으면 구현 전에 키워드를 묻는다.

# 저장소 규약
- 도서관(knowledge/) 변경과 코드 변경은 같은 PR에 섞지 않는다.
- 브랜치 이름: (팀 규약)   - 커밋 메시지: (팀 규약)

# 개발 환경
- Windows: hook과 스크립트는 팀 표준 Python으로 실행한다 (경로: 확정 후)

# 압축할 때
- 이번 작업에서 근거로 쓴 문서 ID 목록과 미결 사항 목록을 보존한다.
```

- `IMPORTANT` 한 줄은 개발 요청 hook이 돌지 않는 대화(키워드 없이 바로 코딩 요청)에서도 걸려야 해서 CLAUDE.md에 둔다.
- 「키워드가 없으면 묻는다」는 hook이 목록을 못 만드는 공백을 메운다.
- 압축 시 보존 지시는 공식 가이드의 방법이다. 목록은 압축 뒤 hook이 다시 넣으므로, 대화 중에 생긴 정보만 보존을 지시한다.

## 근거 — 이 구조를 쓰는 하네스들

하네스에서 역색인(키워드·태그 → 문서)은 널리 쓰인다. 다만 대부분은 **역색인으로 후보를 찾고 최종 선택은 AI 판단에 맡긴다.** 이 구조처럼 **요청이 올 때 키워드로 정확히 맞춰 강제로 붙이는** 방식은 소수다. 대표 큐레이션 목록(awesome-claude-code, ★55,777)의 257개 항목 중 1건이었다(설명문 기준 분류). 그래서 근거를 층별로 제시한다. 수치는 2026-10-16 GitHub 실측이다.

| 이 구조의 층 | 같은 방식을 쓰는 하네스 | 규모·근거 |
|---|---|---|
| ① 마크다운 + 머리말 메타데이터 + 정해진 키워드 목록 | Every **compound-engineering**: 문서마다 머리말, 닫힌 값 목록과 「기존 값 재사용」 규칙, 동의어 접기 | ★25,543 · 사내 운영 · 1차 |
| ② 역색인으로 문서 찾기 | **claude-mem**: 자동 수집 내용을 SQLite FTS5(역색인)에 저장·검색 · **compound-engineering**: 저장 색인 없이 매번 머리말을 grep(이 구조와 같음) · **LinkedIn CAPT**: 플레이북 500+개를 태그로 검색 | ★101,057 · ★25,543 · 엔지니어 1,000+명(2026-01) · 1차 |
| ③ AI 판단이 아닌 정확 매칭 | **diet103 claude-code-infrastructure-showcase**: 저자가 LLM 분류를 시험한 결과 무관한 요청의 약 1/3에서 오경보가 나서, 「반드시 붙어야 하는 경로는 규칙 매칭만」이라고 결론 · 개인 실측: 자동 활성화 50~55% 대 hook 강제 100% · 우리 시험: 관련 문서 누락 0/12 | ★10,033(저자 자가보고) · 일화 · 06 |
| ④ 요청 시점 hook 강제 주입 | **diet103**: 키워드·의도 패턴 표 → `UserPromptSubmit` hook으로 주입 · remindcc: 머리말 트리거를 매번 스캔 · Claude Code 공식 문서가 주입과 서브에이전트 재주입(`SubagentStart`)을 지원 | ★10,033 · ★2 · 1차 |
| ⑤ 이력(바뀜·기각) 표시 | 하네스 선례 없음. compound-engineering은 낡은 문서를 지움 | **근거는 우리 시험뿐**: 기각안 재시도 이력 있음 0/6, 없음 1/6 |
| ⑥ 작성 품질 검증 | compound-engineering이 겪은 사고: 키워드가 한 값으로 몰려 35개 문서가 검색에서 빠짐, 깨진 YAML이 grep에 가려짐 → 2026-10 CI 감사 도입(첫 실행 오류 5·경고 23) | 1차 |

**요약:** 이 구조는 하네스에서 쓰이는 두 방식을 같은 문서 저장소 위에서 합친 것이다.
- 지식을 쌓는 방식은 compound-engineering과 같다: 머리말, 정해진 키워드, 매번 스캔.
- 붙이는 방식은 diet103과 같다: 요청 hook, 정확 매칭.

두 층은 「무엇을 쌓나」와 「언제 붙이나」로 역할이 갈리고 정본도 하나다. 그래서 섞어 생기는 충돌은 작다고 본다(추론). **이 조합 그대로 운영한 공개 사례는 없고, 이력 층의 근거는 우리 시험뿐이다.**

**우리 시험** (Claude Code, 합성 문서 200장, 06): 관련 문서 누락 0/12. 기각안 재시도는 이력을 넣으면 0/6, 빼면 1/6. 서브에이전트 전달은 장치가 없으면 0/2, `SubagentStart` 장치를 넣으면 2/2. 문서 3,000장도 스캔 0.1초 미만(07). **한계:** 문서가 합성이고 횟수가 적다. 방향을 본 것이지 효과를 증명한 것은 아니다.

## Windows 실행 환경 위험

하네스는 Windows PC에서 돈다. 아래는 공식 문서와 이슈를 근거로 한 것이고, **Windows 실기에서는 아직 재지 않았다.** diet103도 일반 Windows는 지원하지 않는다(WSL2 필요). Windows에서 hook 하네스를 돌린 선례가 적다.

| 결함 | 결과 | 대응 |

| C9 Git Bash가 없으면 hook이 PowerShell로 돌고 `$CLAUDE_PROJECT_DIR`가 빈 값 → 스크립트 경로 없음 → 종료코드 2 | **모든 요청이 막힐 수 있음**(추론) | 셸 없이 실행하는 등록 형식(exec form)(B11) |

## 누적 수정 사항과 결함

결정을 한꺼번에 받기 전까지 쌓아 둔 목록이다. 원본은 작성 기계의 `~/dev/harness-kit/review/누적-수정사항과-결함.md`.

**결정된 것 (2026-10-16)**
- 도서관 구조: 문서 종류별 폴더 폐지 → `topics/`(주제 문서, 주입 대상) + `sources/`(입력 원문, 주입 안 함) + `vocabulary/`
- 입력: 「키워드 + 내용」 하나. AI가 원문 보관 후 주제 문서에 더하기·고치기·새로 만들기를 판단하고 반영 요약을 보고
- 변경 종류: 단순 변경은 같은 문서 + 변경 이력(원문 ID), 결정 변경은 새 문서 대체. 판단은 AI, 기준은 CLAUDE.md
- 설계 정본: 도서관 완성 후 「키워드 + 거시 설계」 → 키워드가 달린 skill로 등록, 개발 요청 목록에 강제로 실림. 사람용 문서는 정본에서 생성
- 목록 상한: 70%에서 경고 + 통합 정리 제안, 100% 초과 시 일치순 상위만
- 브랜치 낡음: 도서관은 main 기준, 기록은 main에서만, 세션 시작 낡음 경고
- 문서 ID: `유형-날짜-무작위4자`, 제목·ID에 설비 강제 안 함, 키워드에 설비 외 개념 포함, 요청 양식 「연계 키워드」
- Windows 실기 시험은 나중에, Windows 결함은 누적만
- 주제 문서와 설계 정본이 어긋나면 주제 문서를 따른다 · 기록은 main에서(hook 거부 + CI로 강제)
- 「협의에 없는 결정은 지어내지 않는다」를 핵심 원칙으로 — 근거 주석 · CI 대조 · 독립 검증 · 미결 문서
- 작성 즉시 검사는 알림까지 · 길이: 목록 7,000자 경고/9,000자 절단, 주제 문서 본문 4,000자 쪼개기 제안/6,000자 CI 경고, 변경 이력 20줄 통합 제안
- CLAUDE.md는 공식 가이드 기준 약 40줄, 자동 주입 내용 중복 금지, 변경 판단 기준은 기록 skill로
