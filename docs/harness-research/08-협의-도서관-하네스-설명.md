# 협의 도서관 하네스 — 어떻게 동작하는가

> WES 구축 프로젝트에서 Claude Code를 쓸 때의 작업 구조 설계안이다. 근거 조사는 같은 폴더의 05~07에 있다.

## 한 줄 요약

**사람은 협의 내용을 짧게 말하고, AI가 정해진 양식으로 문서를 써서 도서관처럼 쌓는다. 개발을 시킬 때 「연계설비」를 적으면, 그 설비와 관련된 협의 문서만 자동으로 AI 앞에 놓인다. 이미 바뀌었거나 기각된 협의도 「바뀜·기각됨」 표시와 사유를 달고 함께 놓인다.**

## 왜 필요한가

| 문제 | 그대로 두면 | 이 구조에서는 |
|---|---|---|
| 고객 협의가 수시로 바뀐다 | AI가 옛 협의대로 구현한다 | 문서마다 「유효 / 바뀜 / 기각」 상태를 붙이고, 개발할 때 그 상태가 함께 보인다 |
| 기각된 안을 AI가 다시 제안한다 | 회의에서 이미 끝난 논의가 반복된다 | 기각 사유가 개발 요청 때 자동으로 따라 붙는다 |
| 협의 문서가 계속 쌓인다 | 전부 넣으면 비용이 커지고 AI가 혼동한다 | 요청에 적은 설비 키워드와 맞는 문서만 넣는다 |
| 문서를 사람마다 다르게 쓴다 | 같은 설비를 다른 이름으로 불러 검색에서 빠진다 | 양식과 키워드 목록을 고정하고, 어긋나면 저장·커밋 단계에서 막는다 |

## 전체 흐름

```
 [사람] 협의 내용 입력 ──▶ [AI] 양식대로 문서 작성 ──▶ [도서관] knowledge/ 에 누적
                                                           │  (문서마다 설비 키워드·상태 표시)
                                                           ▼
 [사람] 개발 요청 + 연계설비 ──▶ [자동] 키워드가 맞는 문서 목록을 AI에게 강제로 전달
                                                           │
                                                           ▼
                                   [AI] 필요한 문서만 읽고 구현 (바뀜·기각된 안은 피함)
```

## 예시 1 — 협의 기록

**사람이 입력하는 것**

```
협의 기록 / 키워드: asrs, outbound
ASRS 출고 끝난 공팔레트는 출고 스테이션 3번 버퍼로 돌려보내기로 함. 버퍼는 12매까지.
(설비사A 10/16 정기회의)
```

**AI가 만들어 저장하는 문서** — `knowledge/agreements/AGR-20261016-01.md`

```markdown
---
id: AGR-20261016-01
type: agreement
title: ASRS 출고 후 공팔레트 반송 위치
keywords: [asrs, outbound]
status: active
supersedes: []
superseded_by: []
decided: 2026-10-16
source: 설비사A 정기회의
---
## 결정
ASRS 출고 피킹이 끝난 공팔레트는 출고 스테이션 3번 버퍼(STN-03-BUF)로 반송한다.

## 수치
- 버퍼 용량: 공팔레트 12매

## 열린 사항
- 버퍼가 가득 찼을 때의 처리는 정하지 않았다.
```

저장되는 순간 검사가 돈다. 양식이 빠졌거나, 키워드가 정해진 목록(`vocabulary.yml`)에 없으면 AI에게 바로 고치라고 알린다. 사람은 이 문서를 PR에서 검토만 한다.

## 예시 2 — 협의 변경

**사람이 입력하는 것**

```
협의 변경 / 키워드: asrs, outbound
공팔레트 반송처를 STN-03에서 STN-05로 바꿈. 랙 레이아웃 변경 때문. (설비사A 10/20)
```

**AI가 하는 일 — 문서 두 개를 손본다**

1. 새 문서 `AGR-20261020-02`를 만든다. 반송처는 STN-05이고, `supersedes: [AGR-20261016-01]`을 단다.
2. 옛 문서 `AGR-20261016-01`은 **지우지 않는다.** 상태만 바꾼다.

```markdown
status: superseded
superseded_by: [AGR-20261020-02]
reason: 2026-10-20 랙 레이아웃 변경으로 반송처를 STN-05로 변경
```

> **수정 검토 중(B1):** 옛 문서를 고치지 않는 방식으로 바꾸는 안이 있다. 새 문서에만 `supersedes`를 적고, 「바뀜」 상태와 역방향 링크는 hook·CI가 계산한다. 이렇게 하면 협의 변경이 「파일 추가」 한 번으로 끝나서, 팀원끼리 같은 문서를 동시에 고치다 생기는 충돌이 사라진다. 아래 「누적 수정 사항」 참조.

기각된 제안도 같은 방식으로 남는다. 예를 들어 「겐트리 3단 적층」 문서는 `status: rejected`, `reason: 그리퍼 하중 제한`으로 남는다.

## 예시 3 — 개발 요청

**사람이 입력하는 것**

```
1. 요청: 기능개발
2. 작업: 출고 공팔레트 처리
3. 연계설비: asrs, gantry
4. 요구사항: 공팔레트의 목적지와 적층 단수를 정하는 함수를 만들고, 버퍼가 찼을 때 처리도 넣어줘.
```

**자동으로 AI에게 전달되는 목록** — 사람이 따로 할 일은 없다

```
요청 키워드(asrs, gantry)에 매핑된 문서. 관련 문서를 읽어라. 바뀜·기각된 안은 다시 시도하지 않는다.
- AGR-20261020-02 · [유효] · ASRS 공팔레트 반송 위치 (STN-05) · AGR-20261016-01을 대체함
- AGR-20260815-03 · [유효] · 겐트리 공팔레트 회수 규칙 (2단까지 적층)
- DES-0007        · [유효] · 출고 공팔레트 흐름 설계
- AGR-20261016-01 · [바뀜] · ASRS 공팔레트 반송 위치 (STN-03) · 사유: 랙 레이아웃 변경
- AGR-20260820-04 · [기각] · 겐트리 3단 적층 · 사유: 그리퍼 하중 제한
```

**AI가 만든 결과물(발췌)** — 근거 협의와 피한 안을 코드에 남긴다

```python
"""출고 공팔레트 라우팅.

  AGR-20261016-01(STN-03)은 랙 레이아웃 변경으로 바뀌었으므로 쓰지 않는다.
- AGR-20260815-03 (유효): 겐트리는 2단까지 적층 후 반송.
  AGR-20260820-04(3단 적층)는 그리퍼 하중 제한으로 기각되었으므로 쓰지 않는다.
"""
MAX_STACK = {"asrs": 1, "gantry": 2}

def route_empty_pallet(source, current_buffer_count):
    ...
    # 버퍼 만재 처리는 협의에 없다. 기각·변경된 안을 우회로로 쓰지 않고
    # 발생 설비에서 대기시킨 뒤 알람을 올린다. → 다음 협의에서 확정 필요
```

AI가 다른 AI(서브에이전트)에게 일을 나눠 줄 때도 같은 목록이 자동으로 따라간다.

## 폴더 구조

```
wes-project/
├─ CLAUDE.md                  # AI용 짧은 안내: 요청 양식, 협의는 기록 skill로 남긴다
├─ knowledge/                 # 문서 도서관 (작성은 AI, 검토는 사람)
│  ├─ vocabulary.yml          # 설비·구간 키워드 목록. 키워드는 여기서만 고른다
│  ├─ templates/              # 협의록·명세·설계 양식
│  ├─ agreements/             # 협의록
│  ├─ specs/                  # 요구사항 명세
│  └─ designs/                # 설계 정본
├─ .claude/
│  ├─ hooks/                  # 자동 장치 (아래 표)
│  └─ skills/
│     ├─ record-agreement/    # 협의 기록 절차
│     ├─ revise-agreement/    # 협의 변경·기각 절차
│     └─ equip-asrs/ …        # 설비별 기본 정보 (사양, 인터페이스)
├─ scripts/kw-check.py        # 도서관 전체 검사
└─ src/                       # WES 코드
```

| 자동 장치 | 언제 | 하는 일 |
|---|---|---|
| 문서 목록 전달 | 사람이 요청을 보낼 때 | 「연계설비」 키워드와 맞는 문서 목록을 AI에게 넣는다 |
| 서브에이전트 전달 | AI가 일을 나눠 줄 때 | 같은 목록을 서브에이전트에게도 넣는다 |
| 대화 압축 후 재전달 | 대화가 길어져 압축될 때 | 목록을 다시 넣는다 |
| 작성 즉시 검사 | AI가 문서를 저장할 때 | 양식·키워드 위반을 바로 알린다 |
| 커밋·PR 검사 | 커밋할 때, PR을 올릴 때 | 위반 문서가 있으면 커밋·머지를 막는다 |

**별도의 색인 파일은 두지 않는다.** 요청이 올 때마다 문서 머리말을 바로 훑어 목록을 만든다. 3,000장에서도 0.1초 아래였다(실측). 따로 관리할 색인이 없으니 색인이 낡거나 팀원끼리 충돌할 일이 없다.

## 품질을 지키는 세 가지 원칙

1. **키워드는 정해진 목록에서만.** 「겐트리/갠트리/gantry」처럼 표기가 갈리면 검색에서 빠진다. 새 키워드는 목록 파일을 고치는 PR로만 추가한다.
2. **문서는 지우지 않고 상태를 바꾼다.** 바뀐 협의와 기각된 협의도 남아야 AI가 같은 실수를 반복하지 않는다.
3. **검사는 저장·커밋·PR 세 번.** 사례 조사에서 실제로 난 사고 둘을 미리 막기 위해서다. 하나는 키워드가 엉뚱한 값으로 몰려 문서가 검색에서 사라진 일이고, 다른 하나는 깨진 문서가 조용히 빠진 일이다.

## 근거 — 이 구조를 쓰는 하네스들

하네스에서 역색인(키워드·태그 → 문서)은 널리 쓰인다. 다만 대부분은 **역색인으로 후보를 찾고 최종 선택은 AI 판단에 맡긴다.** 이 구조처럼 **요청이 올 때 키워드로 정확히 맞춰 강제로 붙이는** 방식은 소수다. 대표 큐레이션 목록(awesome-claude-code, ★55,777)의 257개 항목 중 1건이었다(설명문 기준 분류). 그래서 근거를 층별로 제시한다. 수치는 2026-10-16 GitHub 실측이다.

| 이 구조의 층 | 같은 방식을 쓰는 하네스 | 규모·근거 |
|---|---|---|
| ① 마크다운 + 머리말 메타데이터 + 정해진 키워드 목록 | Every **compound-engineering**: 문서마다 머리말, 닫힌 값 목록과 「기존 값 재사용」 규칙, 동의어 접기 | ★25,543 · 사내 운영 · 1차 |
| ② 역색인으로 문서 찾기 | **claude-mem**: 자동 수집 내용을 SQLite FTS5(역색인)에 저장·검색 · **compound-engineering**: 저장 색인 없이 매번 머리말을 grep(이 구조와 같음) · **LinkedIn CAPT**: 플레이북 500+개를 태그로 검색 | ★101,057 · ★25,543 · 엔지니어 1,000+명(2026-01) · 1차 |
| ③ AI 판단이 아닌 정확 매칭 | **diet103 claude-code-infrastructure-showcase**: 저자가 LLM 분류를 시험한 결과 무관한 요청의 약 1/3에서 오경보가 나서, 「반드시 붙어야 하는 경로는 규칙 매칭만」이라고 결론 · 개인 실측: 자동 활성화 50~55% 대 hook 강제 100% · 우리 시험: 관련 문서 누락 0/12 | ★10,033(저자 자가보고) · 일화 · 06 |
| ④ 요청 시점 hook 강제 주입 | **diet103**: 키워드·의도 패턴 표 → `UserPromptSubmit` hook으로 주입 · remindcc: 머리말 트리거를 매번 스캔 · Claude Code 공식 문서가 주입과 서브에이전트 재주입(`SubagentStart`)을 지원 | ★10,033 · ★2 · 1차 |
| ⑤ 이력(바뀜·기각) 표시 | 하네스 선례 없음. compound-engineering은 낡은 문서를 지움 | **근거는 우리 시험뿐**: 기각안 재시도 이력 있음 0/6, 없음 1/6 |
| ⑥ 작성 품질 검증 | compound-engineering이 겪은 사고: 키워드가 한 값으로 몰려 35개 문서가 검색에서 빠짐, 깨진 YAML이 grep에 가려짐 → 2026-10 CI 감사 도입(첫 실행 오류 5·경고 23) | 1차 |

**요약:** 이 구조는 하네스에서 쓰이는 두 방식을 같은 문서 저장소 위에서 합친 것이다.
- 지식을 쌓는 방식은 compound-engineering과 같다: 머리말, 정해진 키워드, 매번 스캔.
- 붙이는 방식은 diet103과 같다: 요청 hook, 정확 매칭.

두 층은 「무엇을 쌓나」와 「언제 붙이나」로 역할이 갈리고 정본도 하나다. 그래서 섞어 생기는 충돌은 작다고 본다(추론). **이 조합 그대로 운영한 공개 사례는 없고, 이력 층의 근거는 우리 시험뿐이다.**

**우리 시험** (Claude Code, 합성 문서 200장, 06): 관련 문서 누락 0/12. 기각안 재시도는 이력을 넣으면 0/6, 빼면 1/6. 서브에이전트 전달은 장치가 없으면 0/2, `SubagentStart` 장치를 넣으면 2/2. 문서 3,000장도 스캔 0.1초 미만(07). **한계:** 문서가 합성이고 횟수가 적다. 방향을 본 것이지 효과를 증명한 것은 아니다.

## 팀 협업 시 문제와 대응

| 문제 | 무엇이 일어나나 | 근거 | 대응 | 규모 |
|---|---|---|---|---|
| 같은 문서 동시 수정 | 두 사람이 같은 협의를 동시에 변경하면 옛 문서에서 충돌 | 공유 진행 파일: 브랜치 8개 중 7개 충돌(swarm #33) · 에이전트 지시 파일: 열린 PR의 40%가 같은 파일 수정(cabros-bot #1339) | 옛 문서를 고치지 않음(B1). 「유효한 후속 문서가 둘」은 CI가 잡음 | 소변경 |
| 문서 ID 충돌 | 순번을 브랜치마다 따로 매기면 겹침 | GitHub Spec Kit에서 같은 결함이 여러 번 보고됨(#1066·#3054·#4270·#4418). 번호 예약이 원자적이지 않아 문서를 덮어쓴 사례 포함 | 순번 금지. 이슈·PR 번호나 날짜-설비-주제 + CI 중복 검사(B3) | 소변경 |

## 누적 수정 사항과 결함

결정을 한꺼번에 받기 전까지 쌓아 둔 목록이다.

**수정 사항**
- B1 옛 문서를 고치지 않음, 「바뀜」·역링크는 계산 · B2 기각은 처음부터 `rejected` 기록 문서 · B3 순번 ID 금지 · B4 키워드 파일 분리
- B5 hook 상태 줄 · B6 `cwd` 기준 · B7 CODEOWNERS · B8 일부러 틀린 문서로 CI 시험 · B9 `source` 중복 검사 · B10 hook·검증기·CI가 같은 파서
- B11 exec form 등록 · B12 UTF-8 고정 · B13 종료코드 규약(예외는 1, 차단만 2) · B14 표준 Python · B15 경로 정규화 · B16 LF 고정·대소문자 검사 · B17 Windows 조건 CI 회귀 시험 · B18 「걸리는 문서 0건인 키워드」와 「어떤 키워드에도 안 걸리는 문서」 집계

**찾은 결함**
- C1 시제품 파서가 블록 목록(`- asrs`)을 키워드 0개로 빠뜨림 · C2 서브에이전트 hook이 다른 세션 목록을 읽을 수 있음 · C3 스크립트 없으면 요청 차단(#92168)
- C4 주입 상한 10,000자(약 1,000장부터 초과) · C5 브랜치 낡음 · C6 작성 즉시 검사는 알림뿐 · C7 부분 변경 관계 없음
- C8~C14 Windows(위 표)

## 정해야 할 것

1. **목록이 너무 길 때의 규칙.** 한 번에 넣을 수 있는 분량은 약 10,000자, 문서 약 130건이다. 1,000장 규모부터 넘는다. 「관련도 높은 순 상위 N건만」과 「바뀜·기각 문서는 한 줄로 압축」 중 고르거나 둘 다 쓴다.
2. **작성 즉시 검사의 강도.** 알림으로 둘지, 저장을 막을지. Windows에서는 이 검사가 약하므로(C12) 커밋·PR 단계가 실질 방어선이다.
3. **브랜치 낡음 대응.** hook이 main을 함께 읽게 할지(소변경), 협의 저장소를 분리할지(구조 변경).
4. **부분 변경 관계 도입 여부.** 예: 「반송처만 바뀌고 버퍼 용량은 유지」.
5. **문서 ID 방식.** 이슈·PR 번호로 할지, 날짜-설비-주제로 할지.
6. **Windows 실기 시험.** C9~C14 재현과 대응 확인을 온보딩 전에 팀 PC 한 대에서 할지.
