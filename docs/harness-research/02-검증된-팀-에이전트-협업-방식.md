# 검증된 팀 협업은 파일이 아니라 작업 표면에 산다

2026-05 이후 실제 팀 프로젝트에서 1차 자료와 수치로 확인되는 AI 에이전트 협업 방식은 하나의 뼈대로 모인다. **사람이 이미 쓰는 표면(Slack 멘션, 이슈 배정, 웹훅)에서 작업 하나를 던지면, 격리된 세션 하나가 그것을 맡아 결정론 검증 → LLM 리뷰·판정 → 사람 최종 승인을 거쳐 PR 하나로 끝난다.** 작업 상태와 인계는 그 작업의 스레드, 세션 DB, 이슈 코멘트, PR 설명에 남는다. 팀이 공유하는 지식은 저장소에 커밋한 지시 파일 하나와 skills·plugin이다. 이 지시 파일은 정본 하나에 도구별 포인터를 두는 형태이고, 사람 maintainer 여럿이 고친다. 이 형태를 1차 자료로 보인 곳은 Shopify, Spotify, Cloudflare, Vercel, Uber이고, Stripe와 Ramp는 2026-05 이전 1차 자료다. 공개 저장소 실측(next.js, airflow, ruff, bun, pytorch 등)도 같은 형태를 보여 준다. 다만 **이 「검증」의 수치는 거의 전부 처리량**, 즉 머지 PR 수나 비중이다. revert율이나 인시던트율 같은 품질 지표를 낸 팀 1차 자료는 하나도 찾지 못했다. Microsoft 연구는 스스로 "a merged PR is not the same as the value it delivers"라고 적었다. 반대로 **팀 증거가 전혀 없는 것**도 분명하다. 프로젝트 전역 progress 파일을 팀이 `main`에서 공유하는 방식, 에이전트가 쓴 ADR 코퍼스를 팀이 운영하는 방식, BMAD·Agent OS·Task Master·Tessl 같은 이름 붙은 방법론의 팀 결과가 그렇다. 다인 OSS의 지시 파일 12개를 검사했더니 계획·진행·ADR을 가리키는 문장이 0건이었다. Rust는 지시 파일이 기존 정책을 넘는 새 결정을 만들지 못하게 명문화했다. 따라서 평가 대상 하네스의 두 축(214KB 전역 progress.md, 에이전트 작성 ADR 173개)은 **팀 관점에서 「검증된 관행보다 앞섰다」기보다 「검증된 관행과 반대 방향에 있다」.** 실행 가능한 `premise` 펜스와 계획 단계 독립 반증만이 검증된 관행에 대응물이 없는 진짜 선행 요소다. 팀용 모듈의 기본형은 검증된 요소만으로 짤 수 있고, 하네스 고유 요소는 「미검증」 표시를 단 선택 계층으로 얹어야 한다.

> **증거 등급과 표기.** 모든 주장에 등급을 단다. **[1차+수치]**는 실천 팀 자신의 글·발표·저장소·연구 원문이 규모나 결과 수치를 낸 것이다. **[1차·수치 없음]**은 1차 자료가 기제만 서술한 것이고, **[2차]**는 언론·팟캐스트·요약을 거친 것이다. **[저자주장·벤더]**는 측정 방법이 없는 자기 주장이나 벤더가 쓴 고객 사례이고, **[없음]**은 팀 증거를 찾지 못한 것이다. 노트의 신뢰도 라벨도 그대로 둔다. **[미검증]**은 원문을 열지 못했거나 스니펫만 본 것이다. **[기초·이전]**은 2026-05 이전 자료로, 사용자가 정한 창 밖이지만 지금도 인용되는 것이다. **[실측]**은 2026-10-13에 이 보고서를 쓰며 `stock-screener` 저장소를 직접 잰 값이다. 노트 인용은 모두 WebFetch 요약 모델을 거쳤으므로 정확한 문구는 원문으로 다시 확인해야 한다. **추론**이라고 붙인 문장은 출처가 아니라 내 판단이다.

**표의 마지막 열이 이 절의 결론이다.** 「검증됨」의 근거는 거의 모두 머지 PR이 얼마나 늘었는가이고, 그 수치가 품질을 보증하지 않는다는 것은 1차 자료 스스로가 적었다. Microsoft 연구의 한계 문장이 그것이다 ([arXiv 2607.01418](https://arxiv.org/abs/2607.01418)). Spotify는 실패를 세 갈래로 나눴다. PR을 아예 못 만드는 경우, CI에 실패한 PR, 그리고 **CI는 통과했지만 기능이 틀린 PR**이다. Spotify는 세 번째를 신뢰를 갉아먹는 가장 심각한 형태로 꼽았다. 그러나 그 빈도는 공개하지 않았다 ([Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). 품질 쪽 수치는 셋뿐인데 모두 약하다. Intercom의 결함 백로그 절반은 2차 인터뷰이고, Linear의 「수정 없이 머지 가능 50%+」도 2차다. 나머지 하나는 관측 연구 둘이다. DORA 2025는 약 5,000명 설문으로 AI 채택이 **처리량과 전달 불안정성을 함께 높인다**고 보고하며 AI를 "amplifier"라 불렀다 **[1차, 기초·이전]** ([DORA 2025](https://dora.dev/research/2025/dora-report/)). RAMP 연구(arXiv 2608.25241, 2026-08-26 — 논문의 성숙도 모델 이름이며 Ramp 사의 Inspect와는 별개)는 441개 저장소를 분석했다. AI 설정을 커밋하지 않은 저장소는 인지 복잡도 증가가 +53%로, 커밋한 저장소(+27%)의 약 2배였고 정적 분석 경고도 1.7배였다. 다만 저자 스스로 이 결과를 "hypothesis-generating"이라고 했다 **[1차+수치, 관측]** ([arXiv 2608.25241](https://arxiv.org/abs/2608.25241)). METR은 2026-02-24 업데이트에서 한계를 밝혔다. 에이전트를 병렬로 돌리는 개발자는 작업 시간을 잴 수 없고, 30~50%가 AI 없이 하기 싫은 과제를 제출하지 않아 선택 편향이 생겨 **자기 측정 설계가 더는 믿을 신호를 못 낸다**는 것이다 **[1차, 기초·이전]** ([METR](https://metr.org/blog/2026-02-24-uplift-update/)).

두 도구의 비중도 짚어 둔다. 창 안의 1차 사례 가운데 도구를 밝힌 곳은 Claude Code 쪽이 많다. Spotify의 Honk가 Claude 기반이고, Intercom은 Claude Code를 단일 플랫폼으로 표준화했다. Codex 쪽 팀 1차 자료는 OpenAI의 ExecPlan 형식 문서뿐이다. Notion의 「Codex @멘션 → PR」은 팟캐스트 경유다 **[2차]** ([How I AI](https://www.iheart.com/podcast/1333-how-i-ai-273448775/episode/spec-driven-development-the-ai-engineering-workflow-333244314/)). **추론:** 검증된 협업 기제(표면 배정, 세션 격리, verifier, 사람 승인)는 도구에 묶이지 않는다. 팀용 모듈의 기본형도 도구 중립으로 짜는 것이 근거와 맞다.

## 작업 상태는 스레드·세션·이슈에 살고, 배정은 이미 쓰는 표면에서 온다

**작업 하나 = 세션 하나 = PR 하나**가 1차 사례 전체의 분할 단위다. 배정은 새 도구를 만들지 않고 사람이 이미 있는 곳에서 한 줄로 던진다. Stripe는 Slack, Jira, 웹 UI에서 받아 dev box를 할당하고, blueprint가 결정론 단계와 에이전트 단계를 번갈아 돌린다 **[1차·발표 요약, 2026-05-06]** ([Summit](https://background-agents.com/summit/sessions/alistair-gray/)). Shopify는 **공개 Slack 채널의 `@river`로만** 부르고 DM은 막았다 **[1차, 2026-05-28]** ([Shopify](https://shopify.engineering/under-the-river)). GitHub는 이슈를 `@Copilot`에 배정한다 **[1차, 기초·이전]** ([GitHub](https://github.blog/ai-and-ml/github-copilot/how-copilot-helps-build-the-github-platform/)). Vercel은 GitHub webhook이 이슈 큐를 채우고, worker가 작업을 바로 가져가 격리된 sandbox에서 실행한다. 원칙은 "Build one agent per task"이고 종류는 분류, 재현, 수정, 리뷰, backport, 문서, 분석, 구현이다. 다기능 단일 에이전트는 "higher maintenance and troubleshooting burden" 때문에 **명시적으로 기각**했다 **[1차, 2026-08-12]** ([Vercel](https://vercel.com/blog/building-a-software-factory-for-ai-sdk)). Microsoft 연구는 배정 정책보다 **동료에게 보이는 사용**이 채택을 퍼뜨렸다고 보고하고 "treat visible peer use as central to rollout strategy"라고 권한다 **[1차+수치]** ([arXiv 2607.01418](https://arxiv.org/abs/2607.01418)). 한 사람이 여러 세션을 병렬로 돌리는 방식은 Claude Code 팀 사례가 있다. 로컬 5개에 웹 5~10개를 각자 별도 checkout에서 돌리고, **10~20%는 예상 밖 상황으로 버린다** **[2차, 원문은 X 스레드, 기초·이전]** ([InfoQ 2026-01-10](https://infoq.com/news/2026/01/claude-code-creator-workflow/)). next.js의 `AGENTS.md`도 같은 격리를 규칙으로 박았다. 「Prefer a Throwaway Worktree」 절은 사용자 checkout을 건드리지 말고 `/tmp`에 worktree를 만든 뒤 끝나면 지우라고 한다 **[1차 실측]** ([next.js AGENTS.md](https://github.com/vercel/next.js/blob/HEAD/AGENTS.md)).

**작업 상태와 인계의 정본은 작업 단위 표면이다.** Shopify에서는 영속 공개 스레드가 정본이다. 두 번째 팀원이 링크나 멘션으로 들어와도 River는 상태를 잃지 않고, "The next person to hit a similar problem starts from this thread, not from a blank prompt"가 이유다 **[1차]** ([Shopify](https://shopify.engineering/under-the-river)). Ramp는 세션마다 Cloudflare Durable Object에 **전용 SQLite DB**를 두고 수백 세션을 병렬로 돌린다. 세션은 여러 사람이 함께 쓸 수 있고, 코드를 바꾼 프롬프트는 그 사람에게 귀속된다 **[1차, 기초·이전]** ([Ramp](https://engineering.ramp.com/post/why-we-built-our-background-agent)). Vercel에서는 **이슈 코멘트, 라벨, PR 설명**이 에이전트 사이의 인계 기록이다. 분류 에이전트는 코멘트를 달고 라벨을 붙이며, 분석 결과는 증거 파일과 함께 코멘트로 남는다 **[1차]** ([Vercel](https://vercel.com/blog/building-a-software-factory-for-ai-sdk)). Stripe는 상태를 파일이 아니라 코드화한 상태 기계에 둔다 **[1차, 기초·이전]** ([Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). OSS 쪽은 반대 방향에서 같은 것을 보여 준다. pytorch `CLAUDE.md`는 「Use `agent_space/` (git-ignored) … Do not commit files from this directory」라고 쓴다. airflow `AGENTS.md`는 생성물을 `files/` 아래에 두게 한다. 지시 파일 12개를 `progress.md|PLANS.md|exec plan|ADR` 등의 정규식으로 검사했더니 **0건**이었다 **[1차 실측, 2026-10-13, 정규식 밖의 표현은 놓쳤을 수 있음]** ([pytorch CLAUDE.md](https://github.com/pytorch/pytorch/blob/HEAD/CLAUDE.md); [airflow AGENTS.md](https://github.com/apache/airflow/blob/HEAD/AGENTS.md)).

작업별 **plan 파일**은 증거 등급이 한 단계 낮다. OpenAI ExecPlan은 형식을 1차로 확인할 수 있다. 필수 living 절은 Progress, Surprises & Discoveries, Decision Log, Outcomes & Retrospective이고, "fully self-contained"를 요구한다 **[1차, 날짜 미표기]** ([OpenAI Cookbook](https://developers.openai.com/cookbook/articles/codex_exec_plans)). 그러나 OpenAI 내부 팀이 몇 개를, 얼마 동안, 몇 명이 운영했는지는 「Harness engineering」 원문이 이번에도 403으로 열리지 않아 **2차 요약으로만** 남았다 ([openai.com](https://openai.com/index/harness-engineering/)). Every의 `docs/plans/`와 `todos/`는 1차로 서술돼 있지만 제품 하나를 **사실상 한 사람**이 만드는 구조에서 나왔다 **[1차·수치 없음]** ([Every Guide](https://every.to/guides/compound-engineering); [Every 2025-12-11](https://every.to/chain-of-thought/compound-engineering-how-every-codes-with-agents)). 여러 사람이 동시에 에이전트 작업을 배정할 때 누가 무엇을 잡고 있는지 조정하는 방법은 공백으로 남는다. Ramp의 프롬프트별 귀속 말고는 1차 서술을 찾지 못했다. 동기식 대안으로는 Scania의 mob이 있다. 4명이 한 화면에서 에이전트를 함께 모니 상태 공유와 리뷰가 실시간으로 녹아들었다. 그러나 마감 압박으로 흩어졌다가 다시 합칠 때 「고통스럽고 예상보다 느렸다」고 적었다 **[1차·수치 없음, 기초·이전]** ([Crisp](https://blog.crisp.se/2025/06/02/michaelgothe/mob-programming-with-ai-inside-a-high-performing-teams-journey)).

## 공유 지식은 사람이 고치는 지시 파일 하나와 기계식 신선도 장치다

다인 OSS의 실측은 공유 규약의 실제 모습을 가장 직접 보여 준다. 유명 저장소 35곳 중 **26곳**이 루트에 `AGENTS.md`, `CLAUDE.md`, `copilot-instructions.md` 중 하나 이상을 커밋했다 **[1차 실측, 2026-10-13]**. 내용은 두 계열로 나뉜다. 첫째는 **운영 매뉴얼형**이다. 빌드·시험 명령, 저장소 구조, 아키텍처 경계, PR 규칙, 「리뷰어가 잡는 것」을 담으며 next.js(520줄), langchain(390), pytorch(356), airflow(251), bun(240)이 여기 든다. 둘째는 **정책 집행형**으로, 에이전트에게 프로젝트의 AI 정책을 따르거나 거절하라고 지시한다. QEMU, CPython, Rust, Node, Kubernetes가 그렇다 ([next.js](https://github.com/vercel/next.js/blob/HEAD/AGENTS.md); [bun](https://github.com/oven-sh/bun/blob/HEAD/CLAUDE.md); [rust](https://github.com/rust-lang/rust/blob/HEAD/AGENTS.md)). 지배적인 형태는 **정본 하나에 도구별 포인터를 두는 것**이다. ruff와 firefox는 `CLAUDE.md`가 `@AGENTS.md` 한 줄이고, bun과 pytorch는 방향이 반대다. zed는 `.rules` 하나를 셋이 가리키고, transformers는 `.ai/AGENTS.md`를 쓴다 ([zed .rules](https://github.com/zed-industries/zed/blob/HEAD/.rules)). Stripe도 Cursor rule을 정본으로 두고 Claude Code용으로 동기화한다 **[1차, 기초·이전]** ([Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)).

**작성자는 압도적으로 사람이고, 「여럿이 조금씩 + 소유자 한 명」 꼴이다.** 측정한 path 이력은 다음과 같다. airflow `AGENTS.md`는 70커밋에 19명이 썼고 potiuk이 36건이다. home-assistant `copilot-instructions.md`는 52커밋에 20명, next.js는 40커밋에 16명이다. bun은 51커밋에 6명이고 Jarred-Sumner가 32건이다. 봇 커밋은 merge bot과 소수뿐이다. `claude[bot]` 2건, `robobun` 5건, `zaniebot` 2건이 전부다 **[1차 실측, GitHub API path 이력 — rename을 따라가지 않고 상한 100커밋]** ([airflow 이력](https://github.com/apache/airflow/commits/HEAD/AGENTS.md); [bun 이력](https://github.com/oven-sh/bun/commits/HEAD/CLAUDE.md)). 반례도 하나 있다. openai/codex는 `AGENTS.md`에 78커밋을 쌓은 뒤 2026-09-30에 PR #49713으로 루트 `AGENTS.md`, `.codex/skills/`, 환경 설정을 지웠다. PR 본문에 사유가 없고 작성자가 `copyberry[bot]`이라, 실패의 증거로도 성공의 증거로도 쓸 수 없다 **[1차]** ([PR #49713](https://github.com/openai/codex/pull/49713)). 기업 쪽은 작성 주체가 셋으로 갈린다. 첫째는 **에이전트가 초안을 쓰고 소유 팀이 MR로 검토**하는 방식이다. Cloudflare는 Backstage 카탈로그와 빌드 감지로 약 3,900개 저장소의 AGENTS.md를 생성하고, "the system opens a merge request so the owning team can review and refine it" 절차를 둔다 **[1차·수치 없음(효과)]** ([Cloudflare](https://blog.cloudflare.com/internal-ai-engineering-stack/)). 둘째는 **사람이 PR 리뷰 중에 에이전트에게 지시해 추가**하는 방식이다. Claude Code 팀은 동료 PR에서 `@.claude` 태그로 CLAUDE.md에 학습을 더한다 **[2차, 기초·이전]** ([InfoQ](https://infoq.com/news/2026/01/claude-code-creator-workflow/)). 셋째는 **에이전트가 자기 skill을 직접 고치는** 방식이다. Intercom의 flaky-spec 에이전트가 그렇다 **[2차·팟캐스트]** ([ChatPRD](https://www.chatprd.ai/how-i-ai/how-intercom-doubled-engineering-output-brian-scanlan-ai-workflows-for-claude-code)).

신선도는 문서를 지키라는 당부가 아니라 **기계 장치**로 지킨다. Cloudflare는 "A stale AGENTS.md can be worse than no file at all"이라고 쓰고, AI Code Reviewer가 저장소 변경을 보고 AGENTS.md 갱신이 필요하다고 표시하게 했다 **[1차·수치 없음]** ([Cloudflare](https://blog.cloudflare.com/internal-ai-engineering-stack/)). Intercom은 주간 GitHub Action으로 모든 CLAUDE.md를 fact-check한다 **[1차·수치 없음, 기초·이전]** ([Intercom](https://ideas.fin.ai/p/how-we-use-claude-code-today-at-intercom)). Anthropic은 PreToolUse hook으로 skill 사용량을 기록해 잘 안 쓰이는 skill을 찾는다. 승격도 중앙 관문 없이 한다. sandbox 폴더에 올려 Slack으로 알리고, 견인력이 생기면 PR로 marketplace에 올린다. "The highest-signal content in any skill is the Gotchas section"이라는 문장도 있다 **[1차·수치 없음, 게시일 2026-06-03/2026-03-17 불일치]** ([claude.dev](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/)). LinkedIn은 playbook을 매시간 전 랩톱에 갱신하고 "Aggressive deprecation"으로 걷어낸다 **[1차 발표, 2026-09-19]** ([InfoQ](https://www.infoq.com/presentations/linkedin-context-engineering/)). Every는 학습 문서가 쌓이자 v2.52.0(2026-03-25)에 consolidation과 overlap detection을 **뒤늦게** 붙였다 **[1차 CHANGELOG]** ([CHANGELOG](https://raw.githubusercontent.com/EveryInc/compound-engineering-plugin/main/CHANGELOG.md)). Thoughtworks Radar Vol.34(2026-04)는 여러 내부 팀의 Spec Kit 사용을 보고했다. instruction bloat가 context rot으로 이어졌고, 한 팀은 재사용 지침을 **skills로 빼서** 해결했다. 같은 판은 「Agent instruction bloat」를 Caution에 올렸다 **[1차·수치 없음, 기초·이전 경계]** ([Thoughtworks Radar](https://www.thoughtworks.com/en-au/radar/languages-and-frameworks/github-spec-kit)).

연구는 이 장치들이 왜 필요한지 보여 준다. 2,303개 context file을 분석한 연구에 따르면 파일은 **추가 위주로** 자란다. 커밋당 삭제는 중앙값 15단어 미만이고, 보안과 성능을 다루는 비율은 각각 14.5%뿐이다 **[2차 — 본문을 fetch 요약으로 읽음, 2025-11-17]** ([arXiv 2511.12884](https://arxiv.org/html/2511.12884v1)). RAMP는 AI 설정 산출물의 **73.8%가 한 번 커밋된 뒤 다시 고쳐지지 않는다**고 보고했다 **[1차+수치, 관측]** ([arXiv 2608.25241](https://arxiv.org/abs/2608.25241)). ETH의 「Evaluating AGENTS.md」 v3(2026-09-29) 초록은 context file이 "does not generally improve task success rates, while increasing inference cost by over 20%"라고 쓴다. LLM이 만든 파일과 개발자가 커밋한 파일 모두에서 그랬고, repository overview는 도움이 안 됐지만 비표준 관행을 지정하는 데는 유용했다 **[2차 — 초록]** ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). 지시 파일을 사람과 에이전트 중 누가 고치는지를 대규모로 센 연구는 아직 없다. Voria 등의 연구는 10,000건 이상의 수정 커밋을 분류하겠다는 registered report 단계라 결과가 없다 ([arXiv 2606.25257](https://arxiv.org/html/2606.25257v1)).

**결정 기록은 OSS에서 사람이 쓴 정책이고, 에이전트 파일은 그 얇은 운영화다.** QEMU는 `docs/devel/code-provenance.rst`를, PyTorch는 `AI_POLICY.md`를, Home Assistant는 공개 웹 문서를 정본으로 가리킨다. Rust는 더 나아갔다. 「Agent instructions such as `CLAUDE.md`, `AGENTS.md`, and skills … may only link to, summarize, or conservatively operationalize existing [policy]」라고 써서 **지시 파일이 새 결정을 만들지 못하게** 했다 **[1차, 2026-08-12 첫 커밋]** ([rust AGENTS.md](https://github.com/rust-lang/rust/blob/HEAD/AGENTS.md); [HA AI_POLICY.md](https://github.com/home-assistant/core/blob/HEAD/AI_POLICY.md)). 기업 쪽에서 가장 가까운 것도 결정의 이유가 아니다. Cloudflare Engineering Codex는 AI가 증류한 「If you need X, use Y」식 **규칙**이고, 증류 결과를 사람이 승인하는지는 서술이 없다 ([Cloudflare](https://blog.cloudflare.com/internal-ai-engineering-stack/)). Uber의 AI Context Graph는 design docs를 상시 로드하지 않고 **검색해서 찾아오는** 그래프에 넣는다 **[1차, 2026-08-27]** ([Uber](https://www.uber.com/us/en/blog/efficient-software-factory/)).

## 리뷰는 결정론 검증, LLM 거부권, 사람 승인의 3단이다

머지 절차는 1차 사례 사이에서 가장 일관된 영역이다. 첫 단은 **결정론 검증**이다. Spotify는 저장소 내용을 보고 자동으로 켜지는 독립 verifier(예: `pom.xml`이 있으면 Maven verifier)를 MCP 도구로 노출하고, PR을 열기 전 **stop hook**에서 관련 verifier를 모두 돌린다 **[1차, 기초·이전]** ([Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). Stripe는 "After the second push and CI run, we send the branch back to its human operator"라는 **CI 재시도 상한 2회**를 둔다 **[1차, 기초·이전]** ([Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). Airbnb는 단계마다 실패하면 오류를 넣어 재시도하되 횟수에 상한을 걸었다. 그리고 "prompt engineering was less effective than retrying conversion multiple times"라는 교훈을 남겼다 **[1차, 기초·이전]** ([InfoQ](https://www.infoq.com/news/2025/03/airbnb-llm-test-migration/)). 둘째 단은 **LLM 리뷰 또는 판정**이다. 확인된 쓰임은 자기 결론을 확인하는 용도가 아니라 **거부권**이다. Spotify의 judge는 diff를 원 프롬프트와 대조해 약 1/4을 거부한다. 주된 거부 사유는 「프롬프트가 정한 범위 밖으로 나감」이고, 거부된 것의 절반은 에이전트가 스스로 고쳤다 **[1차+수치]** ([Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). Cloudflare는 코디네이터가 MR을 trivial, lite, full **위험 등급**으로 나눈 뒤 품질·보안·Codex 준수·문서·성능·릴리스 영향 전문 에이전트에게 맡긴다. 이 리뷰가 머지를 차단하는지는 원문에 없다 **[1차·수치 없음]** ([Cloudflare](https://blog.cloudflare.com/internal-ai-engineering-stack/)). Stripe도 2026-05 발표에서 risk profile과 ownership mapping 기반 리뷰를 언급했다 ([Summit](https://background-agents.com/summit/sessions/alistair-gray/)). Every는 14개가 넘는 리뷰 에이전트를 병렬로 돌려 P1/P2/P3로 분류하고, 그 뒤에 사람이 리뷰한다 **[1차·수치 없음]** ([Every Guide](https://every.to/guides/compound-engineering)).

셋째 단인 **사람 승인**은 여러 곳이 규칙으로 박았다. Vercel은 리뷰 에이전트가 위험을 점수화해 낮으면 approve까지 하지만 "Nothing is merged without approval from a human on the AI SDK team"이다 **[1차, 2026-08-12]** ([Vercel](https://vercel.com/blog/building-a-software-factory-for-ai-sdk)). Ramp는 PR을 **요청한 사람의 GitHub 토큰**으로 만든다. 앱 자격증명을 쓰면 누구나 자기 변경을 스스로 승인할 수 있게 되기 때문이며, 원문은 "You do not want to knowingly create a vector for unreviewed code"라고 쓴다 **[1차, 기초·이전]** ([Ramp](https://engineering.ramp.com/post/why-we-built-our-background-agent)). 반대쪽 끝도 있다. Spotify의 저위험 유지보수 PR은 대부분 auto-merge이고 ([Spotify 2026-06](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint)), Intercom은 자동 승인 비중을 늘리고 있다 **[2차]** ([DX](https://newsletter.getdx.com/p/doubling-the-productivity-of-your)). Intercom은 LLM judge로 과거 PR 설명을 평가하다가 **AI가 쓴 PR 설명의 품질이 시간이 지나며 떨어진 것**을 발견했다. 그래서 모든 PR 생성을 hook으로 가로채 표준 skill로 보낸다 **[2차]** ([ChatPRD](https://www.chatprd.ai/how-i-ai/how-intercom-doubled-engineering-output-brian-scanlan-ai-workflows-for-claude-code)).

OSS는 같은 승인 원칙을 **책임 귀속과 공개 표기**로 명문화했다. LLVM의 2026-01 「human in the loop」 정책은 기여자가 LLM 생성물을 모두 읽은 뒤 리뷰를 요청하고 저자로서 책임지게 한다 **[1차, 기초·이전]** ([LLVM](https://www.llvm.org/docs/AIToolPolicy.html)). Node `AGENTS.md`(2026-08-22)는 `Assisted-by:`를 필수로 하고, `Signed-off-by`는 사람만 달 수 있으며, 에이전트의 push와 무감독 PR을 금지한다 ([node](https://github.com/nodejs/node/blob/HEAD/AGENTS.md)). Kubernetes는 `Co-authored-by`를 금지하고 AI 사용 공개를 요구한다 ([k8s](https://github.com/kubernetes/kubernetes/blob/HEAD/AGENTS.md)). Home Assistant와 PyTorch는 **완전 자율 에이전트의 기여를 받지 않는다** ([HA](https://github.com/home-assistant/core/blob/HEAD/AI_POLICY.md); [pytorch](https://github.com/pytorch/pytorch/blob/HEAD/AI_POLICY.md)) **[모두 1차]**. Rust는 신규 기여자가 LLM으로 PR을 만들려면 **그 PR을 맡을 바로 그 리뷰어**와 먼저 이야기하게 한다 **[1차, 2026-08-05]** ([forge](https://forge.rust-lang.org/policies/llm-usage.html)). 효과를 수로 낸 것은 Linux뿐이다. 7.2-rc4 기준 1,200개가 넘는 커밋이 `Assisted-by`를 달았지만, 상당수 기계 생성 패치에는 태그가 없다고 보고됐다 **[2차, LWN 2026-07-21]** ([LWN](https://lwn.net/SubscriberLink/1083275/d5518174ec4dcbcb/)). **추론:** maintainer와 외부 기여자의 비대칭은 흔하다(Ghostty는 maintainer를 면제하고, Node는 기존 collaborator만 허용한다). 팀 내부에서는 신뢰로 풀고 경계에서만 규칙을 세게 거는 구조다.

## 이름 붙은 방법론과 공유 상태 파일에는 팀 증거가 없다

사용자가 「제안이 아닌 검증」을 요구했으므로, 팀 증거가 없는 것을 따로 모은다. 「없음」은 부재를 확인한 것이 아니라 조사 범위(노트 세 개, 각 약 30~35회 도구 호출) 안에서 **찾지 못한** 것이다.

| 대상 | 팀 증거 | 등급 | 근거 |
|---|---|---|---|

이 표의 의미는 하나다. **「이름 붙은 방법론 + 다인원 제품팀 + 규모·기간·결과·실패를 적은 1차 회고」를 모두 갖춘 사례는 2026-10-13 기준으로 하나도 찾지 못했다.** 팀 증거는 방법론 단위가 아니라 **플랫폼 단위**(Stripe, Shopify, Spotify, Vercel의 배경 에이전트)와 **협업 형태 단위**(mob)로 존재한다. 이름 붙은 방법론 가운데 팀 보고가 가장 강한 것은 Spec Kit(Thoughtworks)이고, 그 보고의 핵심은 성과가 아니라 실패 형태 둘이다. instruction bloat가 context rot으로 이어진다는 것, 그리고 장황한 markdown이 리뷰 부담을 키운다는 것이다. Böckeler는 1인 평가에서 같은 것을 독립적으로 관찰했다. 「I'd rather review code than all these markdown files」라는 말이 그것이다 **[1차, 기초·이전]** ([martinfowler.com 2025-10-15](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

## 이전 보고서가 과장한 다섯 곳

같은 대화의 이전 보고서 「팀 단위 에이전트 하네스 관행」은 벤더 지침과 일화를 중심으로 썼다. 새 노트는 실천 팀과 공개 저장소를 직접 쟀고, 이 노트들이 이전 보고서와 어긋나는 곳에서는 새 노트를 따른다.

| 이전 보고서의 문장 | 새 증거 | 정정 |
|---|---|---|
| 진입 파일은 「100~200줄짜리 지도」로 **수렴했다** | 다인 OSS의 운영 매뉴얼형 파일은 240~520줄(next.js 520, langchain 390, pytorch 356) [1차 실측]. context file 중앙값은 Claude 485단어 ([arXiv 2511.12884](https://arxiv.org/html/2511.12884v1), 2차) | 수렴한 것은 **벤더 권고**이고 실천은 아니다. 실천에서 수렴한 것은 길이가 아니라 「정본 하나 + 도구별 포인터」 형태다 |
| 작업 단위 plan 파일(ExecPlan)이 팀에 **적합**, 처방 1단계로 `docs/exec-plans/active/` | 다인 OSS의 `main`에서 plan 파일 사례 0건. 1차로 확인된 팀 상태 표면은 스레드, 세션 DB, 이슈 코멘트·라벨, PR 설명, 상태 기계 | 「적합」은 추론이었다. **검증된 기본값은 트래커·PR**이고 plan 파일은 미검증 선택지로 내린다 |
| 대형 조직은 「에이전트가 쓴다」와 「모두가 읽는다」 사이에 **반드시** 소유자와 리뷰를 끼운다 | Intercom의 flaky-spec 에이전트는 자기 skill을 직접 고친다(2차). Anthropic skill은 중앙 관문이 없고, Shopify는 리뷰 주체를 서술하지 않았다 | 「반드시」는 과장이다. 사람 MR 리뷰가 1차로 확인된 곳은 Cloudflare와 OSS이고, 나머지는 **사용량 텔레메트리**가 통제 수단이다 |
| OpenAI는 저장소 안에 계획·결정을 두는 쪽을 가장 명시적으로 지지 | openai/codex가 2026-09-30에 루트 `AGENTS.md`와 `.codex/skills/`를 사유 없이 삭제 ([PR #49713](https://github.com/openai/codex/pull/49713)) | 지지는 글(2차) 수준이다. OpenAI의 공개 저장소는 지금 그 패턴을 보여 주지 않는다. 삭제를 실패의 근거로 쓰지도 않는다 |
| ETH 연구: 개발자가 쓴 파일은 성공률 평균 +4%p | v3(2026-09-29) 초록은 LLM 생성 파일과 개발자 커밋 파일 모두 「대체로 성공률을 올리지 않음」, 비용 +20% 이상 | +4%p는 v1 본문의 수치이고 v3에서 유지되는지 미확인이다. 「개발자 작성은 낫다」를 근거로 쓰지 않는다 |

이전 보고서의 「에이전트 초안 + 사람 승인 PR」 처방도 근거를 다시 단다. 이전 보고서는 Kiro 문서와 Vercel adr-skill(2차)을 근거로 들었다. 새 노트에서 1차로 확인된 대응물은 **Cloudflare의 AGENTS.md 생성 → 소유 팀 MR**이다. 이것은 지시 파일에 대한 검증이고, ADR에 대한 검증은 아니다. 하네스 수치 하나도 바로잡는다. 이전 보고서는 「ADR 디렉터리 175개 파일」이라고 썼는데, 여기에는 템플릿과 README가 들어 있다. ADR 파일 자체는 번호가 0175까지 가지만 **173개**이고, 173개 모두 `applies_to`를 가진다. `premise` 펜스는 101개 ADR에 합 154개다(템플릿 제외) **[실측, 2026-10-13]**.

## 이 하네스는 팀 관점에서 검증된 관행의 반대편에 서 있다

평가 대상 하네스를 2026-10-13에 다시 쟀다 **[실측]**. `docs/progress.md`는 214,121바이트에 1,829줄이고, 최근 30일 동안 이 파일을 건드린 커밋이 297건이다. `CLAUDE.md`는 24,313바이트, `.claude/rules/`는 디스크 기준 약 100KB이고(이전 보고서는 본문 81KB로 잼) 루트 `AGENTS.md`는 없다. SessionStart 주입량(약 7.3KB)과 `premise` 재검증 비용(고정비 34.6초, 약 43초)은 이전 보고서가 같은 날 잰 값이다. 네 축을 검증된 관행과 나란히 놓으면 아래와 같다.

| 축 | 검증된 팀 관행 | 이 하네스 | 판정 |
|---|---|---|---|
| 작업 상태·인계 | 작업 단위 표면: 스레드, 세션 DB, 이슈·PR (Shopify, Ramp, Vercel) [1차]. scratch는 git-ignore (pytorch, airflow) [1차] | 전역 progress.md를 `main`에 누적하고 세션마다 주입 | **반대 방향.** 팀 증거 없음. 지금 충돌이 없는 이유는 구조가 아니라 한 사람이 쓰기를 직렬화하기 때문이다(이전 보고서 실측: 양쪽 부모가 progress.md를 고친 머지 0건) |
| 공유 규약 | 정본 하나 + 도구별 포인터, 사람 maintainer 여럿이 PR로 고침 (OSS) [1차 실측] | `CLAUDE.md` + rules 100KB. 사람 사용자 결정과 에이전트 해석을 갈라 적지만 대부분 에이전트가 갱신. `AGENTS.md` 없음 | 형태는 부분 일치(경로 규칙 분할 = Thoughtworks의 skills 분리와 같은 방향). **Codex 사용자에게 보이는 정본이 없다** |
| 결정 | 사람이 쓴 정책을 정본으로, 에이전트 파일은 얇은 운영화 (Rust, QEMU, PyTorch) [1차]. 결정 근거는 검색 대상 (Uber) [1차] | 에이전트가 쓴 ADR 173개에 `applies_to` 포인터와 실행 가능 `premise` | **반대 방향이면서 일부는 앞섬.** 작성 주체는 관행과 반대이고, 낡음 측정은 대응물이 없다 |
| 신선도 | 리뷰어 에이전트 플래그 (Cloudflare), 주간 fact-check (Intercom), 사용량 텔레메트리와 폐기 (Anthropic, LinkedIn), 중복 탐지 (Every) | `premise` 펜스를 SessionStart마다 실행해 「참/발견/판정 불가」 출력. 폐기·부피 억제 장치 없음 | 낡음 측정은 **앞섬**(결정적), 부피 억제는 **뒤처짐** |
| 배정 | 기존 표면에서 한 줄, 작업 하나 = 세션 하나 = PR 하나 [1차] | 한 운영자와 세션 하나. 탐색용 브랜치만 사용 | 팀 기제 없음(솔로 전제) |
| 리뷰·머지 | 결정론 verifier → LLM 거부권 → 사람 승인, CI 재시도 상한, 셀프 승인 차단 [1차] | 구현 **전** 독립 반증 서브에이전트, 드라이런, 펜스. `main`에 직접 커밋하고 사람 승인 관문은 구조상 없음 | 계획 단계 반증은 **대응물 없음(앞섬)**. 머지 전 사람 승인은 **없음(뒤처짐)** |

**추론:** 이 표에서 「앞섬」과 「반대 방향」을 섞으면 안 된다. 전역 progress.md와 에이전트 작성 ADR은 검증된 팀 관행이 아직 도달하지 못한 곳이 아니다. **다인 프로젝트들이 일부러 다른 길을 고른 곳**이다. OSS는 동적인 「어디까지·왜」를 PR, 이슈, 커밋 이력에 두고, 정적인 「어떻게」만 저장소 파일에 둔다. 그 이유를 밝힌 1차 진술은 찾지 못했다. 그러나 Harper Reed의 「merges are horrific」 고백과 이전 보고서가 모은 일화들(swarm #33의 8개 중 7개 충돌, cabros-bot의 40%)이 같은 방향을 가리킨다. 반면 `premise` 펜스와 계획 단계 반증은 검증된 관행이 같은 문제를 더 약하게 푸는 곳이다. 같은 문제를 푸는 장치로 Cloudflare 리뷰어의 「갱신 필요」 플래그, Copilot Memory의 인용 재검증, Spotify judge의 사후 거부권이 있고, 이 하네스의 것은 그보다 결정적이다. 다만 결정성이 팀에서 가치를 내는지 잰 사례는 없다. 이전 보고서가 지적했듯 `premise`의 상당수는 운영자 한 사람의 로컬 DB를 사실로 삼는다. 그래서 팀에서는 「앞섬」이 「사람마다 다른 답」으로 바뀔 위험도 함께 진다.

## 검증된 것만으로 구성한 팀 협업 기본형

## Conclusion

이번 조사로 이전 판단의 무게 중심이 옮겨졌다. 이전 보고서는 「전역 progress.md를 작업 단위 plan 파일로 해체하라」고 처방했다. 그러나 다인 팀이 실제로 고른 것은 더 나은 파일이 아니라 **파일 밖**이었다. 진행과 결정의 이유는 PR, 이슈, 스레드에 살고, 저장소에는 사람이 고치는 정적 규약만 남는다. plan 파일은 1인이나 단일 계보에서만 1차로 확인된다. 그러니 팀 모듈의 기본값은 트래커이고, plan 파일은 선택지다. 「검증됨」이라는 말의 범위도 좁혀 읽어야 한다. 1차 사례들이 증명한 것은 **이 뼈대로 PR이 더 많이 머지된다**는 것이다. **이 뼈대로 틀린 코드가 덜 들어간다**는 것은 아무도 수로 보이지 않았다. Spotify가 가장 심각하다고 꼽은 「CI 통과·기능 오류 PR」의 빈도조차 공개되지 않았다.

이 공백이 이 하네스가 들고 갈 몫이다. 업계의 품질 장치는 대부분 사후 거부권(judge, AI 리뷰)과 주기적 점검(fact-check)이다. 이 하네스의 `premise` 펜스와 계획 단계 반증은 **틀린 전제가 조용히 살아남지 못하게 하는 사전 장치**이고, 공개된 팀 사례 가운데 대응물이 없다. 따라서 팀 모듈을 만든다면 검증된 19개 요소로 뼈대를 세우는 것이 출발점이다. 하네스 고유 요소는 그 위에 「미검증」 계층으로 얹는다. 그리고 그 계층의 가치는 업계가 아직 재지 않은 지표, 즉 **CI를 통과했지만 기능이 틀린 PR의 비율과 낡은 결정이 발견되기까지 걸린 시간**으로 재야 한다. 그래야 이 하네스가 앞선 것인지, 단지 다른 것인지가 처음으로 갈린다.
